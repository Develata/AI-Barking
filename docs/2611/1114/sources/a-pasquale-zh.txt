广告

超过七千个用 Lovable 搭建的网站，向任何打开页面的人返回个人数据，既不用注册，也不用密码。这是德国安全公司 Crissy Field 测出来的结果：他们扫描了该平台上创建的 159,041 个项目，发现护照号码、支付信息和超过 20 万条聊天消息，浏览器里就能直接读到。调查由莉娜·克内斯（Lina Knees）署名，刊登在德国经济类日报 Handelsblatt [https://www.handelsblatt.com/technik/ki/lovable-experten-finden-datenluecke-bei-beliebter-ki-coding-plattform/100264923.html]，该报与研究人员合作完成报道。最新数字见 Crissy Field 发布的报告 [https://www.crissyfield.de/research/lovable-en/]。

在同一领域,Apiiro 在公开的 GitHub 文件中发现了 Claude Code 的明文密码和 API 密钥 [https://pasqualepillitteri.it/zh/news/31174/claude-code-github-xielu-mima-api-miyao-apiiro]。

Lovable 是一家总部位于斯德哥尔摩的瑞典平台，能把一句日常语言写成的话变成可以运行的网页应用。用户写下“我想要一个让客户预订餐桌的网站”，平台就自动写代码、搭数据库，再发布到一个现成可用的地址。公司由安东·奥西卡（Anton Osika）和法比安·赫丁（Fabian Hedin）于 2023 年创立，2026 年 8 月完成 4 亿美元融资，估值达 133 亿美元 [https://www.techzine.eu/news/devops/143582/lovable-valued-at-13-3-billion-after-new-funding/]。据其向 Handelsblatt 提供的数据，平台上已创建超过 5000 万个项目，每周新增 120 万个。搭建这些项目的人，绝大多数不会编程，说白了，这正是他们选 Lovable 的原因。

再说 Crissy Field。这是一家总部在汉堡的公司，做渗透测试和代码审计，客户包括 Apple、Otto 和 DeepL。故事里的第三个名字是 Supabase，Lovable 生成的应用几乎都把数据放在这项服务上，也就是一个开箱即用、由浏览器直接查询的数据库。

Crissy Field 对 159,041 个 Lovable 项目的扫描，数据来自这家汉堡安全公司发布的报告

立即试用

你用 Lovable 发布过应用吗？打开编辑器的发布窗口，安全扫描就会自动启动，只需你已有的账号，不收费。借助 Wiz 的深度版本，则需要在工作区层面完成关联。Supabase 的文档讲解了如何关闭那些敞开的数据表。

Crissy Field 的研究人员发现了什么

扫描从 Common Crawl 起步，这是一个定期为开放网络拍摄快照的公共档案库。研究人员从中提取出 2025 年 12 月至 2026 年 9 月之间发布的 159,041 个 Lovable 项目，再核实其中有多少连接了 Supabase 数据库，结果是 34,545 个。关键一步在后面：在 24,664 个网站上，数据库在页面加载时就已经返回记录，访问者既不用登录，也不用点击任何东西。

页面加载数据本身并不算缺陷，报告作者也这么说。商品目录或公开留言板总得展示点什么。问题出在后头：有人拿页面里的同一把密钥，向数据库索取更多内容。在其中 7,403 个网站上（占细查样本的 30%），10,560 张不同的数据表里出现了带电子邮件地址的记录。这些是真人的地址，不是企业的联系邮箱。

方法上有一点比数字更要紧：没有人强行突破任何东西。研究人员只使用了这些网站向任何访问者开放的权限，发出的都是只读请求，用的也是页面交给浏览器的同一把密钥。报社在 8 月中旬收到最初的线索，经核实后，把结果摆到了 Lovable 面前。

从论坛到护照，最糟糕的几个案例

从敞开的数据表里流出来的东西，同寻常的新闻邮件列表完全不是一回事。一个德国生活方式论坛暴露了超过 8 万份完整档案，含姓名、电子邮件、出生日期和性别，外加 20 多万条聊天消息。活动主办方和餐厅则让人读到数以万计的订单和已售门票，包括电子邮件、电话号码、邮寄地址、支付信息、票码，而这恰恰是门口诈骗所需的全部材料。

一家物业管理公司把内部邮件的 AI 摘要放在了可以读取的位置，里面有租户、业主、商业伙伴的信息。最严重的一例涉及一家服务商，其明文保存了一千多条含身份证件的记录，有护照号码、有效期和国籍，报告称这些材料足以实施身份盗用。另一个案例里，一家企业发给客户的 28 万封邮件可供查阅。此外还有合同、发票、私人相册，以及在 WhatsApp 上交换的内部通信。

这些数据没有一条来自严格意义上的入侵。它们就摆在那里，门后无人上锁。据 Handelsblatt 报道，想要拿走这些数据的人，至少有一年时间可以动手。

需要注意的局限

那个 30% 并不能说明有多少 Lovable 应用在泄露数据。它只适用于被细查的 24,664 个网站，作者明确写道，不应把它当作已确认的泄露率。在五千万个项目里，大部分在一条提示词之后就被放弃，或从未被收录，真实比例依然未知。

样本来自 Common Crawl，它只收集开放网络上能找到的东西，所以只通过私人链接分享应用的人不在档案库中，这项研究既不能为他们开脱，也不能指控他们。检索标准同样朝两个相反的方向削减：找到的部分邮箱是公开联系方式或测试数据，而那些装满个人信息却不含邮箱的数据表，则被排除在统计之外。

Handelsblatt 的数字与报告的数字并不一致，因为报告发布在后，更新了报纸上刊出的分析。读到这件事的人会因来源不同看到不同数字，可信的是后者。

没人能确定这些数据是否已被他人提取。没有证据不等于没发生过，只是意味着没有任何记录能说明谁查询过这些数据库。

原因何在：公开密钥和缺失的规则

说到这里就涉及技术了，不过三句话讲得清。用 Lovable 搭建的应用把数据存进 Supabase，再通过浏览器用一把叫 anon key 的密钥去调取，每个项目只有一把，写在页面源代码里，任何人右键就能看到。这把密钥不是秘密，也不必是秘密。真正决定能读什么的，是写在数据库内部的访问规则，叫 Row Level Security，逐表逐行规定谁能看到什么。规则要是缺失，或者写得太宽，数据库就会对所有人有问有答。

这正是 2025 年春天被登记为 CVE-2025-48757 [https://nvd.nist.gov/vuln/detail/CVE-2025-48757] 的同一类缺陷，当时研究员马特·帕尔默（Matt Palmer）发现，平台展示区里有 170 个 Lovable 应用，会向未认证的访客返回个人数据。十八个月过去，这已不是孤立事件，而是一种成规模的常态。原因在于这些应用的诞生方式：写提示词的人不知道有个东西叫 Row Level Security，自然也就无从发现它是关着的。

Supabase 其间调整了默认设置。已有项目的人值得留意这条时间线。2026 年 4 月 28 日起，可以选择不再把新建数据表自动暴露给网页接口；5 月 30 日起，这一选项成为新项目的默认行为；而从 2026 年 10 月 30 日起，它对所有现有项目生效，详见官方更新日志 [https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically]。不过同一份文件里有个分量不轻的保留条款：已经存在的数据表保留现有权限，依然可以访问。这次改动保护的是新表，而不是那些一年来一直在漏数据的旧表。

Lovable 回应：安全是共同责任

在 Lovable 看来，这是整个行业都已知且普遍存在的配置问题。公司的立场由其安全负责人伊戈尔·安德留申科（Igor Andriushchenko）转述，即安全是提供工具的一方与发布应用的一方之间的共同责任。Handelsblatt 写道，报社自己的核查所指向的并不止某一家供应商，因为只要数据库被匆忙接到网站上，同样的配置缺陷就会出现。再看服务条款，白纸黑字写明，应用及数据处理由客户负责。

公平地说，Lovable 确实筑起了一些防线。官方文档 [https://docs.lovable.dev/features/security]介绍了一项基础扫描，打开发布窗口时自动运行，检查的内容之一正是过于宽松的访问规则；此外还有基于 Wiz 的深度扫描，供将其关联到工作区的用户使用。不过同一页上有一条真正重要的提醒：这些工具有帮助，但不能取代真正的安全审查，对于涉及敏感数据的应用，公司建议找人做一次审查。

报告毫不绕弯地提出了另一点。Lovable 的营销承诺不需要技术能力，读到这句承诺的人很容易理解成连安全能力也不需要。两者并不等同，而这中间的差距，由终端用户来买单。就是那个订了一张餐桌、或上传了护照复印件的人。

如何检查你的应用是否在泄露数据

用 Lovable、Replit 或类似生成器发布过东西的人，几分钟内就能自查，不需要专业工具。顺序很重要。

打开你网站的页面，查看源代码。搜索字符串 supabase.co。如果有，说明应用连接着 Supabase 数据库，公开密钥就在旁边，这是正常现象。

进入 Supabase 控制台，打开数据表那一栏。每张含有个人数据的表都必须启用 Row Level Security。与在控制台手动创建的表不同，由 AI 或 SQL 脚本创建的表，往往一出生就没有开启。

检查规则，别只看开关。允许任何人读取的规则，等于没有规则，因为访问权限应该绑定到数据所属的用户，而不是单纯“打开了页面”这件事。

每次发布前都运行安全扫描，认真读警告，不要直接关掉。如果应用处理身份证件或支付，请把专业人员的审查也算进预算。

反过来也一样，对只是使用这类应用、而不是搭建它们的人。在向一个看起来像是匆匆拼凑出来的表单网站上传证件复印件之前，最好先问问是谁、用什么工具做的。今年我们已经在别的形态里见过这种动态，从让 10 万个工作区的密钥陷入风险的 Railway 攻击 [/zh/news/26687/railway-heike-gongji-100000-workspace-miyao-fengxian]，到OpenCode 被攻破、半个行业的 API 密钥受牵连 [/zh/news/25141/opencode-gongji-api-miyao-openai-anthropic-google]，为开发者简化生活的基础设施，把原本分散各处的东西集中到了一个点上。

法律上由谁负责

对中国读者来说，可以先看国内的规则。依据《个人信息保护法》（PIPL）和《数据安全法》，发布应用并收集数据的一方是个人信息处理者，必须采取必要的安全措施；发生泄露时，要立即采取补救措施，并按规定通知履行个人信息保护职责的部门和受影响的个人，这就是法律上的泄露通知义务。一个对路人敞开的数据库，完全落入这一范围，而它是 AI 生成的这一事实，并不会让责任挪动分毫。作为对照，在欧盟，发布应用的人是 GDPR 意义上的数据控制者，须确保适当的安全措施，一旦发生泄露，要在 72 小时内向本国监管机构通报，风险较高时还要通知当事人。英国的 ICO 通过 UK GDPR 适用同一套框架，美国则因各州立法分散而结果各异，其中加利福尼亚州通过 CCPA，在未加密数据外泄时赋予用户诉讼权利。

对填过那张表单的人来说，影响不大，因为损害早已发生。而对搭建应用的人，一个网站敞开一天与敞开一年之间的差别，就是麻烦与罚款的差别。

常见问题（FAQ）

1. 用 Lovable 创建的应用都不安全吗?

不是。Crissy Field 的研究在深入分析的 24,664 个样本中，发现 7,403 个网站的数据可被读取。作者提醒，这个比例不能推广到平台上的所有应用。访问规则配置得当的 Lovable 应用，不会暴露任何东西。问题在于，正确的配置不会自己出现，你得先知道有这回事。

2. 我怎么知道自己的应用有没有泄露数据?

数据库不保存公开的读取记录。你可以按上面的四个步骤，核实数据表现在是否敞开，但要确定过去有没有人下载过数据，就得查 Supabase 项目的日志，而免费套餐的日志只保留很短的时间。如果数据表曾经敞开、网站又被收录过，稳妥的假设是内容已经外流。

3. Supabase 2026 年 10 月 30 日的改动，能让我高枕无忧吗?

只对你今后新建的数据表有效。Supabase 的更新日志说得很明确，现有数据表保留当前权限，依然可以从网页接口访问。一个 2026 年 1 月创建、数据表敞开的项目，今天照样敞开，除非你亲手处理。

4. 用户的应用暴露了数据，Lovable 要负责吗?

按其服务条款，不负责。合同把应用和数据处理的责任划给客户，安全负责人说的是共同责任。不过在欧洲监管机构面前，数据控制者仍是向用户收集数据的人，也就是发布应用的人，而不是卖给他搭建工具的人。

5. 只有 Lovable 如此，还是其他应用生成器也一样?

只要把数据库连到浏览器却没有访问规则，机制就是一样的。Lovable 之所以被拿来审视，是因为它规模最大，而且在页面代码里留有可识别的痕迹，批量扫描很容易。使用其他同类工具的人，比如那篇对比了 Lovable、Bolt、Base44、v0 和 Replit [/en/news/591/ai-app-builders-comparison-2026] 的文章里提到的那些，最好也检查同样的几项。

买单的是填表的人

Lovable 靠着一个承诺，建起了一家 133 亿美元的公司：任何人都能在一个下午发布一个应用。承诺兑现了。如今外面有数以百万计的应用，出自从没听说过访问规则的人之手。平台正从生成应用，转向托管并运行应用。站在这个位置上，把数据库配置推给服务条款，说服力就弱了。写提示词的人不知道该去检查，上传护照的人，甚至不知道背后用的是什么工具。

在工作中使用这个平台的人，眼下也能尽一份力，尽管最有用的那一份并不是某个工具。那是弄清楚自己在要求机器造什么，就像为 Lovable 撰写提示词的五步法 [/zh/news/29304/lovable-ti-shi-ci-zen-me-xie-wu-bu-fa-zhi-nan]那样；再就是看出项目何时已认真到值得用上真正的开发者工具，就像从 Lovable 迁移到 Claude Code 和 Codex CLI 的指南 [/zh/news/2400/lovable-claude-code-codex-qianyi-zh]里讲的。Vibe coding 降低了构建软件的门槛，却没有降低保管他人数据的门槛。两者之间的距离，如今和平台的增长 [/zh/news/4924/lovable-5yi-vibe-coding-dong-zhen-ge]一样宽。如果你有已发布的应用，查看数据表的最佳时机是一年前。第二个好时机，就是现在。
