From the blog post:

 Using datasets from the open web archive Common Crawl,
 we identified and analyzed 159,041 Lovable projects from
 December 2025 to September 2026. Of these, 34,545 used
 Supabase.

 24,664 websites sent database records from Supabase as
 soon as they loaded, without requiring a login or any
 other interaction. That alone is not a security issue:
 the data may be intended for public display. But by
 making additional read-only requests, we were able to
 retrieve more database content. We found records
 containing email addresses in 10,560 tables across 7,403
 of the 24,664 websites (30%).

What isn’t mentioned in the analysis is that we ran a System 1 decision model on each dataset to determine whether it contained privacy-sensitive data. Using a confidence threshold of 85%, we found that nearly 4,000 websites leaked such information.
Edit: That's 15,9% of all Lovable websites that use Supabase.

That's a good question. But it is a very fine line between being a white hat that reports a vulnerability in good faith and someone who actually exploits that vulnerability and turns a vulnerability report into an actual breach. This is - in my opinion, clearly the HN hive mind disagrees - across that line.
For instance, if I run into a server and I see 'passport.jpg' in a directory listing I could download it to see if it really is a passport. But at that point in time I am flirting with becoming a defendant in a data breach rather than that I'm reporting a possible vulnerability. Sure, you could argue that the site owner might close the hole and then they could downplay that it really was a passport photograph. But I care more about the hole being closed than that I care about the contents of the file, which clearly are not meant to be disclosed based on the filename alone.
Independent researchers that are under contract with the companies they review sometimes have more leeway in what they are allowed to do. But downloading enough data to be able to run statistical analysis using LLMs is turning this into a reportable breach and that is a great way to get this whole thing to backfire, possibly to the point where the OP turns defendant.

The idea was that RLS (Row-level security) would be enabled on any tables exposed to the data API, and RLS was “heavily encouraged” to be turned on by default in the dashboard, and RLS was on by default since at least 2025. Tables require explicit RLS policies to be accessible by the data API, so by default it’s not open like that anymore.
In practice it’s an absolutely stupid design. If you create tables without using their dashboard, like with an ORM or with SQL directly, it’s incredibly easy to have them not use RLS and be wide open to the public.
Taking a step back, the whole “query the database straight from the frontend” is a terrible design in general. For example, they still don’t offer rate limiting! Even if the tables data is secured, there’s nothing stopping someone from hammering the database directly with reads/writes until it overloads it, as there’s no application level rate limiting in the middle. Bonkers.

The hint is not a problem if you use the PostgreSQL default of deny for every table, Supabase is migrating to this default https://github.com/orgs/supabase/discussions/45329 [https://github.com/orgs/supabase/discussions/45329]. If the defaults are in place even if you see the table name on the hint it will be inaccessible (fails immediately before RLS checks).
Note that the hint is added by PostgREST and it was introduced at a time where users manually typed table names, causing them to report malfunctions on typos. These hints are not as necessary anymore so they're usually disabled via config[1] and will likely be dropped on a next version.
[1]: https://docs.postgrest.org/en/v16/references/configuration.h... [https://docs.postgrest.org/en/v16/references/configuration.html#client-error-verbosity]

When an app has end users, security is a key part of the product. That’s why we keep investing in making security tools better and easier to use, taking on as much of the security load as we can and fixing more issues automatically.
I personally believe that making security accessible is what leads to making software accessible. We’re committed to both.

As with many gray areas in the law, this all likely comes down to a reasonableness test. New laws may be needed but, to the fullest extent possible, these issues will be framed through the lens of existing law—e.g. product liability. And, once tested in court, these will likely lead to new precedents around existing laws.
For instance, questions will arise as to whether it's reasonable for Lovable to hand this kind of power over to a customer. And, if their software is capable of detecting vulnerabilities, but allows the customer to proceed, is that reasonably responsible behavior on Lovable's part?
Then, there are tests regarding what their customers should reasonably be expected to understand. For instance, it might be tempting to compare this to gun liability laws, wherein manufacturers can disclaim responsibility if their guns are mishandled. But, here, what is the level of knowledge required to fully understand the risks—including the risk/cost of breaking a production build? And, is it reasonable that their customer should be expected to understand?
So, this even comes down to their marketing. If they are actively selling to novice customers, with the pitch that no expertise is required, then customers may argue that they were "set up", and it may prove very difficult to pin the blame on those customers.
Attorneys would likely argue that Lovable can't have it both ways—selling to amateurs, then blaming their customers for being amateurs.
Disclaimer: I once played a lawyer in a 7th grade mock court. Oh, and my company was once sued.

Keeps it private from him and is very careful who she shares it with.
Buys something online from a website she had no idea was built on Lovable (doesn't even know what that is, why would she?).
He finds her address, knock knock.
Unlikely? Yes, at the individual level. But the odds that just one customer out of all the folks using the 4,000 websites estimated by this researcher to leak private information is in a situation where their address becoming public puts them at risk? Probably pretty high...

Keep in mind these no-code sites are proliferating at the very same time that LLMs are becoming incredibly effective at finding vulnerabilities — even Postgres delayed their latest release to focus on a backlog of serious bugs uncovered by an LLM (Opus?). sshhole.com is another example of an egregious bug in ssh being uncovered after years in the wild by LLMs. It's really a perfect storm…

So I'm a member of a couple of communities where people regularly submit their apps "see what i made".
I would say that something like 3/4 supabase projects that are submitted have issues like this. The latest i found was exposing health-related data.
Supabase is positioned similarly to firebase: you don't need a separate backend, and you access your database directly from the frontend. Security is dependent on relatively complicated rules in your database (simpler for firebase, a lot more involved for supabase with RLS)
This means it's a tool that is frequently reached for by newbies - the same sort of people who are the worst equipped to actually implement these complicated security rules themselves. With the advent of vibecoding, many people building are almost entirely dependent on the AI doing the right thing in every case. And this will get progressively more complicated to do correctly the more complicated the schema and usage patterns become.
I think we are in a territory where it is borderline irresponsible for supabase.

That's a good question.
We discussed several aspects, including:
1. The website owners should be informed so they can investigate how many of their customers are affected, notify them of the leak, and report it to the relevant authorities. However, we did not necessarily have their contact details or another way to reach them.
2. Sending thousands of emails to the leaked addresses could further expose that data, as the addresses would then be stored in our email client, on the mail server, and elsewhere. We would have needed to automate this, meaning a service like Mailgun would also receive the data. There was also a significant risk that these emails would end up in spam.
3. The most responsible path forward seemed to be sharing the website URLs and some metadata with Lovable, allowing them to contact the website owners through the appropriate channels.

That's not the problem here. Lovable uses the Supabase Auth layer; they just have their own interface on top of it.
Supabase is kind of similar to Firebase in that you usually communicate directly with the browser through a JavaScript lib. So you need to pay close attention to the security rules (RLS policy in Supabase's case) to restrict data per row based on the user auth.
It's easy to get it wrong; that's why so many Firebase and Supabase databases end up exposed. The platforms have improved the UX so that it's not so common anymore, but it's definitely a gun that's easy to shoot yourself with.
You don't have to expose it like that. You can disable that client and use a server to communicate with the database, which reduces the exposed surface in exchange for complexity (by even having a backend at all).
Mix that design with users with zero tech background who know nothing about systems design and LLMs, and you have a recipe for disaster.
We use Lovable as a prototyping tool and then eject it, review, and deploy on a different platform. It works great for that use case.

In other words, it would be the equivalent of a company like Public Storage leaving all of its storage units with no locks on them at all.
Affected users should be able to sue for a lot in these basic security failures. And obviously for many of these small websites, the potential damages would quickly bankrupt the site owners, but that's the point. People would think a lot more carefully about how they protect sensitive data if there were real negative consequences for their failures.
