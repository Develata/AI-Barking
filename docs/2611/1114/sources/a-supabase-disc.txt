 c-p-b

 [/c-p-b]

 Apr 4, 2022
 [#discussioncomment-2502325]

I'm rather surprised that this is open by default. It seems quite bad from a security perspective. For someone who doesn't really know what they are doing, it seems quite easy under the default settings to let anonymous users probe your API. At the very least, IMO, RLS should be enabled on each table by default. But even this is not enough - RLS enablement doesn't cover functions/RPC's. Also postgrest is configured to automatically show what you have permissions to do on OpenAPI by default - which allows any anonymous user to probe database structure if they have permissions on it simply by going to the root and calling it. So even if you turned on RLS for your tables any anonymous user could see what functions they have privileges to execute if they have your API endpoint.

So initially when I was trying to do this I thought this would be enough (subbing in postgres for your database name, of course):

REVOKE ALL PRIVILEGES ON DATABASE "postgres" FROM "anon";

That will prevent anon from getting in and querying anything. But they can still see the underlying structure of anything they have permissions on via the OpenAPI spec that is made available by default. In other words, they can't connect to the database, but they can see what they have permissions on in the database if they could. Still quite bad, IMO. So now we have to revoke all privileges on everything in the public schema and make sure nothing gets added back in when new objects are created by altering the defaults:

REVOKE ALL PRIVILEGES ON DATABASE "postgres" FROM "anon";
REVOKE ALL PRIVILEGES ON SCHEMA "public" FROM "anon";
REVOKE ALL PRIVILEGES ON SCHEMA "storage" FROM "anon";
REVOKE ALL PRIVILEGES ON ALL SEQUENCES IN SCHEMA "public" FROM "anon";
REVOKE ALL PRIVILEGES ON ALL SEQUENCES IN SCHEMA "storage" FROM "anon";
REVOKE ALL PRIVILEGES ON ALL FUNCTIONS IN SCHEMA "public" FROM "anon";
REVOKE ALL PRIVILEGES ON ALL FUNCTIONS IN SCHEMA "storage" FROM "anon";
REVOKE ALL PRIVILEGES ON ALL TABLES IN SCHEMA "public" FROM "anon";
REVOKE ALL PRIVILEGES ON ALL TABLES IN SCHEMA "storage" FROM "anon";

However, even THAT is not enough. If you do that and go check the OpenAPI specification, anonymous users can still see any functions that you have in the database, even though we revoked all privileges from them. This is because public grants execute on functions by default ( and the code that checks whether to display it in OpenAPI looks at execute:

https://hackage.haskell.org/package/postgrest-8.0.0/docs/src/PostgREST.DbStructure.html#accessibleProcs [https://hackage.haskell.org/package/postgrest-8.0.0/docs/src/PostgREST.DbStructure.html#accessibleProcs]

So finally we want to revoke the ability for the public schema to execute functions. THEN all of that function info disappears from the OpenAPI spec

REVOKE ALL ON ALL ROUTINES IN SCHEMA public FROM PUBLIC;

Sure, I could just do the first thing and turn off database connections and also turn off openAPI for unauthenticated users, but perhaps I want to not have to mess with Postgrest config to do that.

Maybe I'm missing something here or perhaps @steve-chavez [https://github.com/steve-chavez] can weigh in but that seems to me, apart from deleting the role entirely (which may have other ramifications for supabase?) that revoking the privileges permanently is a fix but not really the best or most elegant fix.

I must say this part is not settled yet for Supabase, so any feedback is welcome.

 Maintainer

but granting table access to service_role only has no effect on the visibility, whether I check the OpenAPI response using either the anon or the service_role key.

I don't understand this. Do you mean that revoking privileges on service_role still shows access to tables in the openapi output with follow-privileges?

I am not sure how to interpret these results. Whether this is an issue/limitation in Postgrest, or a miss configuration by Supabase. I am leaning towards an issue with Postgrest because the behavior I observe seems quite inconsistent with I would expect from changing some parameters in the config.

postgREST doesn't do anything on roles permissions, it's stateless. If you suspect a bug in postgREST, I recommend running it on a clean local postgres database (you can follow a tutorial here [https://docs.postgrest.org/en/v12/tutorials/tut0.html]) and report an issue.

Supabase does change the default whitelist pg behavior for tables/views access on the API roles, there's a way to to revert that back with ALTER DEFAULT PRIVILEGES as mentioned on https://github.com/orgs/supabase/discussions/4547#discussioncomment-9064981 [https://github.com/orgs/supabase/discussions/4547#discussioncomment-9064981]

The PostgREST API exposes a schema table/views/functions, this can be configured with db-schemas. On Supabase this happens to be configured to public.

If you put a function in a private schema, will rpc fail to work?

I think it's a valid usecase to use rpc but call functions in other schemas

You can add other schemas to db-schemas.

For anyone in the future, this is what we had to execute to get the following:

Stop exposing the Rest API schema via the /rest/v1/ endpoint to anon and authenticated roles

Deny access to the public and storage schemas from the Supabase client

Keep service-role functional (so far)

Caveats:

Using the supabase client will still return errors exposing some details about the schema...

This is the non-over-doing version which does not cause any warning.

-- Default privileges for future objects
-- Revoke all privileges from the public role to secure the database by default.
REVOKE ALL ON SCHEMA public FROM public;

-- Explicitly revoke all other permissions on all existing objects in the public schema
-- for the anon and authenticated roles. This enforces the "zero client DB access" model.
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon, authenticated;
REVOKE ALL ON ALL FUNCTIONS IN SCHEMA public FROM anon, authenticated;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA public FROM anon, authenticated;

-- Set default privileges for future objects created by the postgres role (or other admin roles).
-- to ensure they are not accessible by anon or authenticated roles by default.
ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
REVOKE ALL ON TABLES FROM anon, authenticated;

ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
REVOKE ALL ON FUNCTIONS FROM anon, authenticated;

ALTER DEFAULT PRIVILEGES FOR ROLE postgres IN SCHEMA public
REVOKE ALL ON SEQUENCES FROM anon, authenticated;

-- Disable PostgREST's OpenAPI endpoint for anon and authenticated roles.
ALTER ROLE anon SET pgrst.openapi_mode TO 'disabled';
ALTER ROLE authenticated SET pgrst.openapi_mode TO 'disabled';

NOTIFY pgrst, 'reload config';
