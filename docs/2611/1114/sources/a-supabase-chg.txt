Backup sign-in options for Supabase accounts
 [/changelog/account-backup-sign-in]

Nov 13, 2026

Improvement
 [/changelog?types=improvement]

Account Security in the dashboard has two backup sign-in options for your Supabase account.

If you only sign in with an OAuth provider, such as GitHub or ChatGPT, you can add a password for your account email. If you lose access to that provider, sign in with your email and password instead.

When you set up MFA, you get 10 single-use recovery codes. If you lose your authenticator app, use a code to complete the MFA step. Account Security shows how many codes are left and lets you regenerate them.

No action required, but we recommend setting up both. See the MFA guide [https://supabase.com/docs/guides/platform/multi-factor-authentication#recovery-codes] for details.

Correlated Logs
 [/changelog/53230-correlated-logs]

Nov 10, 2026

Improvement
 [/changelog?types=improvement]

Correlated Logs is now available in Beta. The Studio Logs tab now lets you connect log events using three meaningful identifiers: requestId, traceId, and userId.

What's new [#whats-new]

Every log item now has four tabs: a structured Overview, Raw JSON, and two contextual tabs that appear when relevant:

Timeline — where a requestId is present, fetches all log items for that request and shows them as a timeline. You can select any item in the chain to see its details and navigate back to the full list.

User — where a log item is associated with an authenticated user, shows their details and links directly to that user in Auth. From the Auth user page, you can view all their logs in the same unified view.

You can also filter the logs list by user attributes to see all log items for a specific user, in the same way you filter by requestId or traceId.

For AI agents using the Supabase MCP server, the query_logs tool supports the same identifiers. See MCP debugging [https://supabase.com/docs/guides/ai-tools/mcp#debugging].

How to use it [#how-to-use-it]

Open the Logs tab [https://supabase.com/dashboard/project/_/logs] in your project dashboard and filter by requestId, traceId, or user attributes. Click into any log item to see the Timeline or User tab where available.

To send a traceId from your application, see client-side tracing [https://supabase.com/docs/guides/observability/client-side-tracing].

Logs in CLI v3 [#logs-in-cli-v3]

Inspect hosted logs in your terminal:

_10
supabase logs --remote --service postgres --level error --since 30m

Filter by service, severity, or time range. Use --from and --to for fixed UTC bounds.

In an interactive terminal, use the up and down arrows to select a row, Enter to inspect it, C to copy the full record as JSON, and L to load newer logs on demand.

For scripts and agents, --output-format json and --output-format stream-json read once and exit. Query hosted logs with --sql or load SQL with --file.

The command defaults to local logs, which require the experimental stack runtime.

Read the CLI logs guide [https://supabase.com/docs/guides/observability/cli-logs] for setup and examples.

Why we built this [#why-we-built-this]

When something goes wrong, the signal is spread across log items from different services, and tracking it back to a specific request or user means cross-referencing timestamps by hand. These connections should be a click away.

This is a Beta release. Try it and share feedback in the GitHub Discussion below.

Breaking Change: supabase-flutter v3 brings type safety to the whole API surface
 [/changelog/supabase-flutter-v3]

Nov 6, 2026

Breaking Change
 [/changelog?types=breaking-change]

supabase-flutter v3 is the next major version of the Supabase client libraries for Flutter and Dart. You can try it today through the 3.0.0-dev prereleases on pub.dev [https://pub.dev/packages/supabase_flutter/versions]. The stable 3.0.0 release is planned for November 11, 2026.

What you get [#what-you-get]

Types across the whole client. supabase gen types --lang dart turns your database schema into a Dart file with a row, insert, and update type for every table. The new supabase.table(Books.table) API uses them end to end: selects return List<BooksRow> instead of List<Map<String, dynamic>>, a filter such as Books.price.lt(20) only accepts a value of the column's type, writes take generated insert and update types, embedded selects follow foreign keys, and stream() emits typed rows. Postgres functions get typed methods on supabase.rpc. Beyond the database, the connection state of the realtime client, channel results, AuthState, and every service exception are typed too. A renamed column breaks your build, not your users' sessions.

An API that reads like Dart. Timestamps are DateTime, URLs are Uri, durations are Duration, realtime listeners are Streams, AuthState is a sealed class you can switch over exhaustively, and every service exception extends one SupabaseException base.

Skills for coding agents. The supabase, supabase_flutter, supabase_typegen, and supabase_test packages ship package skills [https://dart.dev/ai/package-skills] for Claude Code, Cursor, Gemini, and Copilot. They teach your agent the v3 API instead of the v2 code it was trained on, and include a skill that carries a v2 project through the upgrade.

The typed API is additive. from() keeps working on the same client, so you can move one table at a time. It is marked @experimental while its shape settles.

Why v3 breaks v2 code [#why-v3-breaks-v2-code]

Large parts of v2 were ported directly from supabase-js. Timestamps and URLs were strings, realtime used callbacks, and order() sorted descending by default, the opposite of SQL, with nothing in the analyzer or the results to reveal it. A major version is the only moment these shapes and defaults can change, so v3 changes all of them at once. You upgrade once instead of absorbing a series of smaller breaks.

Who is affected [#who-is-affected]

Every Dart and Flutter project on supabase_flutter or supabase v2 that upgrades to v3.

Projects that depend directly on gotrue, realtime_client, storage_client, or functions_client. These are renamed to supabase_auth, supabase_realtime, supabase_storage, and supabase_functions, and the old packages are marked discontinued on pub.dev when v3 ships. If you only depend on supabase_flutter or supabase, your dependencies and imports stay the same.

Projects that use a third-party package built on supabase_flutter v2. You can upgrade once that package releases a v3-compatible version.

Self-hosted projects running a GoTrue older than API version 2024-01-01. v3 only reads the newer error codes.

What happens if you take no action [#what-happens-if-you-take-no-action]

Nothing changes. A ^2.x version constraint never resolves 3.0.0, and pub never picks a prerelease unless you ask for one. v2 keeps receiving security and critical fixes for 6 months after the stable 3.0.0 release. New features only land in v3.

Changes the compiler will not catch [#changes-the-compiler-will-not-catch]

Most of the upgrade shows up as compile errors. Some changes do not, such as the default sort direction of order() and how apps on v2 and v3 exchange realtime broadcasts, so check the full list of changes the compiler will not catch [https://github.com/supabase/supabase-flutter/blob/main/MIGRATION.md#changes-the-compiler-will-not-catch] in the migration guide before you ship.

Migration steps [#migration-steps]

Read the changes the compiler will not catch [https://github.com/supabase/supabase-flutter/blob/main/MIGRATION.md#changes-the-compiler-will-not-catch]. Add ascending: false to every order() call that relies on descending order, while you are still on v2.

Bump supabase_flutter or supabase to ^3.0.0 in pubspec.yaml. Replace direct dependencies on gotrue, realtime_client, storage_client, and functions_client with their renamed packages.

Install the package skills, for example with dart run skills@ get -p supabase_flutter, then ask your coding agent to run the migration skill if you work with one.

Fix the compile errors with the migration guide [https://github.com/supabase/supabase-flutter/blob/main/MIGRATION.md]. For example, anonKey on Supabase.initialize becomes publishableKey. Your existing anon key is still a valid value.

Go through the changes the compiler will not catch one by one, and release every app that shares a realtime broadcast channel at the same time.

Optionally, add supabase_typegen as a dev dependency, generate your types with Supabase CLI 2.122.0 or newer, and move your queries from from() to table().

Rollout timeline [#rollout-timeline]

DateMilestoneUser action
