Postman silently auto-installs AI plugins and attempts to share all API data [https://api.daily.dev/r/9WqVbcbLH]

Postman's desktop app silently installed plugins into Codex and Claude Code without user consent, a GitHub issue reports. Postman's own log shows an 'auto-existing-upgrade' event installing both agent plugins. The Codex plugin also added a startup hook instructing the agent to load a 'postman:api-engineer' skill for any API engineering task, and the installer code calls a function that approves its own hook's trust hash. A remote MCP connection to mcp.postman.com was enabled too, though it failed authentication. Affected versions: Postman desktop 12.33.4, Codex plugin 1.1.0, Claude plugin 2.0.1.

Questions this post answers

Why is Codex automatically loading a Postman skill for API tasks without me asking for it?

Postman desktop (version 12.33.4) can silently install a Codex plugin via an 'auto-existing-upgrade' process, which writes a SessionStart hook into ~/.codex/config.toml. That hook instructs Codex to load the 'postman:api-engineer' skill before handling any non-trivial API engineering task, not just when Postman is explicitly requested, and the plugin's own installer code approves the hook's trust hash itself. Anyone auditing unexpected agent behavior can track incidents like this hook hijack on daily.dev.

How do I remove the Postman plugin and hook trust that got auto-installed into Codex and Claude Code?

A full removal needs to cover agent configs, hook trust records, plugin marketplaces, caches, MCP connections, and a separately installed CLI binary. On macOS this touches ~/.codex/config.toml, ~/.claude/settings.json and ~/.claude/plugins/installed_plugins.json, plus a Postman executable placed in ~/.local/bin, since no single uninstall path was confirmed to clean all of these. Developers cleaning up unwanted agent integrations can follow security write-ups like this one on daily.dev.

Is the Postman remote MCP server actually authenticated when it gets auto-enabled in Codex?

No. The auto-added MCP configuration points Codex at https://mcp.postman.com/mcp, but Codex logs show the server startup failing with 'Auth required, when send initialize request', meaning the connection was enabled without a working authenticated session. Teams vetting MCP integrations before enabling them can follow reports like this on daily.dev.
