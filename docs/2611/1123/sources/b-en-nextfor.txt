NariQ Fits Qwen3.8-27B Into 10 GB Without Losing Its Agent Skills

A 27B model in a single file small enough for one consumer GPU is an old promise that usually breaks on long agent runs. Nari Labs says its 3-bit build doesn't, and published its own numbers to argue the point.

Emily Carter

🔥Heat: 900·Published 2026-11-24

Dek: A 27B model in a single file small enough for one consumer GPU is an old promise that usually breaks on long agent runs. Nari Labs says its 3-bit build doesn't, and published its own numbers to argue the point.

NariQ puts Qwen3.8-27B in a 10 GB gguf file

Nari Labs published NariQ v1 on 20 November, a quantized release of Qwen3.8-27b at three widths: 3, 2.5 and 2 bits per weight. The repository ships Qwen3.8-27B-NariQ-3.0bpw.gguf, a 2.5bpw build, a 2.0bpw build and a BF16 mmproj file for the vision tower.

The 3-bit file lands around 10 GB. For anyone used to a 27B model wanting 50 GB of BF16 weights, that's the whole pitch in one number: a model that fits on a single workstation card, or on a laptop with enough unified memory.

NariQ is a compressed copy of an existing model, not a new one and not a fine-tune. That distinction matters when you read the claims, because the base model's behaviour sets the ceiling.

The claim is narrow and testable. Nari Labs says the 3-bit and 2.5-bit files match BF16 on long-horizon agent tasks, math and image understanding. It says the 2-bit file is weaker on math and agents.

Why 3-bit quantization breaks agent chains first

Chat is forgiving. An agent isn't. A long-horizon run is a chain of tool calls where each step depends on the last, so a small quality loss doesn't stay small. It compounds.

Ask a quantized model one question and a 2 percent error rate looks fine. Let it loop through twenty file edits and shell commands, and that rate decides whether the run finishes or dies in a broken state you have to debug by hand.

That's why aggressive quants pass a demo and fail a job. The interesting part of NariQ isn't the file size. It's the attempt to hold agent behaviour at 3 bits, which is roughly where most compression schemes start falling apart.

The NariQ numbers are self-reported

Everything below comes from Nari Labs, on its own model card, measured with Claude Code CLI 2.1.309 at 262,144 tokens of context. Nobody has reproduced it. Does that make the figures worthless? Not quite, but it does make them an argument rather than a result.

The headline comparisons are close enough to be noise, and worth stating plainly: DeepSWE fully solved tasks came in at 39.8 for BF16 and 41.0 at 3 bits. Terminal-Bench 2.1 was 62.6 against 63.8. AIME 25+26 was 97.7 against 98.3.

The more useful figure is the share of each task's new tests that passed across three rounds: 83.1 percent for BF16, 82.9 at 3 bits, 83.2 at 2.5 bits, and 77.2 at 2 bits. That last number is where the story changes. Two bits isn't a smaller version of the same thing. It's a different, worse model on agent work.

How NariQ was made: trellis codes on agent traces

NariQ is post-training quantization, which means the base model is trained first and compressed afterwards. The calibration data is the interesting part: real coding-agent traces rather than generic text.

Its trellis codes build on QTIP, a quantization method that packs weights into a structured codebook instead of rounding each number independently. Calibrating on agent traces pushes the error toward the kind of inputs an agent actually sees, which is a reasonable way to protect agent scores specifically.

Only the language model is quantized. The multi-token prediction module isn't included yet, and the KV cache and activations stay in BF16. So the memory saving is real, and it isn't the whole model.

The catch: NariQ needs a llama.cpp fork

Here's the part that decides whether you can use it this month. The files need Nari Labs' own llama.cpp fork. Stock llama.cpp, Ollama and LM Studio can't load the new tensor types yet, and the team says it hopes to merge support upstream.

Warning

Without the fork, the GGUFs won't load at all. This isn't a drop-in Ollama pull, and no amount of prompt tuning fixes a tensor type the runtime doesn't know.

Hardware coverage is uneven. The fork is tuned for SM120 cards such as the RTX PRO 6000. Older NVIDIA generations run slower than comparable GGUFs. Apple silicon is slower again. AMD and Intel GPUs aren't supported, and anything older than Ampere falls back to CPU execution, which isn't a practical option for a 27B model.

An M3 Pro with 18 GB decodes at about 3.8 tokens per second with the 3.0bpw file, and 4.9 with the 2.0bpw file. That's readable, not comfortable. If your laptop is the target machine, budget for patience.

Running NariQ as a local llm on your own GPU

The documented path is one command on Linux with an NVIDIA GPU and driver 570 or newer. It downloads binaries and files, checks them, and fits the context to your card. Nari Labs suggests 32 GB or more for the full context window.

Sampling settings are fixed in the card for agent work: temperature 1.0, top-p 0.95, top-k 20, thinking on. Copy them before you judge the model, because the difference between a working 3-bit agent and a broken one is sometimes just the sampler.

For European teams weighing a local llm against an API, the appeal is straightforward. Prompts and code stay on hardware you control, which simplifies a data-protection review. The catch is that the hardware you control is probably one specific card generation right now.

What to watch before you delete your BF16 weights

Three things would change the picture. Upstream llama.cpp support would make the files ordinary GGUFs that Ollama and LM Studio can load. KV-cache quantization would cut memory further. And other 27B-class models getting the same treatment would turn a single release into a method.

Until then, NariQ is a serious piece of work with a narrow deployment window. Test it on your own agent traces, on the fork, before you plan around it. The Hacker News thread passed 100 points, which tells you developers are interested, not that the numbers hold on your workload.
