Qwen3.8 - How to Run Locally

Guide to running Qwen3.8 quants including Qwen3.8-27B on your local setup.

Qwen3.8-27B is a 27B parameter dense model Qwen, featuring vision and reasoning capabilities, a 256K context window, and runs locally on 17GB RAM/VRAM setups. Qwen3.8 excels at agentic coding, vision and chat tasks, and can now run via Unsloth GGUFs, NVFP4 and Unsloth Desktop [/docs/models/qwen3.8#run-qwen3.8-in-unsloth-desktop].

Nov 11 Update: Qwen3.8-27B GGUFs now use Unsloth Dynamic V3.1 [/docs/basics/dynamic-3.0-ggufs] which improves average accuracy by 5-10% accuracy at comparable sizes including Terminal Bench, DeepSWE and more benchmarks. We're working on an even better version of Dynamic quants which will be applied to Qwen4 and future models.

Dynamic 4-bit Qwen3.8-27B in Unsloth Desktop

Dynamic V3.1 Update (November 11th 2026) [#dynamic-v3.1-update-november-11th-2026]

We're excited to release new Qwen3.8-27B GGUFs using our updated Unsloth Dynamic [https://unsloth.ai/docs/basics/dynamic-3.0-ggufs] V3.1 (preview) algorithm which improves Unsloth quants by 5-10% accuracy at the same size on most benchmarks and is the best in class for most tasks including coding, agentic workloads and general chat.

Most quants from 2bit until 6bit are updated. We found 3bit UD3 quants to do on par with UD3.1, so we do not update them. We are actively working on making all quants better!

We ran agentic benchmarks including Terminal Bench 2.1, DeepSWE v1.1, and general benchmarks like LiveCodeBench v6, GPQA Diamond, MMLU-Pro, AIME25 and many others. We used 256K context lengths for all agentic benchmarks, and 128K for the rest. We followed the same methodology for Qwen3.8-27B as DeepSeek-V4.1-Flash [/docs/models/deepseek-v4.1-flash] and Qwen3.8-Flash-Next [/docs/models/qwen3.8-next] which also utilized our V3.1 preview algorithm.

Exllama-v3 considerations [#exllama-v3-considerations]

To compare GSQ-RCO and Exllama-v3, we had to exclude the token embedding layer from the x axis, as Exllama-v3 uses BF16 for it.

If you consider the full download size and total RAM usage for Exllama-v3, then adding the BF16 embedding table and including all embedding sizes changes the plots. Our main plots's x axis removes the embedding layer sizes from all quant providers. However on pure RAM usage and disk space usage vs accuracy, the below plot is the true reflection of actual usage.

We have not investigated why Exllama-v3 keeps token embeddings in BF16, but as the lm_head is still quantized heavily, the embedding layer might have "absorbed" most of the quantization damage from it. We would be glad to benchmark new Exllama-v3 non BF16 token embedding quants like using 8-bit for example, and see if benchmarks change.

GSQ-RCO results are misleading [#gsq-rco-results-are-misleading]

For LiveCodeBench, GSQ-RCO showed Unsloth UD3 quants doing consistently worse than ISTA's. However we found the opposite - UD3 quants (our OLD quants) do better than ISTA on LCB on all sizes except the smallest. UD3.1 further improves on LCB as well.

We approximate that GSQ-RCO used a context budget of 96K, as that best fits the data for the runs we have. At 96K, GSQ-RCO does somewhat do better than UD3, but at 128K, UD3 does much better.

On another benchmark, for ISTA GSQ-RCO's AIME25 benchmarks, their quants reach 100%, 100%, 100% and 96.7% accuracy recovery. And they said our quants do worse.

Through out investigations, we estimate ISTA only did 1 trial - we did 14 trials, and we show on average the recovery rate is 93% to 96% - not 100% accuracy recovery. And in fact our UD3 old quants do BETTER on average than their quants on 14 runs vs 1 run of theirs, so we draw the opposite conclusion if you run the trials more.

We also checked and graded our answers using Math Verify Dynamic 3.1 GGUFs [/docs/basics/dynamic-3.0-ggufs/dynamic-3.1-ggufs] and also LightEval and we find exactly the same conclusions. We also tried greedy decoding (temperature of 0), and this could not get the 100% accuracy recovery ISTA found across multiple greedy runs, as GPUs themselves are non deterministic. That is why you benchmarks should be run multiple times. Greedy decoding is also not representative of real world use cases.

We also checked 96K (which is most likely ISTA's budget) and 128K, and our quants still do on average better.

KLD of Unsloth v3.1 vs v3 [#kld-of-unsloth-v3.1-vs-v3]

We did KLD for multiple domains for Unsloth UD3.1 quants and UD3 quants - we reduce KLD throughout most quants and most domains - we did not replace the 3-bit ones, as we found UD3 to do mostly great, and the accuracy recovery on benchmarks was not significant enough with UD3.1 to warrant an update, so we did not update them.

Benchmark details and setups [#benchmark-details-and-setups]

We follow the same procedure for all benchmarks as for Qwen3.8-Flash-Next, DeepSeek-V4.1-Flash as well as discussed in Dynamic 3.1 GGUFs [/docs/basics/dynamic-3.0-ggufs/dynamic-3.1-ggufs]. We used temperature 1.0, top_p 0.95, top_k 20, min_p 0, no presence or repetition penalty, preserve_thinking and xhigh reasoning for Qwen3.8-27B.

💡 Thinking + Preserve Thinking [#thinking--preserve-thinking]

Qwen3.8 has Preserve Thinking which leaves the thinking trace from the previous conversation. This increases the number of tokens you use, but could increase accuracy in continued conversations. Unsloth [/docs/models/qwen3.8#run-qwen3.8-in-unsloth-desktop] has 'Think' and Preserved Thinking toggles for Qwen3.8 (see right):

Qwen3.8-27B comes with support for reasoning_effort, which can be used to adjust reasoning depth and control cost. These toggles are automatically enabled in Unsloth:

xhigh (default): for complex tasks demanding thorough analysis

medium: balancing accuracy and speed

low: efficient reasoning optimizing for speed and cost

none

To change thinking / reasoning [/docs/models/qwen3.8#how-to-enable-or-disable-reasoning-and-thinking] effort in unsloth run or llama-server, use --chat-template-kwargs '{"reasoning_effort":"medium"}'

If you're on Windows Powershell, use: --chat-template-kwargs "{\"reasoning_effort\":\"medium\"}"

Change medium to your desired reasoning level.

🦥 Run Qwen3.8 in Unsloth Desktop [#run-qwen3.8-in-unsloth-desktop]

Qwen3.8 can run in Unsloth Desktop [/docs/models/qwen3.8#run-qwen3.8-in-unsloth-desktop], an open-source UI app for local AI. Unsloth automatically offloads to RAM and detects multiGPU setups. With Unsloth Desktop, you can run models locally on MacOS, Windows, Linux and:

Search, download, run GGUFs [/docs/new/studio#run-models-locally], MLX and safetensor models

Self-healing tool calling [/docs/new/studio/chat#auto-healing-tool-calling] + web search

Code execution [/docs/desktop#code-execution] (Python, Bash)

Automatic inference [https://unsloth.ai/docs/desktop#feature-deep-dive] parameter tuning (temp, top-p, etc.)

Fast CPU + GPU inference via MLX and llama.cpp

Train LLMs [/docs/new/studio#no-code-training] 2x faster with 70% less VRAM

Qwen3.8-2.4T-A95B [#qwen3.8-2.4t-a95b]

Qwen3.8-2.4T-A95B is a 2.4T parameter (95B active) model with rivaling GPT-5.6 Sol. Full-precision Qwen3.8-2.4T-A95B requires 4.9TB of storage and 1-bit Unsloth [https://github.com/unslothai/unsloth] Dynamic GGUFs takes 397GB (91% smaller), and larger IQ1_S takes 508GB.

Qwen3.8-2.4T-A95B New 1-bit data-types [#qwen3.8-2.4t-a95b-new-1-bit-data-types]

We extended IQ1_S in llama.cpp which is 1.5625 bits per weight to 1.1875 bpw by reducing the number of entries in the codebook - we found this works well for large models, and can still retain a lot of accuracy - we also found these new data-types to be fine for post training quantization (PTQ) without the need for QAT or QAD (quantization aware training / distillation).
