Cisco and OpenAI introduce Shirudo

Thomas Graf, Liz Rice

| Published: November 23, 2026

What: Cisco and OpenAI are introducing Shirudo, an open source security platform that helps teams protect operating systems and workloads while they roll out patches.

Tetragon: Shirudo has its roots in Tetragon, rewritten for the agentic era. Instead of exposing and limiting an agent to the scope of a policy language designed for humans, Shirudo allows an agent to interact in its natural language: code.

Mitigation Example: To test Shirudo’s mitigation capability, we look specifically at the Java4Shell vulnerability and walk through an example of how an agentic control plane utilizing Shirudo was able to develop a mitigating shield for the Java4Shell vulnerability and protect a running Elasticsearch instance.

Introducing Shirudo

Today, Cisco and OpenAI are launching [https://openai.com/index/introducing-shirudo/] Shirudo [https://github.com/shirudo-dev/shirudo], an open source security platform that helps teams protect operating systems and workloads while they roll out patches. Instead of relying on a full software patch followed by a restart of the workload or OS, Shirudo delivers small, targeted mitigations to the running kernel or workload. A mitigation can block the path a vulnerability needs, replace the vulnerable code with fixed code, or add the visibility needed to detect an attack.

Shirudo, Japanese for shield, has its roots in Tetragon, the eBPF-based security platform that Isovalent developed and open sourced back in 2022. Tetragon’s use of eBPF to provide runtime security and vulnerability defense has been ground-breaking in the pre-agentic era, and it has been the foundation for Cisco’s Live Protect capability that provides vulnerability mitigation in Cisco products today.

Shirudo is a rewrite of Tetragon designed for agents and it incorporates a crucial learning: in order to unlock defense at machine speed with agents, we need to let agents speak their natural language: code.

Initial approaches pointed agentic workflows at existing interfaces and abstractions that were designed for humans: consoles, configuration files and policy languages. That is a natural first step but it fundamentally constrains the effectiveness of agents. Humans benefit from abstractions that hide machine-level details and translate them into concepts we can reason about. Agents are different. They are very good at generating code and can absorb huge amounts of context quickly. An agent doesn’t mind reverse engineering several million lines of assembly code. Instead of limiting agents to what a human-oriented policy language defines, agents must be able to develop mitigations at machine speed with code.

A graph showing that human abstraction takes the AI longer to process and work, compared to direct machine interface

eBPF was created more than a decade ago to solve a problem very similar to the one we face today of needing to deploy exploit protections quickly without interrupting application workloads. Back then, the popularity of Linux made it harder to change the kernel every time a new requirement came up. Every change had to be coded up, released, and packaged up as part of a distribution before it could be rolled out. Every code change was also a stability and security concern. Users wanted a stable operating system, but also an operating system that continues to evolve. eBPF solved this by adding a safe runtime sandbox inside the kernel. It can load small programs, written as eBPF bytecode, at many points in the operating system to extend, augment, or replace its behavior while it keeps running – and without interrupting running applications. Think of eBPF as making the operating system programmable in the same way JavaScript made the web browser programmable without needing to update or restart the browser. The kernel checks (or “verifies”) every eBPF program before it runs, so that this flexibility never comes at the cost of safety or security.

So eBPF gives us a perfect platform for using the operating system to mitigate vulnerabilities and harden the system. Agents can write eBPF programs that collect exactly the signals they need to observe how the system is behaving. They can load new programs that block a vulnerable code path or shield a workload, while the system keeps running. The sandbox and security layer of eBPF add a crucial safety and trust aspect required to put agents at work.

A model for injecting code mitigations

eBPF is a well-established platform for modifying the behavior of the operating system kernel, and in many cases this proves to be the perfect tool for building mitigations that protect against exploiting vulnerabilities in the kernel and even in application code. It also serves as the inspiration for another form of code mitigation that is realistically possible with the use of AI agents: modifying the byte code of applications themselves, or of the user-space run-time that they execute in. As you’ll see in the Java4Shell example, later in this post, agents are capable of creating Java byte-code modifications to protect against other classes of vulnerabilities that aren’t suited to eBPF protections.

Shirudo Architecture

Shirudo consists of a one-shot CLI so that it doesn’t require a permanently running daemon, either on the target machines to be protected, or on the operator machine that builds and delivers signed packages. The control plane on the target is an eBPF program loaded into the operating system during boot.

Shirudo on the operator machine builds security shields consisting of eBPF or application bytecode, and delivers them as signed .bee packages via an OCI registry. The Shirudo layer on each target pulls these .bee packages, validating each signature using TPMs to establish trust and safety.

A flow diagram showing how the operator and the target machine work with each other, will all components of Shirudo in there

Shirudo In Action

Let’s take a look at how Shirudo works in action. Shirudo is built for an agentic control plane, and in this example we are using Codex as the control plane.

The screenshots above illustrate a fully automated process of vulnerability mitigation driven out of Codex:

The discovery of vulnerabilities and gathering of vulnerability information: The agent loop can either be tasked to actively search for new vulnerabilities itself, or to work off external sources of new vulnerability disclosures.

The generation of mitigation code: This includes the generation of a reproducer of the exploit, the validation of the exploit, the evaluation of the most effective mitigation point (eBPF, Java runtime, ...), and the validation of the mitigation code. This step is repeated until a successful mitigation is found

Rolling out the mitigation to affected target nodes: The mitigating shield is signed and securely rolled out to all affected nodes. This step is continuously monitored and repeated to achieve the highest possible security score while closely monitoring the health of applications. This particular step can be designed to be more or less autonomous, just like with any agentic workflow.

Monitoring of infrastructure for exploitation attempts: Once mitigation shields are deployed, the “hit” count represents active exploitation attempts of shielded vulnerabilities. Exploitations can be investigated on demand.

Example: Mitigating Java4Shell

Java4shell [https://calif.io/java4shell] is a recent vulnerability discovered in OpenJDK. We fed the Java4Shell vulnerability information into the agentic Shirudo control plane to automatically create a shield against an exploitation of this vulnerability. This resulted in a mitigation written as Java bytecode. The bytecode injects into any Java application and adds validation on the base64 input to guard against the overwrite that is used to exploit the vulnerability.

To test it, we ran Elasticsearch 9.5.5, observed how the mitigating shield got attached to the running Elasticsearch process, and then attempted to exploit the vulnerability. The exploitation was not successful, and the following trace can be found in the Elasticsearch logs that documents the successful mitigation of the exploit:

Rethinking Infrastructure for the AI Era

We need this kind of machine-speed defense because AI models have become incredibly good at finding and exploiting software vulnerabilities, and they get better with every generation. They can also chain flaws together and discover creative new attack vectors that no one has thought about before. Yet a critical fix in widely-used software, from the Linux kernel to the libraries every application depends on, still takes days, weeks, or even months to reach the majority of systems. That timeframe is no longer acceptable given that the mean time to exploitation has become negative – in other words, a growing number of vulnerabilities are now being exploited by malicious actors before they are publicly disclosed. This will only accelerate with the further evolution of AI models and with cybersecurity capabilities becoming the norm in open-weight models.

Two graphs, one falling, showing mean time to explot has gone negative, one rising aggressively to the end, CVE fixed per release

Software vulnerability patching is only the tip of the iceberg and represents a more fundamental flaw in today’s infrastructure design: much of the world’s infrastructure was fundamentally designed to be secured with policy, patching, and threat detection all operating at human pace.

It’s clear that we have to rethink how we secure and defend infrastructure. Infrastructure must become secure by default, hardened continuously, self-defending, and able to detect and counter new attacks at machine speed.

Shirudo operating principles [https://www.youtube.com/watch?v=VesOL1cZk04]

Defense at Machine Speed: Attacks driven by AI unfold in seconds, so defenses have to respond just as fast, without waiting for a person to notice and react. That is why the system is designed to defend at machine speed. Its software exposes interfaces that AI agents can operate directly, such as programmable controls in the operating system, rather than abstractions designed for humans.

Self-Augmenting: Software should keep getting harder to attack on its own, instead of waiting for the next release to be hardened. In practice, it adjusts itself at runtime as the security landscape changes. Code that a workload doesn't need is removed to shrink the attack surface, vulnerable code is cut out or replaced, and patches are applied live, without restarting applications or machines.

Hardened by Default: Systems should be secure from the moment they are built, not secured afterwards. That means defense in layers, built from first principles and from the bottom up. Every layer trusts the one beneath it, so hardening starts in the kernel: reduce the attack surface to what the workloads need. Live mitigations help shrink the attack surface, but they complement the protections built into the kernel rather than replace them.

Rebuildable and Immutable: If a system is compromised, it should be possible to simply recreate it from a known good state. Immutability, meaning that the operating system foundation is immutable on disk, means that any system can reboot into a good known state.

Driven by Reinforced Learning: The system learns from experience and gets better at defending itself each time it receives feedback. As new models open new attack paths, it uses reinforcement learning to keep improving its security posture: it tries defensive measures safely, measures their effect on both security and application health, and keeps what works.

Anchored in Hardware: Trust rooted only in software will become even harder to maintain than it already is. TPMs - Trusted Platform Modules that use hardware to verify integrity - will become a vital part of the platform. TPMs will be used to measure every state change and ensure that all changes to the system have valid signatures and are intended by the control plane. This starts with the TPM ensuring that the system can only boot into a known good configuration.

Shirudo is a step towards this vision of self-defending infrastructure.

The Future is Open & Collaborative

The Shirudo project is only the beginning, but it already shows the true potential of combining agents as a workforce with machine interfaces to let agents output what they are best at: code. We put a lot the initial focus on the mitigation of vulnerabilities but we expect Shirudo itself will evolve, and additional projects around it will emerge that we hope can serve as the open foundation to build self defending infrastructure to safely run applications and agents side by side.

We believe that building secure infrastructure for the AI era is an industry-scale problem. That is why we invite everyone to collaborate alongside Cisco and OpenAI and join the community around Shirudo. Collaboration is open to everyone on GitHub [https://github.com/shirudo-dev/shirudo], whether you work on the Linux kernel and eBPF, build infrastructure and platforms, research AI security, or red team systems.
