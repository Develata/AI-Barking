广告

Claude Code 会把每条用 "Yes, and don't ask again"(是,并且不再询问)批准过的命令,原样明文写进项目的 .claude/settings.local.json 文件,密码和 API 密钥也不例外. 据 Apiiro 的研究 [https://apiiro.com/blog/coding-agents-leaking-secrets-github-dont-ask-again],GitHub 上 104,185 份公开的本地设置文件中,有 1,122 份至少含有一个真实密钥.

Apiiro 是一家安全公司,销售保护应用和编程代理的产品,这项研究由 Shmulik Cohen 和 Matan Giladi 署名,2026 年 11 月 5 日发布. Claude Code 是 Anthropic 推出的、在终端中运行的代理: 它读取项目代码,提出要在开发者电脑上执行的命令,并在每条命令之前征求许可(只批准一次,或永久批准).

最近芝加哥一位教授的遭遇, 即Claude 删除了他一整年的讲义 [https://pasqualepillitteri.it/zh/news/31155/zhijiage-jiaoshou-claude-shanchu-jiangyi], 说明了一份代理无法触及的副本有多重要.

Claude Code 的本地设置文件与 Apiiro 研究的数据

密码如何进入设置文件

场景再日常不过. 开发者让 Claude Code 查明登录为什么在预发布环境失败,或者跑一次数据迁移. 代理提出的命令自带密钥(数据库连接字符串,API 令牌),否则命令根本跑不起来. 代理在执行前请求确认,一次会话里要问好几次. 选择 "Yes, and don't ask again" 的人,既让命令开始执行,也在项目文件夹内的 .claude/settings.local.json 里添加了一条权限规则. 这条规则就是命令本身,一字不差,连密钥一起.

Apiiro 特别指出,这是 Claude Code 的行为,与底层模型无关: 研究人员用 Opus 5.5 和 Fable 5.1 都复现了问题,也就是 Anthropic 最新的模型.

这个文件本该留在开发者的机器上. 官方文档 [https://code.claude.com/docs/en/settings]写明了预设的保护措施: Claude Code 第一次在尚未忽略该文件的 git 仓库里写入它时,会把 **/.claude/settings.local.json 加进 git 的全局排除列表. 然而这一补救只在该开发者自己的电脑上有效. 规则不会进入仓库的 .gitignore,因此不会随项目流转,以下几种情况就此暴露: 之后才变成仓库的文件夹,在另一台机器上的克隆,以及已经提交过的文件.

提交往往是 Claude 自己完成的. 在 Apiiro 能够还原的 1,105 个含真实密钥的仓库里,有 539 个出现过以 Claude 为共同作者的提交修改了该文件. 这些提交涉及所有近期模型,从 Sonnet 4.5 到 Opus 5.5.

来源: Apiiro 研究,2026 年 11 月 5 日

Apiiro 研究的数据

数据采集在 11 月 1 日至 3 日通过 GitHub 的代码搜索完成,共列出分布在 103,617 个仓库中的 104,185 份文件副本. 其中 1,122 份(1.1%)含有真实密钥,即已知提供商格式的密钥,或者紧挨着公网主机的密码或令牌. 合计 1,379 个不重复的密钥,其中 636 个是提供商密钥,743 个是可从互联网访问的主机所用的密码或令牌.

超过三分之一的密钥直接通向数据库. 统计到 379 个数据库密码和 122 个 Supabase 的 "service-role" 密钥(Supabase 是托管数据库服务,这种密钥可直接访问数据,此前的Lovable 应用暴露护照和聊天记录一案 [/zh/news/29842/lovable-shuju-xielou-huzhao]就与它有关),另有 103 个 Supabase 账户令牌,可掌控所有者名下的全部项目. 其余包括 43 个 SSH 登录凭据,42 个 GitHub,GitLab 和 npm 令牌,23 个 AWS 密钥和 6 个私钥.

文件越长,出现频率越高. 8 KB 以上的文件中,每十份就有一份含真实密钥,而 500 字节以下的文件,不到五百份才有一份: 开发者点 "don't ask again" 的次数越多,列表就越长.

而且这些文件仍然在线. 11 月 2 日,每一份都还躺在各自仓库的主分支上,中位数情况下首次提交已是 217 天前(118 个仓库超过一年). 74 个仓库的 211 个分支(fork)带着完全相同的副本. 事后删除文件解决不了问题,因为历史版本在 509 个仓库中保留了 734 个密钥,它们没有出现在任何现行副本里.

把 git 历史,团队共享的 settings.json 文件和保存在仓库里的会话记录加在一起,Apiiro 得出 1,994 个仓库中共有 2,539 个不重复的密钥. 涉及 63 个组织,大多是各种规模的软件公司. 最严重的几起包括: 一家数据库供应商具有管理权限的云密钥,一个生产环境 Azure Postgres 的密码,一个 Square 生产令牌,以及一个病历数据库所有者的密码. Apiiro 已在 11 月 2 日和 3 日把每起案例通知了所有者. 一家公司确认其密钥确实仍然有效.

需要注意的局限

所有统计均出自 Apiiro 之手,这家公司销售面向编程代理的安全产品,在这一议题上有利益关系: 目前没有第三方重复过这些统计; 2,539 个密钥的总数还参考了一位 LLM 审核者的判断,而非人工核查.

"真实密钥" 指已知提供商格式的凭据,或指向公网主机的凭据. Apiiro 没有试用任何密钥,也没有联系任何主机,因此仍然有效的凭据数量不明: 唯一的确认来自一家公司.

这份快照只涵盖 GitHub 上的公开仓库,时间为 11 月 1 日至 3 日. 研究本身承认,历史记录的统计只是下限,私有仓库和开发者的机器都不在其中.

对 16 种代理的比较依据的是它们的文档,而不是实际使用测试. 因此,说 Claude Code 是唯一默认把完整命令写进项目文件的代理,只是对手册的解读.

扫描器为什么看不到

两款广泛使用的开源扫描器,gitleaks [https://github.com/gitleaks/gitleaks] 和 TruffleHog [https://github.com/trufflesecurity/trufflehog],会在仓库里查找格式可识别的密钥,比如提供商的前缀. Apiiro 让它们跑遍了全部 104,185 份文件. 在含真实密钥的 1,122 份中,gitleaks 标出 564 份,TruffleHog 标出 643 份,有 215 份两者都漏掉了(五分之一).

漏洞出在写进命令的密码上,比如 PGPASSWORD=,sshpass -p 或 mysql -p 之后的内容,又比如 curl 调用里的 bearer 头. 对一款按格式调校的扫描器来说,它们不过是某一行里的一个普通单词. 同样的模式会在代理记录自己所执行内容的所有文件里重现. Truffle Security 对 GitHub 上仍然有效的凭据所做的统计 [/zh/news/21393/github-youxiao-pingzheng-truffle-security-543699]显示,一个被误发布的密钥会继续有效多久.

不只是 GitHub,也不只是一个文件

权限规则列表(allowlist)是最清楚的例子,但代理在别处也会写入密钥. Apiiro 检查了 76,011 份共享的 settings.json 文件(298 份含真实密钥),2,523 份由 SpecStory,aider 和 Cursor 导出等工具保存的会话记录(87 个仓库中的 120 份文件),1,200 份代理记忆文件(9 个仓库),2,095 份交接和部署说明(33 份文件,其中含密钥的有三分之一是代理写的),以及 173 份 Copilot 在 VS Code 中的自动批准设置(9 个仓库).

问题也不止于 GitHub. 在 Hugging Face 的 31,053 个 Spaces 中,有 126 个含有该文件,其中一个的权限规则里带着数据库服务密钥和一个用户密码. 在 GitLab.com 上,69 份公开副本中有 2 份带有真实密钥,包括一个 GitLab 访问令牌.

再者,在开发者的笔记本上,这个文件就是一份普通的明文 JSON. Apiiro 提到 2025 年 9 月的 npm 蠕虫 Shai-Hulud,它会下载 TruffleHog 并在受害者的文件上运行(该扫描器标出了 1,122 份含真实密钥文件中的 643 份),还提到三周前的恶意 Nx 软件包,它们指挥用户的 Claude Code 和 Gemini CLI 在磁盘上搜寻密钥. 这与编程代理中的零点击漏洞 Plugin4Shell [/en/news/17177/plugin4shell-zero-click-flaw-ai-coding-agents]以及让凭据暴露五个月的 Claude Code 沙箱绕过 [/zh/news/3041/claude-code-shaxiang-raoguo-socks5-pingzheng]属于同一片地带,区别只有一点. 这里不需要任何漏洞利用: 善意给出的一次点击就够了.

Apiiro 还通过阅读文档,比较了 16 种编程代理的行为. 结果显示,只有 Claude Code 被确认默认把批准的完整命令写进项目文件. 九月底AI 代理在 GitHub 上留下的 343 家公司的 13,000 张截图 [/zh/news/19566/pixelleak-ai-zhinengti-jietu-github]是最接近的先例,但这次的机制更平常.

报告与文档显示了什么

这种行为并不新. Claude Code 公共问题跟踪器 [https://github.com/anthropics/claude-code/issues/5544]上 2025 年 8 月 11 日的一份缺陷报告,描述了已批准的 bash 命令把凭据明文存入 settings.local.json 的情况,该报告现已关闭. 随后是 2025 年 11 月 19 日关于 Claude Code 不再把该文件加入 .gitignore 的报告,以及 12 月 4 日关于敏感令牌未被 git 忽略 [https://github.com/anthropics/claude-code/issues/13106]的报告,二者同样已关闭. Apiiro 写道,这些报告没有一份得到 Anthropic 的回复,其中三份被当作长期无活动或重复而自动关闭. 4 月,Lakera [https://www.lakera.ai/blog/your-ai-coding-assistant-just-shipped-your-api-keys] 曾在 30 个 npm 软件包内的 33 个此类文件里发现凭据.

截至 11 月 8 日,也就是研究发布三天后,Anthropic 没有公开回应,文档在这一点上也没有变化. The Hacker News [https://thehackernews.com/2026/11/claude-codes-dont-ask-again-file.html] 补充说,Apiiro 没有核实这些密钥中还有多少能用.

现在该做什么

对已经用了几个月 Claude Code 的人,清单很短; 顺序很重要,因为只清理不轮换,谁也保护不了.

先轮换每一个可能出现在已批准命令里的密码,密钥和令牌,然后再碰任何文件. 删掉文件并不会抹去历史,分支和克隆.

在组织的 GitHub 里搜索 .claude/settings.local.json 和 .claude/settings.json 文件(此刻每条结果都能被任何人读到),并检查每个仓库的 git 历史,包括如今已消失的文件.

如果文件已被跟踪,执行 git rm --cached .claude/settings.local.json,并把该路径或整个 .claude/ 文件夹加入仓库的 .gitignore 以及组织的模板.

在自己的机器上打开该文件,删除每条含密钥的规则,即使它从未被提交过.

不要再把密钥写进命令,改为引用来自密钥管理器的变量,例如 $DB_URL(这正是 Infisical 为无密码 AI 代理募得 40 million 的主题 [/zh/news/28458/infisical-b-lun-rongzi-4000-wan-meiyuan-ai-zhinengti-mima]),并批准 Bash(npm run:*) 这样的模式,而不是字面命令.

安全团队应当像对待 .env 一样对待 .claude/,.cursor/,.gemini/,.specstory/ 和代理的记忆文件,不仅在仓库里,也在笔记本上. 要把它们纳入提交前检查和 CI(包括历史记录),并确认扫描器能识别命令中的密码,而不只是密钥格式.

常见问题

1. 如果我从没提交过这个文件,是不是就安全了?

从 GitHub 的角度看是,从机器的角度看不是. 规则会一直留在文件里,直到有人把它删掉,命令执行过去很久之后仍然如此. 文件可以不经过 git 就流出去,比如混进已发布的 npm 软件包,用复制命令构建的 Docker 镜像,zip 压缩包,或同步文件夹.

2. 怎么在我的电脑上找到这些文件?

在项目文件夹里按文件名搜索. 命令 find ~ -name settings.local.json -path "*/.claude/*" 会列出每一份副本; 对每一份,只需查看 allow 列表,找出密码,令牌,密钥和连接字符串.

3. 批准一个模式比批准完整命令更好吗?

是的,因为保存下来的规则里是模式,而不是密钥. 用 Bash(npm run:*) 时,文件只记录命令的名字,而键入了密码的那一行仍然只留在会话里.

4. Cursor,Copilot 或 Gemini CLI 也会这样吗?

就 Claude Code 的默认行为而言,目前被确认的只有它. 其他工具同样会在仓库里留下痕迹. Apiiro 在 Cursor 的导出文件,aider 保存的会话,以及 Copilot 在 VS Code 中的自动批准设置里都发现了密钥.

软肋在那一次点击

"Don't ask again" 原本是个捷径,方便又无辜,省得每次都确认同一条命令. 麻烦出在这个捷径被记住的方式上,因为规则复制了整行命令,而那一行里有开发者粘贴进去的一切. 把模式而不是密钥存下来,这是 Anthropic 的事. 对今天使用 Claude Code 的人来说,稳妥的做法只剩一个,别等了,立刻轮换密钥.
