Imports between files

Each picture has the project's files along both sides, sorted by path, so that the files of a folder are next to each other; dotted lines separate the top-level folders. A pixel stands for 1/160 of the files each way and is coloured when files of its row import files of its column; the darker, the more imports per pair of files in the pixel:

A well-structured project probably shows dark squares along the diagonal (folders importing mostly from themselves), some vertical stripes (files that much builds on) and little else; dots spread over the whole picture are imports between unrelated parts. The projects differ in size, so a pixel holds a different number of pairs of files in each picture: compare the patterns rather than the darkness.

 How it's measured

Text search, not Lean. All numbers come from plain text search, with Python
 regular expressions, over the .lean files as stored in git
 (collect.py [https://github.com/rh-shrink/rh-shrink.github.io/blob/main/collect.py]).
 Lean is never run and nothing is elaborated.

There is one data point per commit on main; a merged pull request counts as one
 commit, not as the commits it contains. A GitHub Action checks for new commits every 15 minutes.
 On Nov 25, 2026, main was replaced by the readable edition of the proof
 (grh-lean [https://github.com/lsernau/grh-lean]); the arrow in the charts marks
 this. Before it come the commits of main up to then, which go on in the branch
 alpoge [https://github.com/leanprover-community/riemann-hypothesis/tree/alpoge].
 The original is the first of them, the proof as published; the charts over time have log
 scales, so that both fit.

Source folder

the folder the lakefile names as srcDir, now src/; if it moves, the counts follow it

Total lines

lines of the .lean files in the source folder, including blank lines and comments

Code lines*

total lines, without blank lines, lines that are only comments (--, nested /- -/) and the imports at the top of each file (with its module line)

Theorems

code lines* starting with theorem or lemma, also after attributes and modifiers such as @[simp] private

Other declarations

code lines* starting with def, abbrev, instance, structure, inductive, class, opaque or axiom, likewise

Declarations

theorems and other declarations

Files

.lean files in the source folder

Folders

the folders directly in the source folder, each with everything below it; the files directly in it are one more group

Import statements**

import statements (also public import, meta import) of the project's own files, counted as lines starting with one, assuming the usual one import per line; imports of Mathlib, Lean and other dependencies are left out

Repeated theorem statements

theorems and lemmas whose statement (from after the name up to :=, white space aside, at least 30 characters) is word for word that of another theorem, counting the copies beyond the first. The same text can mean different things in different namespaces, which is why Mathlib has some too

maxHeartbeats overrides

set_option maxHeartbeats, which gives a proof more time than Lean's default

Declaration lengths

code lines* from a declaration to the next one in its file, or to the end of the file

Imports between files

in the pictures of the imports and the ideal build: which files of the project the import statements of each file name (imports of Mathlib and other dependencies are left out)

Ideal build

a simulated build on as many cores as needed: every file starts as soon as all files it imports are built, and takes time in proportion to its code lines*. That is an assumption: how long Lean takes depends mostly on the proofs, which text search cannot tell. The fastest such build takes as long as the import chain (files that each import the next) with the most code lines*; all the other files can be built beside it. The popup names the file of that chain building at that moment

Because this is text search, declarations generated by commands or macros are missed.
