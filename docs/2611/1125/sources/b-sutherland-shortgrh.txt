This page concerns the shorter proof only. The checks of the original 17-million-line proof are recorded on a separate page [../grh/].

Summary

The repository contains two Lean 4 projects, a “readable” edition (grh/, 803 files, about 300,000 lines of code) and a “compact” edition (grh-compact/, 794 files, about 76,000 lines of code). Each proves the same five theorems as the original proof: Mathlib's RiemannHypothesis and four statements about zeros of the Riemann zeta function and of Dirichlet L-functions. Both use Lean v4.35.0 and Mathlib at commit 56a00585.

Both editions compile without errors, and in both the five theorems depend only on the axioms propext, Classical.choice and Quot.sound. Every module of both editions has been replayed through the Lean kernel. Exports of the five theorems made independently on two machines are byte-identical, and nanoda, con-leche and con-ron accept them for both editions. The --compare modes of con-leche and con-ron each confirm all five theorems against the challenge file.

lake comparator --paranoid (Lean v4.35.0) reports “Your solution is okay!” for both editions. It builds the project in a sandbox, compares the five statements with the challenge file, checks the axioms, and then runs Lean's kernel and every external checker shipped with Lean: nanoda, lean4lean, con-leche, con-ron and the paranoid build of Lean's own checker. For the compact edition it passed independently on two machines. For the readable edition it passed on the larger machine; lean4lean needs 332 GB of memory for that edition, more than the smaller machine has, so the run there was stopped without a verdict (see the note below the table).

Machine A is a 16-core AMD Ryzen AI Max+ 395 with 128 GB of memory; machine B is a 192-core AWS r8a.48xlarge with 1.5 TB. The two machines ran from separate clones of the same commit. lake comparator builds the project itself inside its own bwrap sandbox, so the runs on machine B are independent of the builds on machine A; the runs on machine A reuse the build in the first row.

The rows below the two lake comparator rows are separate runs of individual checkers on copies of the exports that lake comparator itself made on machine B (A = readable, B = compact in the scripts). They were run in parallel so that each result is available without waiting for the judge to reach that checker in its sequence. The lean4lean shipped with Lean v4.35.0 does not read this toolchain's compiled files (“incompatible header”), so lean4lean was run on the exports only, not module by module.

lean4lean on the readable edition. lean4lean accepts both editions, but at very different cost. On the compact edition it finished in 28 min 39 s using 7 GB of memory. On the readable edition it took 2 h 35 min and 332 GB, of which 2 h 12 min (7,917,635 ms by its own report) went on the single definition New.Variety.tiltTheory (src/Lib/PadicComparison/Primitive/PeriodCoefficients.lean, line 650); the compact edition defines tiltTheory differently. Lean's own kernel, in its default and paranoid builds, checks the whole readable export in about half an hour with under 8 GB. In practice this means lake comparator --paranoid on the readable edition needs a machine with well over 332 GB of memory and about four hours. On machine A, which has 128 GB, we stopped lean4lean at 70 GB, so that run has no verdict.

The statements

The five theorems are stated in src/Statements.lean, which imports only Mathlib, and src/Main.lean. Statements.lean is byte-for-byte the same file in the two editions, and its four definitions are textually identical to those in the original proof's Statements.lean. The theorem names and the list of permitted axioms in comparator.json are also the same as in the original proof.

theorem riemannHypothesis : RiemannHypothesis
theorem riemannZeta_eq_zero_re : RiemannZetaZerosOnLine
theorem LFunction_ne_zero_of_half_lt_re : DirichletLNonvanishingRightOfHalf
theorem LFunction_eq_zero_re : DirichletLZerosOnLine
theorem LFunction_eq_zero_re_of_isPrimitive : PrimitiveDirichletLZerosOnLine

def RiemannZetaZerosOnLine : Prop :=
 ∀ s : ℂ, riemannZeta s = 0 → (¬∃ n : ℕ, s = -2 * ((n : ℂ) + 1)) → s ≠ 1 → s.re = 1 / 2

def DirichletLNonvanishingRightOfHalf : Prop :=
 ∀ (N : ℕ) [NeZero N] (χ : DirichletCharacter ℂ N) (s : ℂ),
 1 / 2 < s.re → (χ ≠ 1 ∨ s ≠ 1) → DirichletCharacter.LFunction χ s ≠ 0

def DirichletLZerosOnLine : Prop :=
 ∀ (N : ℕ) [NeZero N] (χ : DirichletCharacter ℂ N) (s : ℂ),
 0 < s.re → s.re < 1 → DirichletCharacter.LFunction χ s = 0 → s.re = 1 / 2

def PrimitiveDirichletLZerosOnLine : Prop :=
 ∀ (N : ℕ) [NeZero N] (χ : DirichletCharacter ℂ N), χ.IsPrimitive →
 ∀ s : ℂ, 0 < s.re → s.re < 1 → DirichletCharacter.LFunction χ s = 0 → s.re = 1 / 2

The kernels check elaborated terms, not source text. This file [explicit-statements.out] prints the five statements as Lean v4.35.0 elaborates them with pp.all, so that no notation, coercion or implicit argument is hidden (script [explicit-statements.lean]); the output is identical in the two editions. Source scan

Before building, both editions were searched for constructs that add assumptions, run code during compilation, or change how terms are checked. Neither contains any axiom declaration, native_decide, #eval, unsafe, opaque, implemented_by, extern, initialize, custom elab, macro or syntax, or any kernel-related option. The only uses of sorry are in Challenge.lean, where they stand in for the proofs to be compared. Every file imports only Mathlib or the project's own modules. This scan is a text search and is a precaution, not a proof; the axiom audit and the kernel checks above are what establish the result.

Check it yourself

On Linux with elan [https://github.com/leanprover/elan] and bubblewrap installed:

git clone https://github.com/lsernau/grh-lean && cd grh-lean
git checkout 72fead102f663d5c7a407964a13dc0cf9d977207
cd grh-compact # or: cd grh
lake exe cache get
ulimit -s unlimited
PATH="$(dirname "$(elan which lean)"):$PATH" lake comparator --paranoid

Two practical points. lake comparator looks for the bundled checkers on the PATH, which is why the toolchain's bin folder is added above; without it the command stops at once with "nanoda kernel nanoda_bin was not found". On a machine with very many cores, lake exe cache get may need a higher open-file limit (ulimit -n 65536).

Caveats

These checks show that Lean accepts proofs of the five stated theorems from the three standard axioms. They say nothing about whether the argument has been read or understood by a mathematician, and the repository itself says that it has passed machine checks only.

A passing check establishes the statements as Lean elaborates them. Whether those statements say what the Riemann Hypothesis and the Generalized Riemann Hypothesis are understood to say is a matter of reading Statements.lean and Mathlib's definitions of riemannZeta, DirichletCharacter.LFunction and RiemannHypothesis.

The repository is a single commit by its authors, who describe it as a shorter rewriting of the original proof. We checked the commit named at the top of this page and nothing else.
