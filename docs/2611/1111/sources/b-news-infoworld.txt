AWS unveils local emulator service to help enterprises accelerate app development and testing

 news

 Nov 11, 20266 mins

 The emulator lets developers and AI coding agents test AWS applications locally, reducing cloud provisioning time and costs. 

 Credit: gguy / Shutterstock 

AWS launched a new local emulator service for its cloud services on Wednesday to help enterprises accelerate application development and testing.

The service, named AWS Emulator, will allow developers and AI coding agents to build, deploy, and test AWS-dependent applications on their machines without provisioning actual cloud infrastructure and paying for it, thereby potentially reducing development time and associated costs, the hyperscaler said in a statement.

To achieve this, AWS Emulator replicates the APIs of AWS services locally and exposes a local HTTP endpoint that the AWS Command Line Interface (CLI), software development kits (SDKs), and coding agents can access using the same APIs they use to interact with the cloud, it added.

Developers can redirect these tools to the local endpoint by setting the AWS_ENDPOINT_URL environment variable, allowing existing application code and tests to run against simulated AWS services without modification, it further said.

Local testing to speed up development

The new service addresses a growing problem for developers in software development: the need to test increasingly complex cloud applications quickly and repeatedly without the cost and operational overhead of deploying them to the cloud, said Ashish Chaturvedi [https://www.hfsresearch.com/team/ashish-chaturvedi/], executive research leader at HFS Research.

“Developers can test multi-service workflows involving S3 [https://www.infoworld.com/article/4155868/aws-turns-its-s3-storage-service-into-a-file-system-for-ai-agents.html], Lambda [https://www.infoworld.com/article/2254096/get-started-with-aws-lambda.html], DynamoDB [https://www.infoworld.com/article/4202171/aws-updates-dynamodb-with-native-vector-search-to-ease-ai-application-development.html], and API Gateway without provisioning anything, and they avoid both the AWS charges and the clutter of half-finished resources that experiments tend to leave behind in shared accounts,” Chaturvedi said.

“I am sure there would be clients that found a forgotten test bucket or idle instance on a cloud bill months later. Such clients will appreciate an environment that vanishes when the work is done,” Chaturvedi added.

The bigger advantage of the service, however, will be for developers using AI coding agents, according to Advait Patel [https://www.linkedin.com/in/advaitpatel93], senior site reliability engineer (SRE) [https://www.infoworld.com/article/2257232/what-is-an-sre-the-vital-role-of-the-site-reliability-engineer.html] at Broadcom.

“Agents work in loops: write code, run it, see the error, fix it, repeat. When every loop hits real AWS, you wait on provisioning, you pay for resources, and you clean up whatever the agent forgot to delete. Moving that loop to a laptop cuts each cycle from minutes to seconds,” Patel said.

“Teams get faster feedback, fewer leftover test resources, and smaller dev account bills. It also means you can let an agent try things freely without worrying about it spinning up something expensive in a real account,” Patel added.

Faster delivery, safer AI adoption for CIOs

That combination of reduced operational overhead and costs, in turn, is likely to appeal to CIOs looking to accelerate software delivery and scale AI-assisted engineering across their organizations, according to Chaturvedi.

“The clearest benefit is cycle time. Faster feedback in the inner development loop shortens delivery, and that compounds across hundreds or thousands of developers, especially as AI-assisted engineering spreads,” Chaturvedi said.

“The less obvious benefit is safer agent adoption. Many CIOs hesitate to let coding agents provision infrastructure because one misstep in a real account can be costly or create a security exposure. A local environment where agents can experiment freely gives organizations a way to scale AI-assisted engineering while keeping agents away from real resources until the code has been tested,” Chaturvedi added.

Missing features, fidelity gaps limit production readiness

Despite its potential to accelerate development and testing, AWS Emulator comes with limitations that could prevent enterprises from relying on it as a substitute for testing applications against actual cloud infrastructure, according to Devin Pratt [https://my.idc.com/getdoc.jsp?containerId=PRF005946], research director at IDC.

“At launch, the emulator does not simulate throttling or outages, snapshot and restore, or per-Region availability, which matter most for resilience,” Pratt said.

And these gaps, according to Patel, “are the ones that cause real outages.”

“From an SRE view, throttling, partial failures, and regional differences are exactly what take systems down in production. If your tests never see a 429 or a timeout, your retry and backoff logic never gets tested. So yes, there is a real risk of false confidence, especially if teams start treating ‘passed locally’ as ‘ready to ship’ status,” Patel said.

More so because AWS’s own fidelity measurements indicate that the emulator does not yet reproduce every AWS operation accurately.

The hyperscaler measures the fidelity of the service by comparing API responses with those from actual AWS services and testing whether multi-step workflows behave as expected. Operations that have not been implemented or verified return HTTP 503 errors rather than being treated as successful, it said.

That distinction is important because successful tests against the emulator do not necessarily guarantee that applications will behave identically when deployed on actual AWS infrastructure, Patel said.

Developers will therefore need to validate their applications against real cloud environments before deploying them to production, Patel added.

There are security concerns as well, particularly because the emulator does not sandbox the code it executes, according to Pratt.

This means that if developers include real production credentials in functions being tested locally, the code could still access actual AWS resources, potentially exposing enterprises to unintended resource access or security risks, Pratt said.

Despite these trade-offs, enterprises looking to adopt the service can download the Emulator at no charge, with the tool available for Linux, macOS, and Windows, and its source code published on GitHub, the hyperscaler said.

Currently, the emulator supports all 426 AWS services and is built using Rust to minimize CPU and memory consumption, with support for new services and API changes following updates to AWS’ published interface models, it added.
