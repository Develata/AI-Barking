How we built the agents that built AWS Emulator

Thousands of autonomous AI agents wrote every line of code in AWS Emulator, a new local emulator for AWS now available for download.

Share

Written by Matthew Goldberg, Sr. Principal Engineer

Published: November 11, 2026

5 min read

Key takeaways

AWS Emulator is a local emulator of AWS services, 100% written by autonomous AI agents.

Thousands of autonomous agents write tests, find issues, and fix code without human review.

The source code is available on GitHub [https://github.com/aws/aws-emulator] under a CC0 license and is constantly being updated.

I’m a terrible artist. I always have been. My parents sent me to kindergarten a year early. One day, the teacher sat the class down at one of those long tables. She stretched a giant roll of paper across it and asked us to draw a picture of what the Earth must have been like with dinosaurs. I began diligently working on my section of the scene. But, as one of the youngest in the class, my motor skills were not developed enough to hold a crayon correctly. A few minutes later, my classmates were screaming at me. I had done it all wrong.

I thought about those classmates often this year. Just as they lost their temper with me, I’ve found myself swearing at my AI agents more times than I care to admit. But in neither case is the issue malintent. The agents aren’t trying to disobey me, just as I wasn’t trying to ruin my class’s dinosaur painting. It’s a lack of competence. Earlier this year, my partner bought a coloring book, and we spent hours doing one together. There was something comforting about being given a well-defined area to fill in, knowing that the larger piece of art would come together. I think agents also need coloring books.

Today, we released AWS Emulator, a local emulator of AWS services that you can run on your machine to build and test your AWS applications. The emulator was written entirely by autonomous agents. Our team hasn’t written or reviewed any of the code. We could do this because the guardrails we’ve put in place gave the agents space to work independently and us the trust that they don’t color outside these lines.

AWS Emulator started as a weekend experiment

Earlier this year, researchers at Anthropic [https://www.anthropic.com/engineering/building-c-compiler] demonstrated that AI agents could autonomously build a C compiler. This was a lightbulb moment: If given a well-defined spec and a reference implementation, agents can autonomously build a solution that faithfully implements the specification. AWS has both of those; the AWS API Models [https://github.com/aws/api-models-aws] are our spec and the actual AWS cloud is our reference implementation. To test my hypothesis, I gave Kiro [https://www.aboutamazon.com/news/aws/amazon-ai-frontier-agents-autonomous-kiro] the simplest prompt that I could think of without any expectation that this would work:

Write tests based on the AWS Command Line Interface (CLI)

Iterate on those tests until they pass against real AWS

Build an in-memory implementation that those same tests pass against

Kiro came back after 15 minutes with a passable first version of an Amazon Simple Queue Service (Amazon SQS). I refined my prompt and had Kiro build me the rest of AWS over the weekend. And it did. It obviously had gaps, but it was compelling enough that my team started using it to test our software that Monday.

Turning that into a robust product took more than a weekend. There’s a natural temptation these days to see results like those and believe that AI can build anything [https://www.aboutamazon.com/news/aws/aws-ceo-ai-inference-transforms-developer-capabilities]. Maybe it will eventually. But building something that you feel confident putting in your customers’ hands still requires serious engineering effort. In the case of AWS Emulator, it required building guardrails that ensure the agents color within our lines.

How three teams of AI agents build AWS Emulator

AWS Emulator is fundamentally built by three teams of agents. One team manages a test suite; one team finds issues in the emulator; and one team fixes those issues. We divide agent responsibility into these teams because we’ve found they have more success on bounded tasks.

A graphic showing how teams of AI agents work together to run tests and solve issues.

The first team’s test suite measures fidelity against the real AWS cloud. Each test is a real-world AWS scenario. For example, a test for Amazon SQS might include creating a queue, sending a message, receiving it, acknowledging it, and deleting the queue. Agents devise these tests from publicly released AWS API Models and verify each one against real AWS before submitting. We have tens of thousands of fidelity tests across all of AWS, and that test suite constantly grows as our agents discover new things that they can do with AWS. These tests are one of our most fundamental guardrails in our system because they provide an unambiguous goal that the agents need to meet and can be rerun repeatedly without calling AWS again.

The second team of agents replays the fidelity tests to find divergence in the emulator. When the system initially created the repository, it generated an empty web server that could handle requests for the 438 AWS API Models but did nothing. The agents swarm the repository to figure out what doesn’t work. To kickstart the process, the first issues simply say “build a first version of Amazon SQS.” Once the service is bootstrapped, the agents replay the fidelity tests and file issues for the failing tests. They’re told to reason about the failures and group failures that may share a root-cause.

Each issue is given to an agent in the third team, whose job is to fix that single issue. They check out the code, root-cause the issue, and edit the code until it’s addressed. They must then pass their code change through a gate that ensures it meets our bar. This gate obviously blocks changes that don’t compile. But it also includes agents that review against coding standards, verify the code is secure, and ensure that the change did not regress fidelity. If any of those checks fail, the change is sent back to the agent for rework; if they all pass, it is merged to mainline. We’ve seen thousands of issues fixed every day as hundreds of agents concurrently work on the codebase. Without this merge gate, we wouldn’t trust what our agents are building. We focus a lot on optimizing it because it’s so critical to how quickly and reliably the agents build.

How AWS Emulator ships to GitHub

Once merged to mainline, the changes flow through a release pipeline built entirely on AWS Developer Tools, with AWS CodeCommit as the agents’ primary code repository. Commits typically stack up together and are built and retested before we merge them to a release branch. We then package up the emulator as a binary that you can download. Only at the end of the release process do we also publish the code to GitHub.

Three teams of AI agents build AWS Emulator.

We release the code to GitHub so that you can also see what the agents have done building this emulator over thousands of commits. Every issue filed is in the repository. The ones they’ve fixed are in the directory “issues/things-that-now-work”; the ones in their backlog are in “issues/things-that-do-not-work.” You’ll find fascinating stuff if you dig. We’ve had our agents build many versions of this emulator as we’ve refined the building machine. My personal favorite was from an earlier version, when they decided to build their own Python interpreter to support AWS Lambda functions. We’ve since given them guidance to reuse existing libraries, something that may seem obvious to someone who doesn’t need a coloring book. I’m looking forward to what other novel solutions the agents come up with in this version. But I trust the outcome because of our guardrails. The insights we’ve gained from this history were the main motivation in our decision to release this software as a public dedication under the Creative Commons CC0 license.

What's next for AWS Emulator

This is the first in a series of posts where I’ll dive deeper into topics such as how we architected our multi-agent workflow, how we measure fidelity, and how we ensure our quality and security bar.
