> How the original build was done, and the rebuild that checks it. The original build ran on cloud machines without a sandbox, and compiled each file by calling lean directly with the same inputs lake supplies (module name, package name and the lakefile's options), not through lake build. All the kernel checks above were run on the export from that build. We then repeated the build on a separate machine with lake build Main inside a bubblewrap sandbox: no network, the source tree read-only, only .lake writable, the archive downloaded afresh from the author's site, and Mathlib's files checked against the official cache first. The export made inside that sandbox is byte-identical to the published one, so every check on the published export applies to it.
> The per-file .olean hashes depend on the build directory, and one module is not deterministic. In Lean v4.33.1 a compiled file stores each linter message together with the absolute path of its source file. Of our 175,187 compiled files, 98,219 contain the path /home/ubuntu/grh/src/lean/src/…; the other 76,968, including Main.olean, contain no path. So project-oleans.sha256 can be reproduced only by a build whose source tree is at /home/ubuntu/grh/src/lean; elsewhere, only the files of modules that emit no linter messages should match.
>  The sandboxed lake build was run at that same path, and 175,186 of its 175,187 files are byte-identical to our manifest. The exception is Formalism/LocalToGlobal/SiegelLatticeTheory/CokernelGLCounts/RankPointCounts/LocModel.olean: same size, different contents. Recompiling that one module six times on one machine with identical inputs gave one output four times and the other twice, and those are exactly the two hashes in the two manifests. The two outputs differ in 38 bytes: the name of one bound variable in BBtop.eq_1, an equation lemma that Lean generates automatically the first time a proof asks for it. Two adjacent theorems in the file both ask for it, Lean elaborates theorem bodies in parallel, and the lemma takes that variable's name from whichever theorem gets there first. Bound-variable names play no part in kernel checking, so the two files are logically the same. The export is not affected, and the export from the sandboxed build is byte-identical to ours: an export contains only the declarations that the five theorems depend on, and BBtop.eq_1 is not one of them, because the proofs that caused it to be generated do not refer to it. We checked that this name does not occur in the export. Had a proof on the dependency path referred to such a lemma by name, two builds could have produced exports with different hashes, although every check would still have passed on either. Compiled single-threaded (lean -j1), the module gave the same output six times out of six. A ten-line file with no imports [nondet-repro.lean] reproduces the behaviour: on Lean v4.33.1 and v4.34.1 it compiles to two different outputs with -j32 and to one with -j1; on v4.36.0 it gave one output in 40 runs. The same race, with the first caller's options in place of its names, was reported as Lean issue #15498 [https://github.com/leanprover/lean4/issues/15498] and fixed by pull request #15499 [https://github.com/leanprover/lean4/pull/15499], first released in v4.36.0. That change also removes this behaviour: the file gives two outputs on the nightly builds of 7 and 8 October 2026 and one output in 40 runs on those of 9 and 10 October and on the toolchain built from the pull request alone. Because of this module, the sha256 of the whole manifest file is not reproducible even at the same path; compare file by file.
