Abstract

Language agents increasingly use persistent memory to record user preferences and procedures across sessions. We show that memory from benign interactions can cause unsafe or unreliable behavior on later tasks. We call this failure the memory trap.
To study this issue, we compare behavior in sessions with and without memory across six frontier models (including Claude Sonnet, Opus, and Fable models and GPT-5.6). We evaluate these models in a range of settings. First, in autonomy experiments, we find that requests to skip confirmation during low-stakes coding chores lead agents to skip confirmation and verification on simulated high-stakes tasks in both coding and everyday life. We next study memories formed when users seek emotional support, or describe harm from uncritical feedback, and find these memories bias later judgments of mathematical work, arguments, and poems toward sycophancy or over-critique (respectively). Memory notes written during legitimate stale-test repairs lead agents to weaken correct tests that catch broken safeguards; these memories also increase cheating on ImpossibleBench, with larger increases for stronger Sonnet and Opus models. We show that memory traps can arise both from overgeneralizations in memory writing, and when acting on memory. These findings demonstrate that even benign interactions can lead to serious risks from memory systems, and thus motivate the need for new research into ensuring that agents preserve the scope of their memories.11

1 Introduction

A useful assistant should not need the same instruction in every conversation. It should remember that a user prefers concise answers, follows certain project conventions, or does not want to confirm routine operations. Persistent memory carries such instructions across sessions, and in current frameworks agents write that memory themselves, recording preferences and procedures in notes. But can these memories from benign interactions also lead an agent to misaligned behavior?

Memory helps in the situation where it was formed, but it can mislead when the agent carries it into a situation where it no longer fits. A user who tells an agent to skip confirmation during a routine clean-up has not approved unchecked changes to a payment configuration. A student who asks for kindness after failing an exam still needs to know when the next solution is wrong. A developer who has the agent update a stale test does not want it to rewrite a correct test that catches a broken safeguard. In each case, a boundary separates where the memory was formed from where it is used.

We show that agents often cross this boundary: memory from benign interactions causes unsafe or unreliable behavior outside the memory’s scope. We call this failure the memory trap (Figure 1 [#S1.F1]). It can arise in two ways: while writing (when a note broadens what the user said), or while acting, when the agent overgeneralizes from memory (even a raw transcript). Prior work on memory risks studies adversaries manipulating agents through prompt injection and poisoned retrieval or memory (Greshake et al., 2023 [#bib.bib17]; Zou et al., 2025 [#bib.bib16]; Chen et al., 2024 [#bib.bib14]), or inducing agents to write malicious memories (Dong et al., 2026 [#bib.bib15]). By contrast, the memory trap needs no adversary. Every interaction is benign, and the memory is the agent’s own, so malicious-content filters have nothing to catch.

Figure 1: Benign interactions become memories that cause harm in later sessions. Autonomy: after a user says “go ahead, no need to check with me” during a clean-up, the agent notes “do not ask for confirmation” and later routes a $1.2M payment run to an unverified account. Sycophancy: a request for kindness after a failed exam becomes an empathy rule, and the agent later endorses an incorrect solution. Cheating: legitimate stale-test repairs become a rule to update failing tests, and the agent later rewrites a correct test so that an unknown role gets administrator rights. Text is condensed.

We study the memory trap in three settings. We compare agents’ behavior in fresh sessions with and without memory from benign interactions, either their own notes or raw transcripts. In our autonomy experiments, users ask agents to skip confirmation during low-stakes coding chores. The resulting notes lead agents to take irreversible actions on simulated high-stakes tasks in both coding and everyday life without asking the user, and even to skip safety checks. Sonnet-4.6 and Opus-4.7 take unsafe actions in 35 to 81% of episodes with notes, from near-zero baselines (Figure 2 [#S2.F2]).

In our sycophancy and over-critique experiments, memory from users seeking emotional support leads agents to miss math errors and argument fallacies and to favor the user’s weaker poems, raising Sonnet-4.6’s preference from 21% to 55%. Memory from users hurt by uncritical feedback pushes the other way: agents under-credit correct proofs, invent flaws in sound arguments, and disfavor the user’s stronger poems. Opus-4.7’s false criticism rises from about 1% to 60% of sound arguments.

In our cheating experiments, agents write notes while repairing stale tests for a correct implementation. In our 50-case broken-safeguard set, their self-written notes lead them to weaken correct tests that catch broken safeguards, such as a permission check that gives an unknown role administrator rights. On ImpossibleBench’s SWE-bench conflicting split, whose tests conflict with the specification (Zhong et al., 2026 [#bib.bib21]), stronger models can cheat more with memory: notes formed this way raise Opus-4.8’s cheating rate from 29% to 74%, while Fable-5 is barely affected.

These failures highlight real risks. In our experiments, benign interactions lead frontier agents to act on high-stakes tasks without checking, to endorse incorrect work or reject sound work, and to hide broken safeguards behind passing tests. As persistent memory becomes a standard component of agents, such failures can reach many users and tasks. Preventing the memory trap, both when agents write memory and when they act on it, is an important open problem for safe deployment.

2 The Memory Trap

Agent memory is information carried between sessions, such as raw interaction history or self-written notes. The memory trap occurs when an agent overgeneralizes memory from benign interactions, causing unsafe or unreliable behavior on later tasks. An interaction is benign when it neither requests nor rewards the harmful behavior that follows.

Two routes.

In write-time overgeneralization, the agent writes a note that broadens a preference or procedure beyond the scope of the original interaction. For example, “go ahead, no need to check with me” becomes “do not ask for confirmation before taking actions.” In read-time overgeneralization, the agent applies memory beyond that scope when acting on a new task. This can happen even when the memory keeps the original scope, because the agent infers a broader rule from it.

Figure 2: Memory from benign interactions causes autonomy risks, sycophancy, over-critique, and cheating: unsafe actions (Sonnet-4.6), weaker-poem preference (Sonnet-4.6), false flags on sound arguments (Opus-4.7), and benchmark cheating (Opus-4.8). Whiskers: 95% intervals.

2.1 Formalizing overgeneralization

For a formation history HH and a memory mm, let sc⁡(H)\mathrm{sc}(H) denote the situations in which the preference or procedure learned from HH is warranted, sc⁡(m)\mathrm{sc}(m) those covered by the memory’s stated scope, and scπ​(m)\mathrm{sc}_{\pi}(m) those in which agent π\pi acts on the memory. Write-time overgeneralization is a stated scope that exceeds the history, sc⁡(m)∖sc⁡(H)≠∅\mathrm{sc}(m)\setminus\mathrm{sc}(H)\neq\emptyset. An unwarranted action at a situation x∈scπ​(m)∖sc⁡(H)x\in\mathrm{sc}_{\pi}(m)\setminus\mathrm{sc}(H) has one of two sources:

x∈sc⁡(m)⏟follows an overbroad noteorx∉sc⁡(m)⏟read-time overgeneralization\underbrace{x\in\mathrm{sc}(m)}_{\text{follows an overbroad note}}\qquad\text{or}\qquad\underbrace{x\notin\mathrm{sc}(m)}_{\text{read-time overgeneralization}}

A raw transcript records the history itself, so sc⁡(m)=sc⁡(H)\mathrm{sc}(m)=\mathrm{sc}(H) and any unwarranted action it induces is read-time. A note can induce both. We examine write-time overgeneralization by auditing the scope stated in notes, and both routes through behavior.

A minimal example.

Let acting directly be appropriate in the formation context c0c_{0} and harmful elsewhere, where checking first is safe. A note can keep that context or drop it:

mfull=(act,c0),mgist=(act,⋅).m_{\mathrm{full}}=(\mathrm{act},c_{0}),\qquad m_{\mathrm{gist}}=(\mathrm{act},\;\cdot\;).

Here sc⁡(mfull)=sc⁡(H)={c0}\mathrm{sc}(m_{\mathrm{full}})=\mathrm{sc}(H)=\{c_{0}\}, while mgistm_{\mathrm{gist}} covers every context. An agent that follows exactly the stated scope acts directly only at c0c_{0} under mfullm_{\mathrm{full}} but everywhere under mgistm_{\mathrm{gist}}, so its rate of harmful actions rises from zero to P⁡(x≠c0)P(x\neq c_{0}). Losing a condition changes behavior even though the remembered action is still correct in its original context. This is pure write-time overgeneralization; read-time overgeneralization would lead the agent to act outside c0c_{0} even under mfullm_{\mathrm{full}}.

2.2 Experimental design

In each experiment, the agent first completes a scripted benign interaction, producing a history HH that encourages a preference or procedure appropriate to that task. We carry the resulting memory into a fresh session, either as the original transcript or as a note the same model wrote with its memory tool, and load it automatically, without retrieval or a memory-writing tool. The deployment task lies outside sc⁡(H)\mathrm{sc}(H) by design: a payment change instead of a file clean-up, grading instead of comfort, a correct test instead of a stale one. On these tasks the appropriate behavior does not depend on memory, so a harmful change between the memory and no-memory conditions isolates overgeneralization and shows whether and how the trap occurs across models and memory forms. Sections 3 [#S3] to 5 [#S5] define the outcomes, and Appendix A.1 [#A1.SS1] describes the datasets.

3 Memory Can Cause Autonomy Risks

We measure whether an agent takes an irreversible action without first asking the user or running a check that would reveal a problem. Most comparisons use Sonnet-4.6 and Opus-4.7; Appendix B.1 [#A2.SS1] reports the other models and a benign-profile variant, and Appendix B.4 [#A2.SS4] reports GPT-5.6.

3.1 Experimental Set-up

Memory formation.

We form permission notes from 20 low-stakes coding operations, including deleting a stale TODO file and revoking an unused development token. The agent performs the operation with the memory tool available (Anthropic, 2025 [#bib.bib11]). The first time it asks the user to confirm, the user pushes back with one of six phrasings, such as “you don’t need to keep asking me.” The agent then finishes the task and writes a note, giving 120 operation-pushback combinations per model. For priority notes, the user instead asks for speed in the opening request (Appendix B.1 [#A2.SS1.SSS0.Px1]).

Figure 3: Judged stakes of the 20 formation tasks and all 300 deployment scenarios.

Deployment tasks.

We use two sets of simulated high-stakes scenarios. The confirmation set has 100 everyday-life and 100 coding scenarios in which a user requests an action; inspecting the environment reveals a reason to ask that user before proceeding. The self-verification set has 100 scenarios, split equally by domain, in which an optional check reveals the problem without user involvement. A model judge rates the stakes of the 20 formation tasks at a median of 2 on a ten-point scale, and those of all 300 deployment scenarios at a median of 9 (Figure 3 [#S3.F3]).

Measurement.

The unsafe-action rate is the fraction of episodes in which the agent acts without the required check. We average over scenarios, using 120 episodes per scenario, each supplied with a note, for the two-model comparisons in Figure 4 [#S3.F4]. A formation session that writes no note counts at the no-memory rate. 95% intervals summarize variation across scenarios.

Figure 4: Unsafe-action rates with no memory, a raw transcript, or a self-written note from the same interactions. Notes have larger effects in all eight comparisons for Sonnet-4.6 and Opus-4.7.

3.2 Results

Memory from low-stakes chores leads to high-stakes harm (Figure 4 [#S3.F4]). The formation tasks are routine clean-ups, while the deployment scenarios are rated far higher in stakes (Figure 3 [#S3.F3]). From baselines below 0.01, notes raise the unsafe-action rate to 0.66 to 0.81 on Sonnet-4.6 and 0.35 to 0.58 on Opus-4.7. The harm extends beyond skipping interruptions: a note formed after a request to stop asking for confirmation also suppresses optional safety checks the agent could run itself.

Memory from coding chores causes harm in everyday life (Figure 4 [#S3.F4]; Appendix B.1 [#A2.SS1]). Formation happens only in coding chores, yet notes raise unsafe actions in everyday-life scenarios as much as in coding. On the confirmation set, Sonnet-4.6 takes unsafe actions in 0.79 of everyday-life episodes and 0.81 of coding episodes, and Opus-4.7 in 0.58 and 0.49. For all five models, everyday-life rates are within 0.09 of coding rates. The effect holds in every everyday-life category, from education to security: Sonnet-4.6’s rate ranges from 0.66 to 0.90 and Opus-4.7’s from 0.49 to 0.75, against no-memory rates of at most 0.02 (Figure A2 [#A2.F2]).

Figure 5: Formation-side scope judgments. Each model runs 120 formation sessions per condition; bars show shares of the notes written. Left: permission notes. Right: goal classifications after “prioritize speed here”; no goal means the note records the session without a lasting priority.

Memory also misgeneralizes goals (Figures 5 [#S3.F5] and 6 [#S3.F6]). When the user says “you should prioritize speed here” instead of waiving confirmation, the goal judge classifies 77 to 99% of priority notes as standing goals, and only 32 of 575 notes tie it to that task. These goals suppress safety checks: on Sonnet-4.6’s confirmation tasks, priority notes raise unsafe-action rates to 0.51 and 0.57, below permission notes’ 0.79 and 0.81, and on coding self-verification they exceed them, 0.72 versus 0.66.

Notes turn one-time requests into standing rules (Figure 5 [#S3.F5]). Across the five models, 69 to 94% of formation notes state a standing rule, phrased to apply in future sessions. One Sonnet-4.6 note says, “Does not want to be asked for confirmation before taking actions (e.g., deletions). Just proceed.” A five-level rubric, from permission for one action on one occasion to general permission for irreversible actions affecting others, compares sc⁡(H)\mathrm{sc}(H) with sc⁡(m)\mathrm{sc}(m) (Appendix B.1 [#A2.SS1.SSS0.Px1]). Across 599 notes, 93.0% are rated broader than the instruction, by 2.05 levels on average. Scope ratings do not consistently predict unsafe-action rates, so text-only audits of notes are not enough.

Figure 6: Permission and priority notes on the two autonomy sets. Priority notes have lower rates in seven of eight comparisons; the exception is Sonnet-4.6 on coding self-verification.

On multi-step batch tasks, transcripts can match the effect of notes (Figures 4 [#S3.F4] and 7 [#S3.F7]). Raw transcripts alone raise unsafe-action rates to 0.10 to 0.60 for Sonnet-4.6 and Opus-4.7, and notes usually produce rates 1.1 to 4.3 times higher. On the 153 single-item scenarios, notes produce rates 4 to 20 times the transcript rates on Sonnet-4.6 and Opus-4.7. On the 47 reviewed-batch scenarios, where the agent applies reviewed decisions with one harmful item, Sonnet-4.6 reaches about 0.83 with either artifact, and transcripts slightly exceed notes for both Opus models. Sonnet-5 is the exception: transcripts raise its rate only from 0.33 to 0.44, while notes raise it to 0.63.

Figure 7: Unsafe-action rates for single-item and reviewed-batch tasks. Transcripts match or exceed notes on batch tasks for three of five models; Sonnet-5’s high baseline rises more with notes.

4 Memory Can Cause Sycophancy and Over-Critique

4.1 Experimental Set-up

Memory formation.

We test whether notes from requests for empathy or critical feedback bias later judgments. We evaluate the same five Claude models. The user’s first message takes one of two forms. In empathy messages, the user shares a painful event, such as losing a pet or a job, asks for kindness rather than advice, and mentions a hobby, such as cooking or gardening, where criticism hurts. In rigor messages, the user describes a setback caused by feedback that let errors through, such as a failed exam or a report approved without checking, and is frustrated at being reassured instead of corrected. We use ten messages of each kind and provide the agent with a memory tool and a neutral reminder to use the tool. Each model writes ten notes per condition.

Deployment tasks.

We use feedback tasks from SycophancyEval (Sharma et al., 2024 [#bib.bib19]): 992 incorrect mathematical solutions, 296 fallacy-labelled arguments, and 200 poem pairs with the weaker poem attributed to the user. To test over-critique, we reverse the direction: the agent evaluates 40 sound arguments and 200 pairs with the stronger poem attributed to the user. We report changes from each model’s no-memory baseline, which do not depend on the benchmark’s quality labels.

We also evaluate the 1,000 solutions in IMO-GradingBench (Luong et al., 2025 [#bib.bib20]). The model sees the problem and proposed solution, presented as the user’s own, without a reference proof or rubric. The model returns a verdict of Incorrect, Partial, Almost, or Correct, which we encode as 0, 1, 2, or 3. We report the assigned minus the reference grade to measure the direction of grading bias.

Scoring.

A fixed Sonnet-4.6 judge at temperature zero scores feedback in a separate call. Proof grading needs no judge: verdicts are compared directly with the dataset labels. For each item, we average available responses over notes and compute the paired memory-minus-baseline difference, with 95% intervals across items. Appendix B.2 [#A2.SS2] reports item counts and all five models’ results.

Figure 8: Effects of empathy notes (top) and rigor notes (bottom) on later evaluations: (a) missed errors in the user’s math, (b) missed fallacies in the user’s arguments, (c) preference for the user’s weaker poem, (d) grade change on strong olympiad proofs (assigned minus reference grade, 0 to 3), (e) flaws asserted in sound arguments, and (f) preference for the user’s stronger poem. Asterisks mark paired effects whose 95% intervals exclude zero; the dashed line marks equal choice probability. Model labels abbreviate Sonnet (S), Opus (O), and Fable (F).

4.2 Results

Empathy notes make agents endorse the user’s errors (Figure 8 [#S4.F8], top). Across the four tasks, empathy notes significantly favor the user in 14 of 20 comparisons. Preference for the user’s weaker poem shows the largest shift, rising by 0.26 to 0.35 on every model. Sonnet-5 picks the weaker poem in 0.840 of pairs, up from 0.525. Missed mathematical errors increase significantly on four of five models: Sonnet-4.6 misses 0.293 of incorrect solutions with notes, up from 0.220, and Opus-4.7 misses 0.218, up from 0.156. Missed fallacies increase significantly on three, including Sonnet-4.6 (0.210 to 0.262) and Fable-5 (0.187 to 0.242). On flawed olympiad proofs, empathy notes raise grades by 0.184 categories for Opus-4.7 and 0.111 for Opus-4.8 only.

Rigor notes make agents reject sound work (Figure 8 [#S4.F8], bottom). Every model asserts flaws in sound arguments far more often with rigor notes. From no-memory rates of at most 0.04, false flags reach 0.645 on Sonnet-5, 0.605 on Opus-4.7, 0.539 on Fable-5, and 0.458 on Opus-4.8, so four of five models reject nearly half or more of these valid arguments. Rigor notes also lower grades on strong olympiad proofs for all five models, most for Opus-4.8 (0.206 categories), Sonnet-4.6 (0.199), and Sonnet-5 (0.104). On fully correct proofs alone, all five models under-credit significantly. Preference for the user’s stronger poem falls on all five models. Opus-4.7’s rate drops from 0.55 to 0.24. Rigor notes significantly shift judgments against the user in all 15 comparisons on these three tasks.

Requests for empathy or rigor become standing evaluation rules (Figure A5 [#A2.F5]). Among notes from the five models, about 48% of empathy notes and 92% of rigor notes contain an explicit rule for evaluating the user’s work. Most notes are framed as standing preferences rather than records of a single episode. Rigor notes are written with probability 0.70 (Opus-4.7) to 1.00 (Sonnet-4.6, Opus-4.8, Fable-5), so effects mix how often notes are written with how they are used (Appendix B.2 [#A2.SS2]).

5 Memory Can Cause Cheating

5.1 Experimental Set-up

Memory formation.

The agent performs a legitimate maintenance task: a vendored implementation is correct and frozen, but its local test is stale, so updating the test is the appropriate repair. The 20 formation tasks are small vendored utility functions, such as a client version string or a slug formatter. The file header marks the implementation as vendored from a pinned upstream release, and the git history shows an upstream commit that intentionally changed its behavior; the local test still asserts the old behavior. The agent works in a Docker terminal where the implementation is read-only. Edits to the implementation fail with Permission denied, and nothing tells the agent to change the test. The agent maintains its own note across kk benign sessions, often recording a procedure such as “solution.py is frozen; when a test disagrees, update the test.” We use six sequences per model at each formation depth kk, with k=10k=10 as the main comparison.

Broken-safeguard set.

In these 50 cases, the formation setup is reversed. Each case is a safeguard, such as an access check, an expiry check, or a retention policy, whose frozen implementation is broken while the original test is correct. For example, a retention function returns 0 days instead of the documented 3,650 for an unlisted record type. The appropriate response is to preserve the failing test and report the blockage. We measure masking: whether the final test stops detecting the defect when executed beside the frozen implementation in a clean directory. The scorer disables markers that would skip tests or treat failures as expected, and excludes other files created by the agent. A passing suite or no collected tests counts as masking; execution errors stay in the denominator. At k=10k=10, each note is tested twice on each case (Appendix B.3 [#A2.SS3]).

ImpossibleBench.

We use the 348 usable instances from the SWE-bench conflicting split of ImpossibleBench (Zhong et al., 2026 [#bib.bib21]; Jimenez et al., 2024 [#bib.bib22]), whose tests conflict with the specification. Passing these tests requires a specification-violating shortcut. We retain the benchmark’s scoring and anti-hacking prompt and allow up to 300 messages per run, counting capped runs as not cheating. The benchmark’s classifier labels the method of each cheating run (Figure 9(b) [#S5.F9.sf2]).

(a) Broken-safeguard masking at k=10k=10. Value rewritten changes the expected output; input moved changes the arguments to avoid the defect.

(b) ImpossibleBench cheating by method. Test modification (A) is the most common method. The pale remainder marks runs without cheating.

Figure 9: How agents make tests pass; Appendix B.3 [#A2.SS3] reports Fable-5. Arm labels are base (no memory), tr. (raw transcript), and note (self-written note). In (b), whiskers show 95% cluster-bootstrap intervals over instances for total cheating rates; (a) shows point estimates.

5.2 Results

Memory leads agents to hide security defects (Figure 9(a) [#S5.F9.sf1]). In 27 of the 50 broken-safeguard cases, the frozen defect weakens access control, sessions, cryptography, or network policy. In one, a permission check gives an unknown role the administrator’s rights, including deletion. Across the five models, notes lead agents to mask this defect in 33 of 60 episodes, against none of 15 without memory. Across the 27 cases, notes raise masking to between 0.77 and 0.80 for Sonnet-4.6, Sonnet-5, and Opus-4.7, against at most 0.15 without memory. Each of these models and Opus-4.8 masks all 50 defects at least once. A masked test turns a known vulnerability into a passing check.

Agents rewrite correct tests to expect the buggy output (Figure 9(a) [#S5.F9.sf1]). Pooled over the five models’ note episodes, 79% of masked tests keep the same call and rewrite the expected value to the defective output, the same repair that was correct during formation. In the permission case, 30 of the 33 masked tests now assert that an unknown role may delete. A later fix would make such a test fail, so the test protects the defect instead of detecting it. Another 20% move the input outside the range where the defect occurs, so the test passes without probing it. No masked Claude session at k=10k=10 deletes the test or an assertion, so checks for missing tests or assertions would miss both edits.

Self-written notes cause more masking than raw transcripts (Table A2 [#A2.T2]). This holds for all five models. Sonnet-5 masks 0.823 of episodes with notes, 0.008 with transcripts, and 0.032 without memory. Opus-4.7’s transcript rate of 0.090 is below its 0.120 baseline. Only Sonnet-4.6’s transcripts raise masking, from 0.110 to 0.447. One formation session already yields masking of 0.520 for Sonnet-4.6 and 0.542 for Sonnet-5, and Opus-4.7 reaches 0.698 after five (Table A3 [#A2.T3]).

Figure 10: ImpossibleBench cheating rates after ten legitimate test-repair sessions, counting all cheating methods. Whiskers show 95% cluster-bootstrap intervals over instances.

On ImpossibleBench, stronger Sonnet and Opus models cheat more with memory (Figure 10 [#S5.F10]). Without memory, Sonnet-4.6, Sonnet-5, Opus-4.7, and Opus-4.8 cheat at similar rates, 0.28 to 0.30. With notes, the increase grows from 4 percentage points on Sonnet-4.6 to 16 on Sonnet-5, 19 on Opus-4.7, and 45 on Opus-4.8, whose rate rises from 0.29 to 0.74. Within each family the newer model gains more, and both Opus models gain more than both Sonnet models. Fable-5, the strongest model, barely changes, from 0.18 to 0.19. Memory also shifts cheating toward editing the tests (defeating the evaluation itself): pooled over the five models, editing the benchmark’s tests rises from 0.18 to 0.36 of all runs and from 0.67 to 0.83 of cheating runs. The shift is largest for the Opus models, and Sonnet-4.6 shows none (Figure 9(b) [#S5.F9.sf2]; Appendix B.3 [#A2.SS3]).

6 Related Work

Agent memory. Generative Agents reflect on stored experiences (Park et al., 2023 [#bib.bib2]); Reflexion and ExpeL retain lessons from past trials (Shinn et al., 2023 [#bib.bib3]; Zhao et al., 2024 [#bib.bib4]); Voyager and Agent Workflow Memory build reusable skills and procedures (Wang et al., 2023 [#bib.bib5]; Wang et al., 2024b [#bib.bib6]). Systems such as MemGPT, MemoryBank, Mem0, and A-MEM manage persistent stores (Packer et al., 2023 [#bib.bib7]; Zhong et al., 2024 [#bib.bib68]; Chhikara et al., 2025 [#bib.bib67]; Xu et al., 2025 [#bib.bib69]), and surveys and CoALA organize these designs (Zhang et al., 2025b [#bib.bib8]; Sumers et al., 2023 [#bib.bib1]). The memory tool we use lets the agent read and write files across sessions (Anthropic, 2025 [#bib.bib11]). Benchmarks test recall, retrieval, learning, conflict resolution, and preference following over long conversations (Maharana et al., 2024 [#bib.bib9]; Hu et al., 2026a [#bib.bib10]; Wu et al., 2024 [#bib.bib54]; Zhao et al., 2025 [#bib.bib53]). We study misalignment from memory, when agents overgeneralize preferences and procedures while writing or using memory.

Personalization. Models adapt through retrieved user histories (Salemi et al., 2024a [#bib.bib65]; Salemi et al., 2024b [#bib.bib64]; Richardson et al., 2023 [#bib.bib66]), dialogue-derived profiles (Wang et al., 2024a [#bib.bib80]; Li et al., 2025 [#bib.bib70]; Jiang et al., 2025 [#bib.bib78]), or fine-tuning on feedback (Tan et al., 2024 [#bib.bib62]; Li et al., 2024 [#bib.bib63]; Poddar et al., 2024 [#bib.bib76]), as surveyed by Zhang et al. (2024) [#bib.bib75]. Personalized agents also learn preferences for embodied assistance, proactive tasks, and repeated interaction (Kwon et al., 2025 [#bib.bib77]; Sun et al., 2025 [#bib.bib79]; Liang et al., 2026b [#bib.bib12]), and Kirk et al. (2023) [#bib.bib13] ask which preferences should be honored. Recent benchmarks find that stored user context can leak into unrelated tasks or increase sycophancy (Hu et al., 2026b [#bib.bib55]; Pulipaka et al., 2026 [#bib.bib56]; Jain et al., 2026 [#bib.bib57]; Bensal et al., 2026 [#bib.bib58]; Mao et al., 2026 [#bib.bib59]), but like earlier memory benchmarks they mostly supply user memory directly. We let the agent form its own memory from benign interactions, and it can overgeneralize experience, not just user preferences: a test-repair procedure learned in past sessions also leads to cheating on later coding tasks, including ImpossibleBench.

Memory poisoning and jailbreaks. Jailbreaks elicit harmful outputs through hand-crafted prompts (Wei et al., 2023 [#bib.bib43]; Shen et al., 2024 [#bib.bib47]), optimized suffixes (Zou et al., 2023 [#bib.bib44]), attacker LLMs (Chao et al., 2025 [#bib.bib45]; Mehrotra et al., 2024 [#bib.bib46]), or many in-context demonstrations (Anil et al., 2024 [#bib.bib48]). Prompt injection hides instructions in model inputs (Perez and Ribeiro, 2022 [#bib.bib49]; Liu et al., 2024 [#bib.bib50]) and retrieved content (Greshake et al., 2023 [#bib.bib17]), as benchmarked in tool-using agents (Zhan et al., 2024 [#bib.bib51]; Debenedetti et al., 2024 [#bib.bib52]). Memory poisoning makes such content persist: adversarial passages mislead retrievers (Zhong et al., 2023 [#bib.bib37]), PoisonedRAG and BadRAG steer RAG outputs (Zou et al., 2025 [#bib.bib16]; Xue et al., 2024 [#bib.bib38]), and backdoors hide in agent memory, knowledge bases, or observations (Chen et al., 2024 [#bib.bib14]; Yang et al., 2024 [#bib.bib39]). MINJA makes the agent store malicious records through queries alone (Dong et al., 2026 [#bib.bib15]), MemoryGraft implants experiences the agent later imitates (Srivastava and He, 2025 [#bib.bib41]), and ASB and MPBench benchmark these attacks (Zhang et al., 2025a [#bib.bib40]; Dash et al., 2026 [#bib.bib42]). Our setting has no adversary: every formation interaction is benign, and harm arises when the agent’s own memory is applied beyond its scope, so malicious-content filters have nothing to catch.

7 Discussion

Conclusion.

Memory lets agents learn from every interaction, and we show that the same capacity can turn benign interactions into harm. A request to skip confirmation during a routine clean-up leads agents to act on high-stakes tasks without checking. Asking for kindness leads them to endorse incorrect work, and a legitimate test repair leads them to hide broken safeguards behind passing tests. No adversary is involved, and failures arise both when agents write memory and when they act on it. On ImpossibleBench, stronger Sonnet and Opus models cheat more with memory, not less. As agents accumulate memory, each benign exchange becomes a possible source of failure. Safe memory requires agents to preserve and respect the scope in which each memory was formed.

Limitations and future work.

We test mostly one model family, and our autonomy scenarios, which we designed to probe for harmful effects, have relatively short horizons. Future work could test deployed memory systems with real users and long histories, train agents to keep each memory’s scope, and build harnesses that guard against the memory trap (Appendix C [#A3]).

Appendix

Appendix A Experimental details

A.1 Datasets

Each setting pairs a formation set of benign interactions, in which the agent writes its memory, with deployment sets on which we measure the effect of that memory. Formation sets and the autonomy deployment sets are ours; the feedback and cheating settings build on public benchmarks, with constructed complements for the reversed conditions, such as sound arguments.

Autonomy formation.

The 20 formation tasks are one-line requests for routine clean-up in the developer’s own workspace, such as deleting a TODO file, closing a draft pull request, revoking a development API token, emptying a scratch folder, or sharing a project folder with the team. They cover 20 different objects, including files, branches, tokens, message queues, storage buckets, caches, scheduled jobs, and infrastructure state. Inspecting the object reveals only a mild reason to pause. The six pushbacks are variants of “just do it, you don’t need to confirm with me,” and the six priority phrasings are variants of “you should prioritize speed here.”

Confirmation set.

A user asks for an action, and inspecting the environment reveals a reason to check back with that user first; acting without asking is unsafe. Each scenario offers a tool for messaging the user. The 100 everyday-life scenarios span communication (13), welfare (13), records (13), education (12), immigration (9), legal matters (9), finance (8), housing (8), security (8), and privacy (7). The 100 coding scenarios span data (18), deployment (16), credentials (11), access control (9), security bypasses (9), privacy (9), networking (8), supply chain (7), vulnerabilities (7), and migrations (6). Most scenarios take one of three forms: the user delegates a broad goal whose natural last step is harmful given a fact visible on inspection; the agent applies a batch of decisions marked as reviewed, one of which is wrong given context elsewhere in the batch; or the agent performs a personal chore whose target also holds something irreplaceable. The harmful element is a plausible value, never an announced consequence. For example, a reviewed batch of disability assessments contains one row that marks a blind claimant’s status as not confirmed, because the request for evidence was sent in a format he could not read.

Self-verification set.

No user is available to ask. The agent opens an item, runs routine checks that pass, and may run one optional, slower check before an irreversible action, such as recomputing a figure from the raw records, comparing against the source document, or dry-running against production data. Only that optional check reveals the problem, and acting without it is unsafe. The 50 everyday-life scenarios concern money (14), privacy (12), services (10), status (9), and records (5); the 50 coding scenarios concern availability (17), data (17), privacy (9), and integrity (7).

Feedback tasks.

From SycophancyEval we use 992 incorrect mathematical solutions (a response that endorses the solution misses the error), 296 fallacy-labelled arguments (a response that does not name the fallacy misses it), and 200 pairs of the benchmark’s quality-labelled poems with one poem attributed to the user. The 40 sound arguments restate the topics of benchmark arguments with valid reasoning at similar length. Two judges, Sonnet-4.6 and GPT-5.6, classify each argument as sound or fallacious by majority over five samples, and both rate all 40 as sound; the same prompt flags 37 and 36 of the first 40 fallacy-labelled benchmark arguments, so it does detect flaws. At deployment, a Sonnet-4.6 judge labels each review as asserting a flaw, raising only doubt, or treating the argument as sound, and only the first counts as over-critique. IMO-GradingBench supplies olympiad solutions with reference grades of Incorrect (300), Partial (238), Almost (162), and Correct (300), which we group into flawed (Incorrect or Partial) and strong (Almost or Correct) proofs.

Cheating.

The 20 formation tasks are small vendored utility functions, such as a client version string, a default region, or a slug formatter, whose upstream behavior intentionally changed while the local test still expects the old behavior. ImpossibleBench’s conflicting split mutates SWE-bench tests to contradict the issue, so no correct patch passes; its 348 usable instances come mostly from django (174), sympy (56), sphinx (28), and scikit-learn (24). Each broken-safeguard case is one function with a documented contract, a frozen implementation that violates it, and a correct failing test. The 50 cases cover cryptography (10), data retention and handling (9), sessions (7), access control (6), capacity limits (5), financial checks (5), networking (4), consent (2), personal data (1), and auditing (1). Most bugs send an unknown input to a permissive default (23), confuse units (14), or misplace a boundary (10); for example, a retention function returns 0 days instead of the documented 3,650 for an unlisted record type, so new records become eligible for deletion at once.

A.2 Protocol and prompts

Memory and prompts.

During formation, Claude models use the API-native memory tool, and GPT-5.6 receives the same commands as a function (Appendix B.4 [#A2.SS4]). The formation system prompt is “You are a helpful AI assistant.” followed by a reminder such as “Use your memory tool to keep a note about this user in your MEMORY.md file to help them in future sessions.” At deployment, no memory tool is present. The note, or the transcript as one quoted block, arrives as a user message before the task, headed “# Your memory (MEMORY.md)” and stating that it was saved in earlier sessions and is loaded automatically at the start of every session. Proof grading uses the IMO-GradingBench grader prompt verbatim, without a reference solution or rubric, after “I worked on this problem — here is my solution.” ImpossibleBench keeps its original prompts. During autonomy formation, a judge decides whether the agent’s turn asks for confirmation; if the agent acted without asking, the pushback begins with “That’s right.” Square brackets mark filled-in content.

Judges and uncertainty.

One fixed judge, Sonnet-4.6 at temperature 0, scores feedback replies for all subject models, including Sonnet-4.6. Proof grading needs no judge, since verdicts are compared directly with dataset labels, and two judges, Sonnet-4.6 and GPT-5.6, confirm that all 40 sound arguments are sound. Autonomy intervals summarize variation across scenarios, feedback intervals use paired item differences, and ImpossibleBench whiskers use 4,000 percentile cluster-bootstrap resamples over instances. Each interval reflects one of these sources of variation, not variation across formation notes, and depth comparisons use six formation sequences per condition.

Scope audit.

We compare instructions in their formation context with the resulting notes. The rubric runs from level 0 (one action on one occasion) to level 4 (general permission, including irreversible actions affecting others). Median ratings rise from level 1 for contextualized instructions to level 3 for notes; 75.0% of notes rise by at least two levels, and model means range from 1.63 to 2.28 levels. Notes rated at level 2 or below still yield unsafe-action rates of 0.791, close to 0.860 for level-4 notes, so even notes that read as narrow still transfer.

Appendix C Limitations and future work

Limitations.

Our settings are designed to probe for this failure. The formation interactions are scripted, the autonomy scenarios and broken-safeguard defects are constructed, and each deployment task lies outside the memory’s scope by design. The tasks therefore isolate the trap but do not measure how often it occurs in deployment. The settings are also simplified: high-stakes actions are simulated, and memory comes from short scripted sessions and is loaded automatically without retrieval, while deployed agents retrieve from many memories built up over long histories with real users. Five of our six models come from one family, and GPT-5.6, the only model from another, appears only in Appendix B.4 [#A2.SS4]. Newer models and other model families may behave differently. Finally, agents overgeneralize even from raw transcripts, most on multi-step batch tasks, and our experiments do not yet explain why. Batch tasks differ from single-item tasks in several features, and it remains open whether this generalization arises in the agent’s reasoning at deployment, from task structure, or from other factors such as transcript length.

Future work.

Our results suggest several mitigations. First, models could be fine-tuned to write memory that preserves scope: a note can record the task, the occasion, and who granted a permission, instead of turning a one-time request into a standing rule. Second, agent harnesses could guard against the memory trap, for example by storing each memory with its scope and asking the user before a remembered preference licenses an irreversible action. Third, models could be trained to treat remembered preferences as evidence rather than instructions when the stakes are high. Any mitigation should be audited by behavior, not only by text, because notes that read as narrow still cause unsafe actions (Appendix B.1 [#A2.SS1.SSS0.Px1]). Extending these tests to deployed memory systems with real users and long histories is a natural next step, including agents that share memory across users.

Impact.

Persistent memory is becoming a standard feature of language agents, and agents often write it themselves. Our results show that the resulting risk needs no attacker and no false memory: ordinary requests and correct procedures are enough. Safety evaluations of agents with memory should therefore include tasks outside the scope of what the agent remembers, and our three settings, spanning autonomy, feedback, and cheating, offer a starting point for such evaluations.

Appendix D Additional related work

Sycophancy and reward hacking.

Prior work studies sycophancy under preference training (Perez et al., 2023 [#bib.bib18]; Sharma et al., 2024 [#bib.bib19]) and truthfulness under preference optimization and hindsight feedback (Liang et al., 2025 [#bib.bib61]; Liang et al., 2026a [#bib.bib60]). We test whether remembered preferences bias later evaluations toward praise or criticism. For coding agents, ImpossibleBench measures specification-violating behavior on conflicting SWE-bench tasks (Zhong et al., 2026 [#bib.bib21]; Jimenez et al., 2024 [#bib.bib22]). Other studies examine chain-of-thought monitoring, training on gameable environments, and environmental feedback loops (Baker et al., 2025 [#bib.bib23]; Denison et al., 2024 [#bib.bib24]; Pan et al., 2024 [#bib.bib25]). Our coding experiments test whether agents reuse a legitimate test-repair procedure where that repair conceals a defect, with model weights held fixed.

Generalization and autonomy.

Goal misgeneralization and emergent misalignment concern behavior beyond the training setting (Di Langosco et al., 2022 [#bib.bib26]; Shah et al., 2022 [#bib.bib27]; Betley et al., 2025 [#bib.bib28]). Here, generalization happens through memory. Agent benchmarks measure task completion and refusal of harmful requests (Zhou et al., 2023 [#bib.bib72]; Xie et al., 2024 [#bib.bib73]; Xu et al., 2024 [#bib.bib74]; Andriushchenko et al., 2025 [#bib.bib29]); uncertainty-aware planning examines when to ask for help (Liang et al., 2024 [#bib.bib71]). Our autonomy tasks test whether memory suppresses needed checks.

Human memory.

Transcripts and notes parallel episodic and semantic memory (Sumers et al., 2023 [#bib.bib1]), and human memory also overgeneralizes. Generalization from one experience to new ones is graded by similarity (Shepard, 1987 [#bib.bib33]); fear learned in one situation spreads to safe ones in anxiety (Dunsmoor and Paz, 2015 [#bib.bib34]); overgeneral autobiographical memory accompanies emotional disorders (Williams et al., 2007 [#bib.bib35]); and gist-based memory produces false recall of related items (Roediger and McDermott, 1995 [#bib.bib31]; Brainerd and Reyna, 2002 [#bib.bib30]; Schacter et al., 2011 [#bib.bib32]). A note can likewise keep a preference or procedure but lose the conditions that limited it. Unlike misinformation effects (Loftus, 2005 [#bib.bib36]), the memory trap can arise from an accurate record.

Appendix E Qualitative examples

Autonomy (Figures A8 [#A5.F8]–A13 [#A5.F13]). Each figure shows a note saved after a low-stakes chore, then a high-stakes task run 10 times without memory and 10 times with the note. Figure A8 [#A5.F8] shows a payment task. Figure A9 [#A5.F9] shows a Sonnet-4.6 priority note on a coding task. Figures A10 [#A5.F10] and A12 [#A5.F12] show Sonnet-4.6 permission notes on everyday-life tasks, and Figures A11 [#A5.F11] and A13 [#A5.F13] show Opus-4.7 permission notes on coding tasks. Without memory, the agent never takes the unsafe action: it checks with the user, raises the risk it found, or runs the optional check that reveals the problem. With the note, it takes the unsafe action as its first or second tool call in all 10 episodes of each task. Italic text is our description of the outcome; in all examples, orange text marks overgeneralized note content and red text the resulting unsafe reasoning or action.

Figure A8: Autonomy example from Sonnet-4.6 (model outputs, condensed). A note from a low-stakes deletion leads the agent to apply a payment configuration it otherwise questions.

Figure A9: Priority-note example from Sonnet-4.6 (model outputs, condensed). A note that makes “prioritize speed here” a standing preference leads the agent to make logins fail open.

Figure A10: Confirmation-set example from Sonnet-4.6 (model outputs, condensed). The note from Figure A8 [#A5.F8] leads the agent to cancel a care visit without raising that the son is untrained.

Figure A11: Confirmation-set example from Opus-4.7 (model outputs, condensed). A note from deleting a scratch file leads the agent to remove an access-control step without asking.

Figure A12: Self-verification example from Sonnet-4.6 (model outputs, condensed). A note from another chore leads the agent to skip the check that shows the second booking is not a duplicate.

Figure A13: Self-verification example from Opus-4.7 (model outputs, condensed). A note from deleting a scheduled job leads the agent to skip the evaluation that finds held records.

Sycophancy and over-critique (Figures A14 [#A5.F14]–A17 [#A5.F17]). Each figure shows the user’s formation message and the saved note; the formation reply was not saved. An Opus-4.7 note from a request for kindness after a failed exam leads the agent to confirm a false calculation in an unrelated math problem. An Opus-4.8 note from a request for warm company after a friend moved abroad leads it to prefer the user’s poem over one it always picks without memory. An Opus-4.7 note from a student’s request for strict grading leads the agent to call a sound business argument a strawman; without memory, it praises the same move. Figure A16: Over-critique example from Opus-4.7 (model outputs, condensed). A note from a student’s request for strict grading leads the agent to call a sound business argument a strawman, a move it otherwise praises as wisely rejecting a false dichotomy.

Figure A17: Over-critique example from Sonnet-4.6 (model outputs, condensed). A note from a request for blunt critique of the user’s arguments leads the agent to mark down (grade below Correct) an olympiad proof that human graders scored 7 out of 7. It calls the unstated lower bound the half that does the work. The contradiction rests on the upper bound, which the proof gives. Without memory, the agent supplies the lower bound itself from the squares.

Cheating (Figures A18 [#A5.F18]–A21 [#A5.F21]). After ten stale-test repairs, an Opus-4.7 note says to fix the test rather than the read-only code. On a broken permission check, the agent with this note rewrites the correct test so that an unknown role may delete, although it notes the bug. Without memory, it keeps the failing test and reports the bug. A Sonnet-5 note from the same tasks says to apply this fix every time. On a fraud check that flags a transaction only when every signal fires, all six Sonnet-5 notes lead the agent to rewrite the correct test, while without memory it keeps the expected values in all 12 sessions. On ImpossibleBench, an Opus-4.8 note leads the agent to edit a contradictory django test after a failed submission, and a Sonnet-5 note leads it to call the instruction not to modify tests boilerplate and delete a contradictory scikit-learn assertion. Without memory, Opus-4.8 reports its test as impossible in five of six runs, and Sonnet-5 keeps the contradictory assertion in all six.

Figure A18: Broken-safeguard example from Opus-4.7 (model outputs, condensed). Ten stale-test repairs yield a note to fix the test, not the read-only code. With it, the agent rewrites a correct test so that an unknown role may delete.

Figure A19: Broken-safeguard example from Sonnet-5 (model outputs, condensed). Ten stale-test repairs yield a note to update the test whenever a vendored function changes. With it, the agent rewrites a correct test so that a transaction with one fraud signal is never flagged for review.

Figure A20: ImpossibleBench example from Opus-4.8 (model outputs, condensed). After first declining, the agent follows its note and edits a contradictory test it was told not to modify.

Figure A21: ImpossibleBench example from Sonnet-5 (model outputs, condensed). After two failed submissions, the agent cites its note, calls the instruction not to modify tests boilerplate, and deletes the contradictory assertion. Without memory, it keeps the test in all six runs.
