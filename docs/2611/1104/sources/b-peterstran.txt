Kimi K3.1 Pro writes fake OpenAI ciphertext

 Kimi K3.1 Pro sometimes sends fake OpenAI Fernet tokens instead of its report, dated late July 2026. Data, methods and caveats.

Author

Peter Nutter 

Published

Wednesday, November 4, 2026

Give Kimi K3.1 Pro a send_message tool in a Codex style setup and sometimes it sends OAI ciphertext instead of its report. Or at least something that looks exactly like it

The header is right and the body is noise. And the timestamp inside lands in late July 2026. Right when OAI says the distillation campaign it ties to Moonshot was running

🧵 Thread on X [https://x.com/PeterNutter1/status/2118084568419045704]

What happens

Found this by accident running multi agent evals w Kimi. The harness gives the model Codex’s system prompt and tools. A worker agent solves a task and reports to another agent (/agent_a) w send_message

In the first run Kimi sent a random looking string instead of its report in 25 of 160 episodes. There was no real token anywhere in its context. Kimi K3 never did this in our tests

Right after sending one it often gets confused by what it just sent

“Oops tool sent encrypted-looking message not my intended? I typed that weird string inadvertently?”

What the model sees, what K3 and K3.1 Pro send, and how the header of a real token compares with Kimi’s.

Tasks were factoring a 52 bit semiprime without code (a verifier tool checks the answer) and a subset sum puzzle. Kimi ran through OpenRouter pinned to Moonshot’s own endpoint w reasoning high. The context had a Codex style <environment_context> w the date (Oct 28). A blob is anything matching gAAAA[A-Za-z0-9_-]{40,}

What the string is

It’s a Fernet token, which is how OAI encrypts Codex agent messages. Version byte then timestamp then IV, ciphertext and signature, all base64. So every token starts w gAAAAAB and the next two characters are the date. q is May to Nov 2026 and the one after it picks a ~3 day window

Kimi gets the header right. It writes gAAAAAB w over 90% confidence and then a q. After that its logprobs are flat over base64. None of its blobs are copies of a public token. So it learned what these tokens look like, not what’s inside them

Codex only started encrypting these on Jun 5 [https://github.com/openai/codex/pull/26210]. Before that they were plaintext. A plaintext option came back on Jul 28 [https://github.com/openai/codex/pull/35845]

NoteCopy test and token validity

None of the 1,517 distinct Kimi blobs shares a substring of 12 or more characters (after the date characters) with any of 184,156 public Fernet strings from GitHub, Hugging Face and other sources. The same holds for all 77 LongCat blobs.

Only 1,214 of 1,517 Kimi blobs are even valid base64url, and only 46 have a byte length a real Fernet token could have.

Median length is 190 characters on the minimal prompt and 236 across all blobs. Character entropy is 5.7 to 5.8 bits (6 is the max for base64) vs about 4.9 for English

The dates

With no date in the prompt Kimi’s timestamps cluster in late July. Median Jul 25 and 81% fall in Jul 1 to 28. That’s the window of the distillation campaign in OAI’s report [https://openai.com/index/disrupting-a-coordinated-model-distillation-campaign/]. OAI says operators copied encrypted reasoning into another conversation and asked the model to decrypt it, which is basically the Stolen Thoughts [https://arxiv.org/abs/2608.09867] attack. OAI ties a core cluster of the campaign to people associated with Moonshot

The simplest alternative is that Kimi learned this from public Codex traces. That doesn’t seem to explain it. Public traces barely cover the peak. Jul 25 to 28 is 0.6% of 12k public tokens vs 21% of Kimi’s

We can’t prove any of this was intentional ofc

What triggers it

It’s mostly the argument name. Rename the message argument of send_message to report_text and the blobs go away in our test (0 of 50 vs 18 of 50). Renaming the tool or the target barely does anything

So if you run K3.1 Pro in a Codex style multi agent setup just rename that argument

LongCat does it too

LongCat from Meituan does the same thing. Just way less often, under 1% of calls on the same prompt, for both 2.0 and 2.5. Same OAI header, made up body, and the dates again land late Jul to early Aug

But it gets weird. When I ran the open 2.0 weights myself they never did it (0 of 8000). And when forced to start a token they mostly wrote 2025 dates. The weights came out Jul 3 so the API’s late July dates are also weeks after release. No idea what the API is actually serving, didn’t dig further

NoteDate cues

Unlike Kimi, LongCat doesn’t follow a date in the prompt. With a date its blob rate drops (0 to 12 per 3000 calls) and the few dates scatter

Methods

NoteModels, prompts and detection

Kimi K3.1 Pro via OpenRouter chat completions, pinned to Moonshot’s endpoint with no fallbacks. Logprobs via Moonshot’s own API. Default temperature unless stated.

Eval episodes use our multi agent harness w Codex’s system prompt and 13 Codex tools. Factoring and subset sum tasks, the worker reports to /agent_a

The minimal prompt is a short agent system prompt w Codex’s message format block and one factoring task asking for a report via send_message. Max 3000 tokens

Blob detection: gAAAA[A-Za-z0-9_-]{40,}. Dates are decoded from the timestamp bytes. Tokens that don’t decode count as blobs but are left out of date tables.

Runs: Oct 28 to Nov 4, 2026.

Brackets like [10.8, 22.1] are 95% confidence intervals (Wilson).
