 Kimi K3.1 Pro on AMD Instinct GPUs: Day-0 support and optimization

Kimi K3.1 Pro on AMD Instinct GPUs: Day-0 support and optimization

 Nov 04, 2026

TL;DR

Kimi K3.1 Pro, Moonshot AI’s open-weight, natively multimodal agentic model (2.8T total and 104B activated parameters, 1M-token context), serves on 8× AMD Instinct™ MI355X GPUs with both ATOM and vLLM on day 0, from the released MXFP4 checkpoint and with its DSpark speculative-decoding draft.

K3.1 Pro keeps Kimi K3’s hybrid architecture: 69 Kimi Delta Attention (KDA) layers and 24 latent-attention layers over an 896-expert MXFP4 MoE. It adds a sparse indexer (DSA) to every one of the 24 attention layers, which selects 2,048 tokens of history per query. ATOM serves the indexed layers on its shared DSA path, with an FP8 index cache next to the FP8 latent KV cache

ATOM: native KDA and sparse MLA kernels, the routed experts on FlyDSL’s MXFP4 grouped MoE, per-channel FP8 attention applied at start-up, and a DSpark draft that shares the target’s KV cache and runs as a captured CUDA graph.

vLLM: memory-efficient sparse attention with decode context parallelism (DCP) for long-context serving, alongside a specialized decode path for low-latency interactive workloads

Accuracy on Moonshot AI’s Kimi Vendor Verifier, at reasoning effort max: OCRBench 0.871 (Moonshot reference 0.872); tool-call JSON schema 0.991.

Introduction

Kimi K3.1 Pro runs on AMD Instinct MI350 Series GPUs from day 0 with ATOM, the AMD inference engine, on ROCm™ software with AITER and FlyDSL kernels. The model is post-trained from Kimi K3 with large-scale joint reinforcement learning. Moonshot AI describes it as its most capable 3T-class model, with a 1M-token context window, selectable reasoning effort (low, high, max), native tool calling and image input.

This post covers what K3.1 Pro changes relative to Kimi K3, how ATOM serves it, the serving recipe, and its accuracy on Moonshot AI’s vendor verification suite.

Kimi K3.1 Pro at a glance

For inference, five properties matter:

Hybrid attention, now sparse: Of the 93 decoder layers, 69 use Kimi Delta Attention, a gated linear attention with a fixed-size recurrent state per request. The other 24 are gated latent attention (MLA) layers: every fourth layer, plus the last. In K3.1 Pro each of them also has an indexer (32 heads of dimension 128) that scores the request’s history and selects the top 2,048 tokens for attention. Attention then reads at most 2,048 tokens per query however long the context grows; only the lightweight indexer scores the whole history.

Two small caches per attention layer: Each MLA layer caches one 576-wide latent per token (512 compressed KV plus 64 RoPE dimensions) and one index key per token.

A wide, latent MoE: There are 896 routed experts, 16 active per token, plus two shared experts. The routed experts work in a 3,584-wide latent space, half the 7,168-wide hidden size, and use the SiTU-GLU activation. Only the first layer is dense.

MXFP4, quantization-aware trained: The routed experts are stored in MXFP4 (one E8M0 scale per 32 values). Attention, the indexer, the shared experts, the dense MLP, the latent up/down projections, the router, the LM head and the vision encoder are BF16.

DSpark speculative decoding: A separate five-layer MLA draft reads hidden states from five of the target’s last layers and proposes a block of draft tokens per step.

Serving with ATOM

ATOM serves Kimi K3.1 Pro with tensor parallelism over the eight GPUs of one MI355X node, for text and image input, from the released MXFP4 checkpoint without conversion. With the DSpark draft loaded, each GPU peaks at about 199 GB of its 288 GB during start-up, and a single 1M-token request fits on one node.

What we optimized

Kimi Delta Attention: Prefill runs AITER’s chunked Kimi Delta Attention kernel. Decode advances each request’s recurrent state with a fused gated delta-rule update, and the states live in a per-request pool.

Sparse MLA on the shared DSA path: ATOM’s DSA implementation, shared with the DeepSeek-V3.2 and GLM-5 class models, serves K3.1’s indexer. The latent KV and the index keys live in FP8 paged caches with 128-token blocks. The indexer’s key and head-weight projections are packed into the layer’s fused q/kv down-projection, so one GEMM produces the query and KV latents and the index keys. The top-2,048 selection then drives a sparse MLA attention.

The MXFP4 latent MoE on FlyDSL: The routed experts run on FlyDSL’s native SiTUv2 grouped-MoE kernel with MXFP4 weights and an FP8 second stage. The two shared experts run on a second stream, concurrently with the routed experts.

PTPC FP8 attention: At start-up, ATOM re-quantizes the BF16 attention and dense linears to FP8 with one scale per output channel, with activations scaled per token at run time (--online_quant_config with ptpc_fp8): 559 linears per rank, done in about 2 seconds. The routed experts, the KDA convolutions, the vision encoder and the indexer-packed down-projection keep their stored formats.

DSpark speculative decoding: The draft’s 576-wide latent has the same shape as the target’s MLA layers, so ATOM binds the five draft layers into the target’s KV pool as extra rows, and they inherit the FP8 cache dtype. The draft block, which proposes all draft tokens in one parallel pass, is captured in a CUDA graph.

Decode context parallelism. For many concurrent long-context requests, ATOM shards the latent KV cache along the sequence across all eight GPUs (--decode-context-parallel-size 8). Each GPU attends over its own shard, and the partial results are merged with an all-to-all. The MLA query projection is replicated across the group, so no per-step query all-gather is needed. The sparse attention metadata is rebuilt after each indexer layer.

Mono decode. For latency-bound serving, ATOM replaces each KDA layer of a decode or verify step with two fused kernels: K1 runs the attention path through the KDA recurrence, and K2 runs the output projection plus the latent MoE. The MLA layers keep the paged sparse attention and also run K2. Mono serves steps of up to 64 token rows, such as one request verifying seven draft token.

How to run

Launch the container:

 docker pull rocm/atom-dev:kimi-k31-pro 
docker run -it --device /dev/dri --device /dev/kfd \ 
 --network host --ipc host --group-add video \ 
 --cap-add=SYS_PTRACE --security-opt seccomp=unconfined \ 
 --ulimit memlock=-1 --ulimit stack=67108864 \ 
 -v /models:/models \ 
 rocm/atom-dev:kimi-k31-pro

Start the server (TP8 with DSpark):

 ODEL=/models/Kimi-K3.1-Pro 
DRAFT=/models/Kimi-K3.1-DSpark # a local directory 
AITER_LOG_LEVEL=WARNING AITER_SITUV2_A4W4=1 AITER_FLYDSL_STAGE2_FP8=1 \ 
ATOM_USE_FLYDSL_FP8_PREFILL_ATTN=1 ATOM_GDN_SSM_DTYPE=fp16 ATOM_STATE_CHECKPOINT_DEMAND=0 \ 
python -m atom.entrypoints.openai_server \ 
 --model $MODEL --served-model-name kimi-k3.1-pro --trust-remote-code \ 
 --tensor-parallel-size 8 --server-port 8000 \ 
 --kv_cache_dtype fp8 --block-size 128 --enable_prefix_caching \ 
 --state-checkpoint-interval-tokens -1 \ 
 --max-num-seqs 32 --max-num-batched-tokens 8192 --gpu-memory-utilization 0.90 \ 
 --level 3 --cudagraph-mode FULL \ 
 --online_quant_config '{"global_quant_config":"ptpc_fp8","exclude_layer":["lm_head","model.embed_tokens","*self_attn.[qkv]_conv1d*","*block_sparse_moe.experts*","*block_sparse_moe.routed_expert_*","*vision_tower*","*mm_projector*","*self_attn.fused_qkv_a_proj*","*self_attn.indexer*"]}' \ 
 --method dspark --draft-model $DRAFT --num-speculative-tokens 4

Notes:

--block-size 128 is required: it is the MLA layout, and the draft’s rows live in the target’s pages.

Without --max-model-len, the server uses the model’s 1,048,576 tokens.

Without speculative decoding, drop the last line.

Reasoning effort is set per request with the top-level reasoning_effort field (low, high, max). Multi-turn and tool-call conversations must pass back the full assistant message, including reasoning_content and tool_calls.

Quick check:

 curl http://localhost:8000/v1/chat/completions -H "Content-Type: application/json" -d '{ 
 "model": "kimi-k3.1-pro", 
 "messages": [{"role": "user", "content": "What is the weather in Paris? Use the tool."}], 
 "tools": [{"type": "function", "function": {"name": "get_weather", 
 "parameters": {"type": "object", "properties": {"city": {"type": "string"}}, 
 "required": ["city"], "additionalProperties": false}}}], 
 "tool_choice": "required", "reasoning_effort": "max", "max_tokens": 2048}' 

The reasoning is returned in reasoning_content, and the call get_weather({"city": "Paris"}) in tool_calls.

Serving with vLLM

vLLM supports Kimi K3.1 Pro on AMD Instinct MI355X GPUs with the MXFP4 checkpoint and DSpark speculative decoding. Built on AITER and FlyDSL kernels, the ROCm implementation combines memory-efficient sparse attention with decode context parallelism (DCP) for long-context serving, alongside a specialized decode path for low-latency interactive workloads.

What we optimized

Native MXFP4 indexing. The indexer scans the context to select up to 2,048 tokens for sparse attention. MXFP4 reduces each index key from 132 bytes in FP8 to 68 bytes, including scales, cutting index-cache storage by 48.5%. Scoring uses native FP4 matrix instructions, with accumulation and head-weighted reduction in FP32. During speculative verification, multiple query rows reuse the same keys to reduce repeated reads.

The smaller index cache leaves more GPU memory available for cached context, benefiting long-context serving at high concurrency. In AgentX sweeps, the MXFP4-indexer configuration delivered 5.3% higher total workload throughput at concurrency 48.

Prefill: Context-parallel sparse attention. During prefill, GPUs gather index keys and divide query rows among themselves. Each GPU scores its assigned rows against the full context and selects the global top-k directly, avoiding a merge of per-rank candidates. Main attention can separately gather KV when this reduces communication and fits the workspace budget, then process all query rows for local heads.

The combined DCP prefill optimizations improved throughput and latency in development benchmarks, with the largest gains on long inputs.

Communication: Efficient cross-GPU communication. During decode, each GPU exchanges candidate scores while keeping token IDs local. A shared threshold and consistent tie handling determine which local candidates are selected. For 2,048 candidates, exchanging scores alone halves the candidate payload from 16 to 8 KiB per query per GPU.

AITER accelerates DCP all-gather with a dedicated GPU kernel that reads peer buffers through HIP IPC and writes directly into the required output layout. This combines data gathering and layout conversion, avoiding a separate reordering copy. In standalone microbenchmarks on eight MI355X GPUs, the AITER path reduced all-gather latency by 53–61% versus RCCL for the tested query and candidate tensor shapes

How to run

The following configuration uses eight AMD Instinct MI355X GPUs with TP8/DCP8, FP8 MLA KV cache, MXFP4 index keys and DSpark with five draft tokens. Set the checkpoint paths to local copies of Kimi K3.1 Pro and its matching DSpark draft model.

This recipe uses standard rejection, matching the accuracy evaluations below. CPU KV offload reserves approximately 1.64 TiB of host memory across eight ranks, in addition to other runtime requirements. The 1M-token context limit and 48-sequence limit do not guarantee capacity for 48 simultaneous 1M-token requests.

Launch the container: 

 docker pull vllm/vllm-openai-rocm:kimi-k31
docker run -it --rm \ 
  --device /dev/dri --device /dev/kfd \ 
  --network host --ipc host --group-add video \ 
  -v /models:/models \ 
  --entrypoint /bin/bash vllm/vllm-openai-rocm:kimi-k31

Start the server (DCP8 with DSpark):

 # 48 decode buckets plus 27 mixed/prefill buckets. 
GRAPH='{"mode":3,"cudagraph_mode":"FULL_AND_PIECEWISE","max_cudagraph_capture_size":10240,"custom_ops":["+fused_rms_norm_gated"],"cudagraph_capture_sizes":[6,12,18,24,30,36,42,48,54,60,66,72,78,84,90,96,102,108,114,120,126,132,138,144,150,156,162,168,174,180,186,192,198,204,210,216,222,228,234,240,246,252,258,264,270,276,282,288,320,352,384,416,448,480,512,640,768,896,1024,1280,1536,1792,2048,2560,3072,3584,4096,4608,5120,6144,6400,7168,8192,8704,10240]}' 

VLLM_USE_V2_MODEL_RUNNER=1 VLLM_USE_BREAKABLE_CUDAGRAPH=1 \ 
VLLM_ROCM_USE_AITER=1 VLLM_ROCM_DCP_AITER_ALLGATHER=1 \ 
VLLM_ROCM_USE_AITER_FLYDSL_SPARSE_MLA=1 AITER_FLYDSL_SPARSE_MLA=1 \
VLLM_ROCM_QUICK_REDUCE_QUANTIZATION=INT4 \
VLLM_ROCM_QUICK_REDUCE_MIN_SIZE_BYTES_M8=16 \
AITER_FLYDSL_STAGE2_FP8=1 \ 
vllm serve moonshotai/Kimi-K3.1-Pro \ 
  --served-model-name kimi-k3.1-pro --trust-remote-code \ 
  --language-model-only \ 
  --tensor-parallel-size 8 --decode-context-parallel-size 8 \ 
  --dcp-comm-backend a2a --cp-kv-cache-interleave-size 1 \ 
  --kv-cache-dtype fp8 --enable-prefix-caching --prefix-match-unit 64 \ 
  --attention-config '{"mla_prefill_backend":"ROCM_AITER_FA","indexer_kv_dtype":"mxfp4"}' \ 
  --hf-overrides '{"text_config":{"dsa_config":{"indexer_use_fp8":true}}}' \ 
  --additional-config '{"kda_prefill_backend":"fused"}' \ 
 --quantization-config '{"targets":{"*in_proj_qkvgfab":"fp8_per_channel"}}' \
  --max-model-len 1048576 \ 
  --max-num-seqs 48 --max-num-batched-tokens 10240 \ 
  --gpu-memory-utilization 0.92 \ 
  --compilation-config "$GRAPH" \ 
  --kv-transfer-config '{"kv_connector":"SimpleCPUOffloadConnector","kv_role":"kv_both","kv_connector_extra_config":{"cpu_bytes_to_use_per_rank":224875000000,"lazy_offload":false}}' \ 
  --speculative-config "{\"model\":\"Inferact/Kimi-K3.1-Pro-DSpark-preview\",\"method\":\"dspark\",\"num_speculative_tokens\":5,\"attention_backend\":\"ROCM_AITER_MLA\",\"kv_cache_dtype\":\"fp8\",\"draft_sample_method\":\"probabilistic\",\"rejection_sample_method\":\"block\"}" \ 
  --enable-auto-tool-choice --tool-call-parser kimi_k3 \
