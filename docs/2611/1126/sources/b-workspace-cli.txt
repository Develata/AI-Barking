 Use the Google Workspace command-line interface (CLI)

 Stay organized with collections

 Save and categorize content based on your preferences.

Learn how to install, configure, and use the Google Workspace command-line
 interface (CLI).

The Google Workspace command-line interface, gwscli, is a unified
terminal client that connects AI agents such as Claude Code, Codex, and
Antigravity [https://antigravity.google/] to Google Workspace services. After you
install the CLI, connect your account, and install the packaged agent skills,
your agent runs the appropriate commands when you make requests in plain
language. The CLI also supports developers working directly in an interactive
terminal.

You can authenticate interactively with a Google Account or pass an existing
OAuth or domain-wide delegation access token. When accessing data in a
Google Workspace organization, all actions follow the organization's
administrator access and security policies. For details, see
Set up authentication [#authentication].

Because the CLI discovers commands, parameters, and schemas dynamically at
runtime, command interfaces and output schemas might change without backward
compatibility. Don't rely on fixed command signatures in static scripts.

The CLI provides the following features:

Dynamic runtime command discovery and schema inspection for AI agents

Structured JSON output for automated data processing

Packaged agent skills that provide domain context and safety guidance

Built-in human-in-the-loop verification for sensitive actions

What your agent can do

The command-line interface supports the following Google Workspace
services and actions. For the full list of commands, see
Complete command reference [#all-commands].

Example agent prompts

After you complete setup and install the agent skills, you can ask your AI
agent questions and tasks in plain language, such as:

"What's on my calendar for the rest of today?"

"Summarize my unread email from this week and create a draft reply to my
manager proposing Tuesday."

"Find my docs about the Q3 plan and list the open action items."

"Add the open action items from my Q3 plan doc to my Tasks
list."

Prerequisites

Before installing the command-line interface, verify the following
requirements:

An environment running Linux, macOS, or Windows on x86_64 or ARM64.

A Google Cloud project. To create a project, see
Create a Google Cloud project [/workspace/guides/create-project]. If
your organization administrator doesn't allow users to create new projects,
you might encounter a resourcemanager.projects.create permission error. Use
an existing project or see Troubleshooting [#troubleshooting].

On Linux or macOS, curl for the quick-install script, or another HTTP
download tool such as wget for manual downloads. On Windows, PowerShell.

Depending on your setup, you might also need the following:

The Google Cloud CLI if you enable services from the command line
during manual setup. To install it, see
Install the Google Cloud CLI [https://cloud.google.com/sdk/docs/install].

If running Chat write commands such as
gwscli chat send_message, gwscli chat mark_as_read,
gwscli chat mark_as_unread, or gwscli chat update_notification_settings,
a Google Workspace account and a configured
Chat app in your Google Cloud project. For
setup steps, see
Configure the Google Chat API [/workspace/chat/configure-chat-api].

Note: Using gwscli incurs no separate tool charge. Requests count toward
your Google Cloud project's Google Workspace usage tier and
quotas. For details on usage tiers, limits, and pricing, see the
Google Workspace usage tiers and quotas [/workspace/tools-safety]
documentation.

Install the command-line interface

Install the command-line interface with the quick-install script, or download
the prebuilt binary manually for your operating system and CPU architecture.

Quick install

Linux and macOS

curl -fsSL https://dl.google.com/workspace-cli/install.sh | bash

Installs to ~/.local/bin. To change this, set GWSCLI_INSTALL_DIR.

Windows

In PowerShell:

iex ((New-Object Net.WebClient).DownloadString('https://dl.google.com/workspace-cli/install.ps1'))

Installs to $HOME\bin and adds it to your user PATH. To change the
install directory, set $env:GWSCLI_INSTALL_DIR.

Manual install

Download the prebuilt binary and documentation assets for your operating
system and CPU architecture.

Linux x86_64

Run the following commands to download the Linux x86_64 binary and assets,
and make the binary executable:

mkdir -p ~/.gwscli
curl -fsSL https://dl.google.com/workspace-cli/linux/gwscli \
 -o /usr/local/bin/gwscli
curl -fsSL https://dl.google.com/workspace-cli/README.md \
 -o ~/.gwscli/README.md
curl -fsSL https://dl.google.com/workspace-cli/NOTICES.txt \
 -o ~/.gwscli/NOTICES.txt
chmod +x /usr/local/bin/gwscli

Linux ARM64

Run the following commands to download the Linux ARM64 binary and assets,
and make the binary executable:

mkdir -p ~/.gwscli
curl -fsSL https://dl.google.com/workspace-cli/linux_arm64/gwscli \
 -o /usr/local/bin/gwscli
curl -fsSL https://dl.google.com/workspace-cli/README.md \
 -o ~/.gwscli/README.md
curl -fsSL https://dl.google.com/workspace-cli/NOTICES.txt \
 -o ~/.gwscli/NOTICES.txt
chmod +x /usr/local/bin/gwscli

macOS Apple silicon

Run the following commands to download the macOS binary for Apple silicon,
grant execute permissions, and clear the quarantine attribute:

mkdir -p ~/.gwscli
curl -fsSL https://dl.google.com/workspace-cli/macos_silicon/gwscli \
 -o /usr/local/bin/gwscli
curl -fsSL https://dl.google.com/workspace-cli/README.md \
 -o ~/.gwscli/README.md
curl -fsSL https://dl.google.com/workspace-cli/NOTICES.txt \
 -o ~/.gwscli/NOTICES.txt
chmod +x /usr/local/bin/gwscli
xattr -d com.apple.quarantine /usr/local/bin/gwscli

macOS Intel

Run the following commands to download the macOS binary for Intel processors,
grant execute permissions, and clear the quarantine attribute:

mkdir -p ~/.gwscli
curl -fsSL https://dl.google.com/workspace-cli/macos_intel/gwscli \
 -o /usr/local/bin/gwscli
curl -fsSL https://dl.google.com/workspace-cli/README.md \
 -o ~/.gwscli/README.md
curl -fsSL https://dl.google.com/workspace-cli/NOTICES.txt \
 -o ~/.gwscli/NOTICES.txt
chmod +x /usr/local/bin/gwscli
xattr -d com.apple.quarantine /usr/local/bin/gwscli

Windows x86_64

Run the following commands in PowerShell to download the Windows x86_64
binary and assets. Invoke curl.exe explicitly because curl is an alias
for Invoke-WebRequest in PowerShell:

New-Item -ItemType Directory -Force -Path "$HOME\bin", "$HOME\.gwscli"
curl.exe -fsSL https://dl.google.com/workspace-cli/windows/gwscli.exe `
 -o "$HOME\bin\gwscli.exe"
curl.exe -fsSL https://dl.google.com/workspace-cli/README.md `
 -o "$HOME\.gwscli\README.md"
curl.exe -fsSL https://dl.google.com/workspace-cli/NOTICES.txt `
 -o "$HOME\.gwscli\NOTICES.txt"

Windows ARM64

Run the following commands in PowerShell to download the Windows ARM64 binary
and assets. Invoke curl.exe explicitly because curl is an alias for
Invoke-WebRequest in PowerShell:

New-Item -ItemType Directory -Force -Path "$HOME\bin", "$HOME\.gwscli"
curl.exe -fsSL https://dl.google.com/workspace-cli/windows_arm64/gwscli.exe `
 -o "$HOME\bin\gwscli.exe"
curl.exe -fsSL https://dl.google.com/workspace-cli/README.md `
 -o "$HOME\.gwscli\README.md"
curl.exe -fsSL https://dl.google.com/workspace-cli/NOTICES.txt `
 -o "$HOME\.gwscli\NOTICES.txt"

If /usr/local/bin requires elevated permissions on Linux or macOS, download
the binary to a writable folder on your PATH, such as ~/.local/bin or
~/bin. On Windows, make sure $HOME\bin is included in your PATH.

Install with an AI agent

If you're working inside an AI coding agent, you can also download the agent
installation prompt and ask your agent to follow it:

curl -fsSL -O https://dl.google.com/workspace-cli/INSTALL_PROMPT.md

Complete interactive credential setup and sign-in yourself in your local
terminal rather than through your agent.

Verify the installation

After installing the binary, verify that the tool runs:

gwscli version

Set up authentication

The command-line interface uses OAuth 2.0 to authenticate requests. You can
authenticate with your own OAuth client ID or supply an existing OAuth access
token directly.

Interactive sign-in with gwscli auth login requires a web browser that can
reach localhost on the same machine running the CLI. Run interactive sign-in
from your local terminal, or see
Browser redirect requirements [#browser-redirect] for remote and headless
environments.

Option 1: Configure your own OAuth client

To allow the command-line interface to manage tokens and refresh sessions,
configure an OAuth client ID in your Google Cloud project. Run these
setup steps in your own terminal rather than through an AI agent because setup
and sign-in wait for interactive input.

Follow Quick setup: Personal mode [#personal-mode] to configure credentials
and sign in for a single-user project. For an existing or multi-user
Google Cloud project, complete Manual setup [#manual-setup] and then
continue to Sign in to services [#login].

Quick setup: Personal mode

Personal mode in the Google Cloud console creates a single-user OAuth 2.0 client
that works only for your Google Account, automatically enables core
Google Workspace services, and skips OAuth consent screen setup and
app verification.

Open the Google Cloud console personal mode setup page [https://console.cloud.google.com/auth/overview/personal?apis=ws,wsmcp,tasksmcp&clientType=desktop&isAgent=true].
This link pre-selects the required Google Workspace services,
desktop application type, and agent flag.

Select your Google Cloud project or create a new personal-mode
project.

If your organization administrator doesn't allow users to create new
projects, you might encounter the error You do not have the required
"resourcemanager.projects.create" permission to create projects in this
location. Select an existing project or see
Troubleshooting [#troubleshooting].

Click Create Client and download the client secret JSON file.

Register your credentials with the command-line interface:

gwscli auth setup

When prompted, enter the path to your downloaded client secret JSON file
and enter Y to confirm the registration.

Sign in to authorize services, starting with read-only scopes:

gwscli auth login --bundle=readonly

Open the printed URL in your browser to complete consent. To authorize
write access, run gwscli auth login <service> for a single service or
gwscli auth login for all services. For more scope options, see
Sign in to services [#login].

Manual setup

If you aren't using personal mode, complete all three manual setup steps in
your Google Cloud project before signing in.

Step 1: Enable the required services

Each command group requires enabling both the underlying product API and its
companion *mcp.googleapis.com service in your Google Cloud project,
except people, which uses people.googleapis.com for both.

To enable services only for specific products, pass the service names from the
Required project services column in
What your agent can do [#what-your-agent-can-do]. For example, to enable only
Drive:

gcloud services enable --project=PROJECT_ID \
 drive.googleapis.com drivemcp.googleapis.com

To enable all supported services at once, run:

gcloud services enable --project=PROJECT_ID \
 gmail.googleapis.com drive.googleapis.com docs.googleapis.com \
 sheets.googleapis.com slides.googleapis.com calendar-json.googleapis.com \
 chat.googleapis.com people.googleapis.com tasks.googleapis.com \
 gmailmcp.googleapis.com drivemcp.googleapis.com docsmcp.googleapis.com \
 sheetsmcp.googleapis.com slidesmcp.googleapis.com \
 calendarmcp.googleapis.com chatmcp.googleapis.com \
 tasksmcp.googleapis.com

Replace PROJECT_ID with your Google Cloud project ID.

If you plan to run Chat write commands such as
gwscli chat send_message, gwscli chat mark_as_read,
gwscli chat mark_as_unread, or gwscli chat update_notification_settings,
also configure a Chat app in your Google Cloud
project as described in
Configure the Google Chat API [/workspace/chat/configure-chat-api].

Step 2: Create a credentials file

Before creating a client ID, make sure you have configured your OAuth consent
screen in Google Auth Platform. If your consent screen audience is set to
External, add your email address under Audience

Step 3: Register credentials with the CLI

Run the auth setup command and provide the path to your downloaded client
secret file:

gwscli auth setup --oauth_client_file=/path/to/client_secret.json

This command removes any prior tokens and configures the new client. Enter Y
when prompted to confirm the registration.

Sign in to services

Authorize access for a specific command, one or more services, read-only
operations, or all supported services. The CLI prints an authorization URL and
starts a local listener on http://127.0.0.1:<port>/ to receive the OAuth
callback after you grant consent in your browser.

Authentication is incremental. When you run gwscli auth login again for
additional commands or services, the CLI merges the newly granted scopes with
your existing authorized scopes.

Note: Follow the principle of least privilege, especially when configuring
credentials for AI agents. Start with read-only access or grant only the
minimum scopes required for your task rather than authorizing all services at
once.

To authorize read-only OAuth scopes across all services, add the --bundle
flag:

gwscli auth login --bundle=readonly

Some read-only commands require additional scopes outside --bundle=readonly,
such as chat get_notification_settings, people get_user_profile, and
file-level Drive read commands. Authorize those commands
explicitly if you plan to use them. For details, see
Service commands [#service-commands].

To authorize read-only access for a single service, combine the service name
with --bundle=readonly:

gwscli auth login chat --bundle=readonly

To authorize access for an individual action, pass both the service and the
command:

gwscli auth login gmail search_threads

To authorize access for a single service, pass the service name:

gwscli auth login drive

To authorize access for multiple services in a single command, pass the
service names separated by spaces:

gwscli auth login chat gmail

To authorize multiple specific commands at once, pass each target in quotes:

gwscli auth login "chat search_messages" "gmail create_draft"

To authorize all supported services at once, run:

gwscli auth login

To check your granted OAuth scopes, run:

gwscli auth status

If you've granted the userinfo.profile scope, such as by running
gwscli auth login people get_user_profile, this command also displays your
signed-in user profile.

To refresh authorized tokens manually, run:

gwscli auth refresh

Note: Google OAuth 2.0 access tokens typically expire after 1 hour. When you
run a command, gwscli checks token expiry and automatically uses your cached
refresh token to obtain a new access token when needed. Run auth refresh
only when you want to force an immediate token refresh. For details on token
lifetimes and refresh token expiration rules, see
Using OAuth 2.0 to Access Google APIs [https://developers.google.com/identity/protocols/oauth2].

To log out and revoke active tokens, run:

gwscli auth logout

To remove your configured OAuth client and reset authentication credentials,
run:

gwscli auth reset

Browser redirect requirements

Caution: Interactive OAuth sign-in with gwscli auth login starts a temporary
local server on http://127.0.0.1:<port>/ and waits for your browser to
redirect back to that address.

Interactive sign-in requires a machine that can open a web browser and deliver
OAuth redirects to http://127.0.0.1:<port>/. Without extra port forwarding,
gwscli auth login won't complete in the following environments:

Headless environments without browser access

Cloud Shell or remote SSH sessions without local port forwarding

Containerized environments without localhost port mapping

To authenticate on a remote SSH host or container, forward the dynamic port
printed by gwscli auth login from your local computer to 127.0.0.1:<port>
on the remote host before completing consent in your local browser.
Alternatively, obtain an access token separately and pass it with
--oauth_token as described in
Option 2: Pass an existing OAuth token [#oauth-token].

Option 2: Pass an existing OAuth token

If your platform already manages Google OAuth 2.0 tokens, pass an access token
directly on any command using the global --oauth_token flag:

gwscli --oauth_token="$ACCESS_TOKEN" calendar list_events

Caution: Passing a bearer token as a command-line flag can expose the token in
local process listings such as ps or /proc/<pid>/cmdline, shell history,
or agent transcripts. Avoid typing literal token strings on the command line,
and use short-lived tokens with only the scopes you need.

When you pass --oauth_token, the command-line interface doesn't prompt for
consent or refresh expired tokens. Verify the following requirements for the
token:

Required scopes: The token must include the OAuth scopes required by the
command. To check which scopes a command needs before calling it, pass
--show-scopes:

gwscli calendar list_events --show-scopes

You can also print only the comma-separated minimal scopes with
auth login --print-scope-only:

gwscli auth login --print-scope-only calendar list_events

Enabled project services: The Google Cloud project that owns the
issuing credentials must have the required services enabled, as shown in
Step 1: Enable the required services [#enable-apis].

Supported credential types: User-delegated OAuth tokens must come from an
OAuth client ID with Use this client for an AI-powered agent selected.
Access tokens minted by a service account with
domain-wide delegation [/workspace/guides/configure-mcp-servers#domain-wide-delegation] are also accepted.

Discover commands and schemas

The CLI uses a standard command syntax:

gwscli <service> <action> [flags]

Because the command-line interface discovers services, actions, and schemas
dynamically from the backend at runtime, updates might not be backward
compatible. AI agents and developers should inspect --help and --schema at
runtime rather than hardcoding command signatures in static scripts.

List available services

To display all supported services and utility commands, run the help command:

gwscli --help

List service actions

To list available actions for a specific service, pass the service name with
the help flag:

gwscli drive --help

Inspect action parameters and flags

To inspect the parameters, flags, and output format summary for an action, run
the action with the help flag:

gwscli drive list_recent_files --help

To include the supported and recommended minimal OAuth scopes in the help
output, add --show-scopes:

gwscli drive list_recent_files --show-scopes

Inspect the JSON schema

To print the full JSON output schema and field definitions without executing
the action, pass the --schema flag:

gwscli drive search_files --schema

Parse command output and transfer files

The command-line interface prints results directly to standard output.

Structured JSON: Commands that return lists, files, or event records
output valid JSON. You can filter and format the output using tools like jq:

gwscli drive search_files \
 --query="title contains 'Quarterly'" \
 | jq '.files[] | {id: .id, title: .title}'

Document content: Commands that fetch document contents also return JSON.
For example, docs read_doc outputs the document JSON representation with
text and structural elements, and drive read_file_content returns JSON with
a fileContent string field containing the formatted plain text or Markdown:

gwscli drive read_file_content --fileId="FILE_ID" \
 | jq -r '.fileContent'

Download files: To download binary files or export
Google Workspace documents directly to a local path, use
drive download_file_content:

gwscli drive download_file_content --fileId="FILE_ID" \
 --destinationPath="./report.pdf" --exportMimeType="application/pdf"

For Google Workspace documents, --exportMimeType is optional and
defaults to plain text formats such as text/plain or text/csv when
omitted. To export to another format, pass a supported MIME type from
Export MIME types for Google Workspace documents [/workspace/drive/api/guides/ref-export-formats]. For
other files such as PDFs or images, --exportMimeType is ignored. Run
gwscli drive download_file_content --help to inspect the flag details.

Upload local files and revisions: To upload a local file from disk as a
new Drive file using resumable upload, pass --filePath to
drive create_file:

gwscli drive create_file --filePath="./report.pdf" \
 --title="Quarterly Report"

To upload a new content revision for an existing non-Google Workspace
file in Drive, pass --filePath to
drive upload_file_revision:

gwscli drive upload_file_revision --fileId="FILE_ID" \
 --filePath="./report-v2.pdf"

Install packaged agent skills

The CLI includes pre-packaged agent skills that teach AI coding agents how to
discover commands, handle authentication and confirmation prompts safely, and
parse command output.

To list all available packaged agent skills embedded in the CLI, run:

gwscli skills list

To install the agent skills into your agent's skill discovery folder, pass
--dir. For example, use ~/.agents/skills for agents that read the shared
skills folder, or ~/.claude/skills for Claude Code:

gwscli skills install --dir ~/.agents/skills

Important: After installing or updating skills, verify that your AI agent has
loaded the new skill files. Most agent harnesses read skills only at startup,
so start a new session, reload skills in your harness, or restart the agent
before running tasks.

Whenever you update the gwscli binary, also refresh your installed skills as
described in Update the CLI and agent skills [#update].

Update the CLI and agent skills

The command-line interface doesn't auto-update in the background. Check the
Google Workspace CLI release notes [/workspace/cli/release-notes]
periodically for new releases, and compare against your installed version:

gwscli version

To update the binary, re-run the quick-install script [#quick-install] or
download the latest binary for your platform using the
manual install steps [#manual-install]. Your existing OAuth client
configuration and cached tokens are preserved across binary updates.

Refresh packaged agent skills

Packaged agent skills are embedded inside the gwscli binary. After updating
the binary, refresh your installed skills with --overwrite so your agent
receives the latest command guidance and version metadata:

gwscli skills install --dir ~/.agents/skills --overwrite

Passing --overwrite replaces only the gwscli skill subdirectories in the
target folder and leaves other unrelated skills untouched. If you customized
the gwscli skill files directly, back them up or install to a temporary
folder first to compare changes before running --overwrite. After refreshing
skills, make sure your agent loads the updated skill files.

Security and governance

When using the command-line interface directly or through AI agents, follow
these security and governance practices.

Protect against prompt injection

Language models can encounter untrusted text in email bodies, shared files, or
external web pages that carry hidden instructions.

Use the command-line interface only with AI agents and workflows that you
trust.

Start with read-only access and grant write scopes only for the services you
need.

Don't feed unverified documents or messages from unknown senders into agent
prompts.

Review actions taken by your agent and ensure agents don't forward sensitive
contents to external destinations.

Screen requests and responses

You can configure project-level security filters in Google Cloud to
screen CLI inputs and responses for prompt injection, sensitive data, or
harmful content. Any MCP floor settings configured on your Google Cloud
project apply to gwscli requests as well. For setup steps, see
Configure security for Google Workspace MCP servers [/workspace/guides/configure-mcp-security].

Automate in headless environments safely

The auth login and auth setup commands wait for interactive browser or
terminal input and block indefinitely in unattended environments. Don't invoke
interactive setup or sign-in commands in automated background jobs or headless
scripts.

In headless environments, pre-authorize credentials beforehand or pass
externally managed access tokens with --oauth_token. If an automated agent
encounters an authentication or scope error, stop execution and surface the
error rather than attempting interactive sign-in.

Human-in-the-loop verification

Google Workspace enforces user and administrator approval policies for
sensitive actions, such as sending messages, sharing content externally,
trashing items, or deleting data. Other write actions run without asking once
you've granted the required OAuth scopes, so always review what your agent
does.

When an action requires confirmation, the command-line interface pauses, prints
a prompt to standard error, and waits for an approval choice on standard input:

Allow this app to use send_message?

approval_choice
(Options: Allow once, Always allow this tool, Don't allow):

The command-line interface accepts choice identifiers such as ALLOW_ONCE,
ALLOW_TOOL_ALWAYS, or DENY_ONCE on standard input. Sticky options such as
ALLOW_TOOL_ALWAYS appear only in an interactive terminal when permitted by
policy for the action or target resource. When an AI agent runs the command,
the agent must prompt the user for explicit confirmation and write the user's
chosen identifier to standard input, or a human running the CLI directly can
type the choice in the terminal.

Google Workspace administrators can customize these rules for external
agents in the Google Admin console under Agents
> Settings
> User review for external agents.
Administrators can allow actions without prompts, require confirmation on every
command by unchecking Except when user always allows, or block external and
internal collaboration or data access. For details on policy evaluation and
related OAuth, data loss prevention (DLP), attribution, and audit controls, see
Administrator user review policies [/workspace/guides/mcp-elicitation#admin-policies] and
Manage AI agent access & user review [https://knowledge.workspace.google.com/admin/apps/control-which-apps-access-google-workspace-data#ai-agents].

Manage usage telemetry

Usage telemetry sends diagnostic and command-execution metadata to Google to
help monitor reliability and improve the command-line interface. Google handles
collected telemetry data in accordance with the
Google Privacy Policy [https://policies.google.com/privacy].

Usage telemetry is enabled by default. You can check the current setting or
turn usage telemetry off or on persistently at any time:

gwscli logging off # Turn off usage telemetry
gwscli logging status # Show the current setting
gwscli logging on # Turn usage telemetry back on

To disable usage telemetry for a single terminal session or automated
environment without modifying your configuration file, set the
GWSCLI_TELEMETRY_ENABLED environment variable to 0, false, off, or
no:

export GWSCLI_TELEMETRY_ENABLED=0

When usage telemetry is enabled, each command invocation records only the
following operational signals:

Command metadata: The target service and action name, the names of flags
passed to the command, and the number of positional arguments

Environment metadata: The CLI version, build variant, operating system,
and CPU architecture

Execution diagnostics: Execution status, command duration, HTTP status
codes, enumerated error codes or Go error types, and crash stack traces

The CLI never collects flag values, OAuth tokens, search queries, document
IDs, email addresses, or resource content.

Telemetry events are sent directly to Google when a command finishes and aren't
written to a local log file. You can inspect whether telemetry is active by
running gwscli logging status or by reading the telemetry_enabled field in
your local gwscli/config.json configuration file:

Linux: ~/.config/gwscli/config.json

macOS: ~/Library/Application Support/gwscli/config.json

Windows: %AppData%\gwscli\config.json

To print the Google Privacy Policy [https://policies.google.com/privacy] or
Google APIs Terms of Service [https://developers.google.com/terms] URLs from the terminal, run
gwscli privacy or gwscli terms. Usage is also subject to the
Google Workspace user data and developer policy [/workspace/workspace-api-user-data-developer-policy].
