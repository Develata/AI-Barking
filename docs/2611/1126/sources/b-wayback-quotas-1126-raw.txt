 Gmail API and MCP server quotas

 Stay organized with collections

 Save and categorize content based on your preferences.

As of May 1, 2026, the Gmail API, Google Calendar API, and Google Drive API have
updated usage quotas. These three APIs (and their MCP servers) also support the
Scaled Tier for requesting higher rate limits beyond standard quotas. Standard
Tier limits take effect across all projects on April 1, 2027. For rollout
timelines and policy details, see
Usage tiers and quotas for
Google Workspace APIs and MCP servers [/workspace/guides/quota-usage-tiers].

As the Gmail API is a shared service, we apply quotas to make sure it's used
fairly by all users and to protect the overall performance of the
Google Workspace system.

Use this document to understand Gmail API and MCP server usage and
quotas. For pricing, see Understand Google Workspace API and MCP server pricing
and billing tiers [/workspace/guides/quota-pricing].

Monitor your usage

There are two ways to monitor your Gmail API and MCP server usage and
quota information:

To monitor your usage from the Quotas & System Limits tab of an API or MCP
service page:

Gmail API: In the Google Cloud console, click Menu
menu
> APIs & Services
> Enabled APIs & Services
> Gmail API
> Quotas & System Limits.

Go to Gmail API Quotas & System Limits [https://console.cloud.google.com/apis/api/gmail.googleapis.com/quotas] 

Gmail MCP server: In the Google Cloud console, click
Menu menu
> APIs & Services
> Enabled APIs & Services
>
Gmail MCP API
> Quotas & System Limits.

Go to Gmail MCP API Quotas & System Limits [https://console.cloud.google.com/apis/api/gmailmcp.googleapis.com/quotas] 

To monitor your usage from the Google Workspace dashboard:

In the Google Cloud console, click Menu
menu
> the View all products tile
> Google Workspace
> Dashboard.

Go to Google Workspace dashboard [https://console.cloud.google.com/workspace-api/dashboard] 

If prompted to select a Google Cloud project, select the one that you want
to monitor.

Optionally, in the upper-right corner of the Dashboard tab, you can set
the time range (1 day, 7 days, or 30 days). This lets you gauge your
usage over different periods.

Note: The Google Workspace dashboard doesn't display the
Gmail MCP server's Standard Tier limit of 5,000 requests per
day, per project. To monitor that limit, view the Quotas & System Limits
tab on the Gmail MCP API page.

Usage tiers

Google Workspace APIs are accessible under two tiers:

Standard Tier: Enabled by default at no cost for all new and
existing Cloud projects, with published usage limits. Starting
November 24, 2026, projects with higher limits keep running, but they can't
request additional quota without enrolling in the Scaled Tier (or
attesting to the internal-use exception). Starting April 1, 2027,
unenrolled projects revert to Standard Tier limits, and excess requests
are throttled. Usage on this tier never produces charges on a Google Cloud
bill.

Standard Tier with internal-use exception: Designate projects as
"Internal-use exception" and request higher per-project REST API usage
quotas without switching to the Scaled Tier (MCP server quotas aren't
eligible for increases under this exception).

Scaled Tier: Designed for applications and AI agents that need higher
rate quotas. Starting April 1, 2027, Gmail API charges apply
after daily usage exceeds the bucket's daily no-charge
allowance [#daily-threshold] for the linked Google Cloud Billing
account. On the same date, Scaled Tier Gmail MCP server usage
begins incurring charges from the first request (with no daily no-charge
allowance). Prices are quoted across three billing tier
buckets [/workspace/guides/quota-pricing#billing-buckets] (Light, Medium,
and Premium).

Note: MCP requirement enforcement starts February 1, 2027. AI agents or similar
access tools calling Google Workspace data must use MCP servers instead
of REST APIs. Starting on that date, AI agents calling REST APIs directly are
limited to Standard Tier quotas, regardless of tier.

To learn more about tier policies, quotas, and pricing, see Usage tiers and
quotas for Google Workspace APIs and MCP
servers [/workspace/guides/quota-usage-tiers].

Daily no-charge allowances

Projects on the Standard Tier never incur Google Cloud charges (GA MCP
servers are capped at 5,000 no-cost requests per day, per project). For
Cloud projects enrolled in the Scaled Tier, the following billing rules
apply:

Gmail API: Your linked Google Cloud Billing account
receives daily no-charge allowances of HTTP 2xx (200–299)
requests—including 200 OK and 204 No Content responses—for each
billing tier bucket [/workspace/guides/quota-pricing#daily-allowances]
(70,000,000 Light, 10,000,000 Medium, and 1,000,000 Premium requests per
day across all projects sharing the billing account), resetting at midnight
Pacific Time (PT). Both Google Cloud Billing and the
Google Cloud console count only HTTP 2xx responses, excluding 3xx,
4xx, and 5xx responses.

Gmail MCP server: Scaled Tier MCP usage has no daily
no-charge allowance (0 billing units per day), so charges apply from the
first HTTP 2xx request starting April 1, 2027. Because failed
tools/call requests (including tool execution and argument-translation
errors) return HTTP 200 with isError: true in the JSON-RPC response,
they also count toward billing. HTTP 3xx, 4xx, and 5xx responses
don't count toward billing. Each tool call counts as 1 billing unit (and 1
request toward the Standard Tier daily limit) by default. However,
list_drafts and search_threads each count as 10 billing units (and 10
daily requests) per call because they make multiple API calls.

Non-billed responses—such as 304 Not Modified and 4xx or 5xx error
responses—still count toward 1-minute rate-limit quotas.

Gmail API quotas

Quotas are defined in terms of quota units [#per-method-quota], an abstract
unit of measurement representing Gmail resource usage.

The Gmail API enforces two types of quotas:

Per minute per project: The maximum number of quota units your
Cloud project can use in one minute.

Per minute per user per project: The maximum number of quota units that
any single user can make within your Cloud project in one minute.
This quota helps ensure a fair distribution of capacity among your app's
users.

The following table details these usage limits:

Usage limit type
Limit

Per minute per project
1,200,000 quota units

Per minute per user per project
6,000 quota units

If you exceed a quota, you'll receive a 403: User rate limit
exceeded [/workspace/gmail/api/guides/handle-errors#user-rate-limit] HTTP
status code response. If this happens, you should use an exponential backoff
algorithm [#exponential-backoff] and try again later.

For additional information on handling limit errors, see Resolve
errors [/workspace/gmail/api/guides/handle-errors].

Per-method quota unit costs

The number of quota units consumed per request varies depending on the method
you call and the query parameters.

A billing tier bucket [/workspace/guides/quota-pricing#billing-buckets] is a
pricing category (Light, Medium, or Premium) that groups API methods and
MCP operations based on their resource intensity, operational complexity, and
payload size. Under the Scaled Tier, REST API operations within a bucket only
begin counting as billable requests after daily traffic exceeds that specific
bucket's independent daily no-charge allowance.

The drafts.get [/workspace/gmail/api/reference/rest/v1/users.drafts/get],
messages.get [/workspace/gmail/api/reference/rest/v1/users.messages/get],
and threads.get [/workspace/gmail/api/reference/rest/v1/users.threads/get]
methods use dynamic quota costs based on the
format [/workspace/gmail/api/reference/rest/v1/Format] query parameter.
Retrieving full message content (such as the default full format or raw)
consumes three times as many quota units as using metadata or minimal,
which omit message bodies. To reduce quota usage when you don't need full
message payloads, set format to metadata or minimal.

The Gmail MCP server enforces three types of quotas:

Per minute per project: The maximum query cost your
Cloud project can use in one minute.

Per minute per user per project: The maximum query cost that any single
user can use within your Cloud project in one minute.

Per day per project (Standard Tier): The maximum number of requests

enrolling in the Scaled Tier [#usage-tiers]. list_drafts and

Troubleshoot issues

If you encounter issues with API and MCP server quotas, use the following
troubleshooting options.

Resolve time-based quota errors

For all time-based errors (maximum of N requests per X minutes), we recommend
your code catches the exception and uses a truncated exponential backoff to
make sure your devices don't generate excessive load.

Exponential backoff is a standard error handling strategy for network
applications. An exponential backoff algorithm retries requests using
exponentially increasing wait times between requests, up to a maximum backoff
time. If requests are still unsuccessful, it's important that the delays between
requests increase over time until the request is successful.

Example algorithm

An exponential backoff algorithm retries requests exponentially, increasing the
wait time between retries up to a maximum backoff time. For example:

Make a request to the Gmail API.

If the request fails, wait 1 second + random_number_milliseconds and retry the
 request.

If the request fails, wait 2 seconds + random_number_milliseconds and retry the
 request.

If the request fails, wait 4 seconds + random_number_milliseconds and retry the
 request.

Do so up to a maximum_backoff time.

Continue waiting and retrying up to some maximum number of retries, but
 don't increase the wait period between retries.

where:

The wait time is min(((2^n)+random_number_milliseconds), maximum_backoff),
 with n incremented by 1 for each iteration (request).

random_number_milliseconds is a random number of milliseconds less than or
 equal to 1,000. This helps to avoid cases in which many clients are
 synchronized by some situation and all retry at once, sending requests in
 synchronized waves. The value of random_number_milliseconds is
 recalculated after each retry request.

maximum_backoff is typically 32 or 64 seconds. The appropriate value
 depends on the use case.

The client can continue retrying after it has reached the maximum_backoff
time. Retries after this point don't need to continue increasing backoff time.
For example, if a client uses a maximum_backoff time of 64 seconds, then after
reaching this value, the client can retry every 64 seconds. At some point,
clients should be prevented from retrying indefinitely.

The wait time between retries and the number of retries depend on your use case
and network conditions.

Resolve MCP server quota errors

If you encounter issues with MCP server quotas, see the Troubleshooting section in the
