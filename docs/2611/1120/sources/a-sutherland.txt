Summary

The published Lean source compiles without errors, the five headline theorems depend only on the three standard axioms, every module has been replayed through the Lean kernel, two independently written kernels, nanoda and con-leche, accept the full exported proof, and lean4lean accepts every compiled module. con-leche's --compare mode, an independent implementation of Comparator's statement matching, confirms all five theorems against the challenge. The lake comparator run and the Lean-kernel replay of the export are still in progress.

What was verified

The theorem riemannHypothesis : RiemannHypothesis in the submission's Main.lean, where RiemannHypothesis is Mathlib's own definition (Mathlib/NumberTheory/LSeries/RiemannZeta.lean):

def RiemannHypothesis : Prop :=
 ∀ (s : ℂ) (_ : riemannZeta s = 0) (_ : ¬∃ n : ℕ, s = -2 * (n + 1)) (_ : s ≠ 1), s.re = 1 / 2

and four further theorems, including the analogous statement for all Dirichlet L-functions. "GRH" here means Dirichlet L-functions only.

Arithmetic consequences

As a check that does not depend on Mathlib's definition of the zeta function, the proof was combined with kimihiro64/Robin1984 [https://github.com/kimihiro64/Robin1984] (commit acab1a3), an independent formalization of Robin's and Lagarias's criteria on the same Lean and Mathlib versions. Importing both gives two theorems about the divisor sum, with no hypotheses and no mention of zeta (ArithSolution.lean [ArithSolution.lean]; statements alone in ArithChallenge.lean [ArithChallenge.lean], which imports only Mathlib):

theorem robin_inequality :
 ∀ n : ℕ, 5040 < n →
 ((ArithmeticFunction.sigma 1 n : ℕ) : ℝ) <
 Real.exp Real.eulerMascheroniConstant * (n : ℝ) * Real.log (Real.log (n : ℝ))

theorem lagarias_inequality :
 ∀ n : ℕ, 0 < n →
 ((ArithmeticFunction.sigma 1 n : ℕ) : ℝ) ≤
 (harmonic n : ℝ) + Real.exp (harmonic n : ℝ) * Real.log (harmonic n : ℝ)

Check it yourself

With Lean v4.36.0 installed, nothing needs to be built. You need roughly 100 GB of RAM and 70 GB of disk.

zstd -d --long=30 solution.ndjson.zst # --long=30 is required
zstd -d --long=27 challenge.ndjson.zst
sha256sum solution.ndjson challenge.ndjson # compare with the hashes above

lake comparator --config comparator.json \
 --challenge-from-export challenge.ndjson --solution-from-export solution.ndjson

nanoda alone took about 28 minutes on 80 threads. The Lean kernels are single-threaded and take much longer.

The fastest independent check is con-leche built from source (Lean v4.36.0, about two minutes to build). It needs about 50 GB of RAM and took under four minutes on 64 threads:

git clone https://github.com/leanprover/con-leche && cd con-leche
git checkout compare # 5dc36dc1; master (cd2eceab) for the plain check
lake build con-leche
.lake/build/bin/con-leche --compare challenge.ndjson solution.ndjson

Caveats

The build ran on cloud machines without a sandbox, and compiled each file by calling lean directly with the same inputs lake supplies (module name, package name and the lakefile's options), not through lake build.

The per-file .olean hashes depend on the build directory. In Lean v4.33.1 a compiled file stores each linter message together with the absolute path of its source file. Of our 175,187 compiled files, 98,219 contain the path /home/ubuntu/grh/src/lean/src/…; the other 76,968, including Main.olean, contain no path. So project-oleans.sha256 and its sha256 can be reproduced in full only by a build whose source tree is at /home/ubuntu/grh/src/lean. For a build at any other path, only the files of modules that emit no linter messages should match.

 What we checked: a lake build of 240 modules on a different machine, at a different path, gave 168 files identical to the manifest and 72 different; all 72 contain that build's path and none of the 168 do. Separately, 77 modules compiled both ways in the same directory, by lake build and by our direct invocation, were byte-identical. We have not compared the full set against a lake build.

The exported proof (solution.ndjson) is the artifact the independent kernels checked. Its hash is the one to compare across builds; we have not examined whether the export format can carry a source path.

The export was produced from that unsandboxed build. We have not ourselves compared its sha256 with an export made from a sandboxed lake build.

A passing check shows that the formal statements, as written in Lean against Mathlib's definitions, follow from the three standard axioms according to the kernels used. It relies on those kernels and on Mathlib's definitions being what they are intended to be.

A first build attempt used a wrong module root and was discarded in full; none of it is in these results.
