Engineering

Building a Software Factory

AI made writing code fast, but reviewing it became a bottleneck for our engineers. This is how we handed our delivery line to agents one step at a time, and what the numbers say.

November 20, 2026

by Alejandro Alvarez, Technical Staff

Every month, agents write an increasing share of our code, and the queue of pull request reviews grows as a result. Review bots catch problems, but each finding sends the change back for another round of reviews, and in the end, the pull request still waits for a person to approve it.

Over the summer, the share of human reviews in our core API repository spent on agent-written code more than tripled, to about one in five, and the number of pull requests awaiting human approval doubled.

Anthropic engineer Felix Rieseberg’s “How to be more ambitious [https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/]” inspired us to think ahead. Instead of asking agents for better changes, we tested if they could take over each stage of software delivery and decided how we would judge each handover before looking at its results. OpenAI has described [https://openai.com/index/harness-engineering/] a similar shift on a product built from an empty repository.

Cloud agents drove 38% of the pull requests we merged in October, up from 0.1% in June. Between September and mid-November, the median wait for a first approval fell from over two hours to about five minutes and the number of pull requests we merged each week more than doubled. Changes approved by an agent were reverted no more often than those approved by people.

Where we began

Seven jobs between a task and production. Review means reading the change and asking for fixes; approval is the sign-off that lets it merge. Agents already helped with the first; each step below hands the next job to them.

At the start of the year, an engineer picked a task, prompted an agent to write it and opened a pull request, then waited for CI and handed issues back to the agent. Then they found a colleague to review it. Once a change merged, main could break, and whoever noticed first had to find the cause and fix forward or roll it back. QA was also done by hand. Every handoff between these steps was a person’s job, so the more changes agents wrote, the more work was passed to engineers.

Agents, with a person at their side. An engineer walks every change through every station and tests it by hand at QA. Review is the slowest stop: the engineer has to find a colleague, pull them off their own work and bring them over while pull requests pile up at the door.

Step 1 · Write and pass CI

The problem: An agent writing a change might save us an hour of typing, but it leaves an afternoon of cleanup fixing flaky tests, lint failures, merge conflicts and review comments.

What we built: An internal service that runs coding agents in the cloud and stays with each pull request until it's green. You give it a task and approve the plan, and then the agent writes the change, opens the pull request, reruns CI, fixes tests, answers review comments and rebases.

How we knew it worked: The service was handling 38% of our pull requests by its third month, and our agents also needed minimal intervention. In a sample of 100 of their pull requests merged in the first half of November, 78 had no commits from a person.

From two pull requests in June to over 3,000 a month. Seven repositories. November is projected from its daily average so far. Agent-driven merges were 38% of all merges in October and 30% so far in November. This is a floor: we only count pull requests we can attribute to an agent.

The same road, without the walk. A person hands the agent the task once, and the agent carries it to a green pull request on its own. The handoff counter stays at zero until review, where the change waits for a person.

Where the bottleneck moved

Agents produced review-ready pull requests faster than people could read them, so review became the next station to hand over.

The problem: Our third-party review bot lacked context, so engineers learned to skim past it and still read every change themselves.

What we built: An AI reviewer with the same context as the agents writing the code, including the plan, the diff and the code around it. Usually, the author is another agent, so a change goes back and forth between the coding agent and the AI reviewer until it’s clean.

How we knew it worked: In our core API repository, 93% of the AI reviewer’s comment threads were resolved or led to a code change in the first half of November, up from 84% in September. A rebuild in late September cut the cost of each review to about a third, while weekly review volume increased.

Review loops back to code. The AI reviewer sends flawed changes back to the coding agent until they pass. Clean changes still queue for a person to approve.

The problem: Letting the AI reviewer approve would clear the queue, but that meant code would merge without a person reading it. We needed proof that AI approvals matched the judgment of our engineers before taking this step.

What we built: Risk-based approval. A separate agent rates each pull request low, medium or high risk, rounding up when unsure, and the rating decides who can approve it. At first we let AI approve low-risk changes on its own and medium-risk changes where a repository allows it. High-risk changes go to a person, and code owners still sign off on critical areas of our codebases like database migrations, secrets and authentication.

We started by having the reviewer approve alongside people and tracking how often a person disagreed. In mid-October, we let pull requests merge on AI approval alone. Across September and October, a person objected to only 15 of the 977 pull requests it approved, about 1.5%, at about the same rate before and after that date.

How we knew it worked: The median wait for a first approval fell from over two hours in September to about five minutes in mid-November, and about seven in ten merges the AI reviews in our core API repository go through on its approval alone. Of all pull requests merged on AI approval alone from October to November, only one in a thousand was reverted, compared with about one in two hundred for those people approved. Given the majority of AI approvals were for low-risk changes less likely to be reverted, we compared across risk levels and found AI approvals hold comparable to that of humans.

The problem: We launched a new product called App Studio [/product/app-studio], and unit tests weren’t enough to build confidence. We needed something to use it like a person would, signing up and testing all features and changes.

What we built: A QA loop that tests the product like a user. Agents drive browsers through the live product in parallel, flagging anything that doesn’t run as expected. Before reporting a bug, the agent rules out any issues with its own setup and finds the code that caused it. Confirmed bugs become a task for agents to fix, and the loop reruns the scenario to verify it.

How we knew it worked: In its first four days, the QA loop found 86 confirmed bugs, and agents fixed all of them. Since early November, every change merged has to pass a verification run on its own preview environment first.

Let Agents Watch Main

✓Approve

✓QA

6Fix breaks

The problem: At this volume, we can't wait for someone to spot or report issues. Every hour the main codebase stays broken, more changes pile on top of the break.

What we built: When an alert fires, agents work through a set of steps: retry the checks, diagnose the failure, apply a known fix if one exists and call a person if none of that works. A coordinator, which we describe more below, runs these steps and holds its own merges until main is green. After each release, our release system monitors production and automatically undoes the release if a health check fails.

How we knew it worked: In its first two weeks it saw about 140 alerts. All but one were fixed without the coordinator having to call anyone in, with a median of 23 minutes from red to green. Automatic rollback has fired in production.

Where the bottleneck moved

Every station now had an agent, but an engineer still decided what each one worked on and in what order.

7Run the line

The problem: Engineers were the line’s coordinators, responsible for starting agents, ordering merges and babysitting the runs that stalled.

What we built: A coordinator that runs the software factory. It reads the issue tracker, hands work to agents and orders merges. It brings in a person when our rules require one or when a step gets stuck.

The coordinator runs the line. Work comes in from people’s specs and from alerts, and shipped changes come out the other end, through the same steps as before. When policy says a person decides, the change loops out to people and comes back.

How we knew it worked: We earned trust in the coordinator the same way we did for AI approval. First it ran read-only, only tracking its decisions. Before production, a person judged every action it proposed in short test runs. In the first two weeks after the coordinator went live, it dispatched over 14,000 agent tasks, from diagnosis and planning to review and fixes, which led to about 1,900 pull requests.

Read-only shadow mode before any writes
Without it: The bug from the read-only run would have gone live and re-run work that had already finished.

Gates re-checked at the exact commit being merged
Without it: A pull request was merged by override after its checks had refused it, and agents kept pushing commits after a reviewer had signed off.

External actions safe to repeat
Without it: Agents raced on the same task and cancelled each other's copies, a few times leaving none running.

People step in by policy, not by accident
Without it: Our earlier merge tooling stalled three times on a prompt waiting at someone's keyboard and blocked every merge, once for over an hour.

Rollback in one call
Without it: The release train pulled a release off every production pool on a noisy error signal, and undoing an unwanted rollback took more than one step.

Safety rails. Each one answers a failure we hit in our earlier tooling or in the coordinator's own testing.

Where the bottleneck moved

With the line running itself where our rules allow, more of the wait is now upstream, in deciding what to build and answering agents’ questions.

Where the line is now

Where Each Station Stands Today

The line is furthest along in the codebase behind App Studio. Nearly every pull request merged there in October and November was written by agents, and our agent service drove about seven in ten of them in October.

By late October, we saw about 2.5 times as many weekly merged pull requests across our main repositories compared to September. The median approval wait fell from over two hours to about five minutes.

The new job

The Engineer’s Role

Our engineers now read a smaller share of the diffs. They decide what gets built, answer agents’ questions about architecture, set the rules for what ships and fix the places where agents stall. That last job has four parts:

Find where agents waste effort: We look for runs that stall and for the parts of the codebase where agents’ changes keep needing rework.

Remove the blockers: Many of our biggest wins have been access and infrastructure fixes. If an agent can’t reach a test environment, credential or preview deploy, this stalls everything behind it.

Make the path agent-friendly: We organize codebases so agents can find their way around them, write playbooks for failures we’ve already seen and set up better patterns and core systems so agents can use them safely.

Keep the measures honest: We decide how each station will be judged before we look at its results.

Working on the factory. Agents carry every change from station to station. Engineers work on the road between them: paving the rough stretch, clearing what blocks it and adding the check that catches what slipped through. Watch the shipped count climb as they do.

To find where agents waste effort, we built a tool that measures friction from the AI agent’s record on every pull request, including how long it takes to implement the change, how many problems the reviewer finds, how serious they are, whether a problem comes back after an agent’s fix and how long a change takes to come clean. It compares each area of a codebase with what’s typical for a pull request of the same size and draws the result as a map, so the areas where agents struggle most stand out.

Mapping a codebase by friction

Every area, folder and file is shaded by how much review effort agents’ changes cost there. Hot spots get a targeted fix.

Illustrative. The map is drawn automatically, with each area compared against a typical pull request of the same size. It points us at where a cleanup, a doc or a guardrail will pay off, and each fix is tracked to see whether the friction stays down.

Each area on the map comes with a brief an agent can act on: the evidence, a likely cause, a bounded change and a test that keeps it fixed. In our first cleanup, 23 pull requests in one internal service reused existing helpers, removed dead code and added reuse checks to CI, and duplicated lines in the files they touched fell by 16%.

What's Next

Automating software delivery shifts the bottleneck upstream, to deciding what to build in the first place. Our long-term goal is a system that takes a description of an outcome and ships it, bringing in people at defined points where human judgment is required.
