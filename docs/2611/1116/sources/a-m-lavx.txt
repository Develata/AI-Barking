Windows 11 Collects Data on Coding Agents and Developer Tools You Use

•4 min read

Xusheng Li found that Windows 11's MissionControlAggregator records which coding agents and developer tools run on a PC and queues a usage bitmap for upload when optional diagnostic data is enabled. In the U.S. setup tested, optional diagnostic data was enabled.

Xusheng Li reported Nov. 16, 2026, that a Windows 11 system component records which coding agents and developer tools run on a PC and queues a usage bitmap for upload when optional diagnostic data is enabled.

The component is MissionControlAggregator.dll. DiagTrack, the Connected User Experiences and Telemetry service, starts AggregatorHost.exe, and that process loads the DLL. MissionControlAggregator does not scan running processes. It subscribes to Windows events that already carry application identities, then matches those identities against built-in lists.

Xusheng Li found the lists while asking an AI assistant to scan recent Windows binaries for undocumented features. The assistant returned executable names that included coding agents and familiar developer tools. The names sat inside MissionControlAggregator.dll. Following references led from string comparisons to a running component that records matches, saves them locally and reports them through Windows Diagnostics.

Four CLI agent slots check copilot.exe, claude.exe, codex.exe and agy.exe, with extensionless equivalents on the WSL route. Five desktop agent slots check github.exe, claude.exe, codex.exe, cursor.exe and antigravity.exe. A feature named CLICodingAgentUsage, feature ID 62580080, guards the agent checks. The list extends beyond AI agents. The same component checks node.exe, python.exe, dotnet.exe, gcc.exe, clang.exe, gdb.exe, javac.exe, devenv.exe and code.exe, among others. Those checks feed 12 broader developer-tool categories.

Some slots also verify the publisher. The Node.js slot expects Node.js Foundation. The Python slot expects Python Software Foundation. The .NET and Visual Studio slots expect Microsoft Corporation. The compiler and debugger group that contains GCC and Clang has no publisher check in this path.

For Windows programs, the aggregator consumes KernelProcess.AppStateChangeSummary and Win32kTraceLogging.AppInteractivitySummary. These events provide application identities that handlers parse and pass to the matchers. For WSL, the aggregator consumes Microsoft.Windows.Lxss.Manager.Exec and ExecCritical and uses the imageName field. A native Windows codex.exe can reach the CLI-agent checks through the app-state summary route, so collection covers Windows executables as well as programs launched inside WSL.

A successful match sets a slot in aggregator state. Later, ReportCohorts<12,4,5> converts those slots into bitsets and emits a self-describing TraceLogging event named Segments.SubCohorts. The numbers correspond to 12 broader tool categories, four CLI agents and five desktop agents. The report stores a bitmap of which agents were observed during the reporting window. Executable names do not appear in the report. The source events also include runtime, time in focus, interaction counters and resource usage, but the component discards those details. Timestamps in the report describe the collection window, not how long each agent ran.

The aggregator saves state on disk at:

C:\ProgramData\Microsoft\Diagnosis\AggregatorStorage\MissionControlAggregator

To test the finding, Xusheng Li copied cmd.exe to a file named codex.exe and ran it in an interactive Windows session. The name caused the component to record Codex in CLI slot 2. A separate run without an additional ETW trace also set that slot. A separate test with a copy named gcc.exe set developer-tool slot 3. In the upload queue, that report showed SubCohorts: [8], or 1 << 3, the compiler and debugger category shared by GCC and Clang.

The report is treated as optional diagnostic data. In the U.S. setup Xusheng Li tested, optional diagnostic data was enabled by default and labeled Include Optional. After completing setup with those defaults, AllowTelemetry was 3, which confirms that optional diagnostic data was enabled. Xusheng Li found the agent event in DiagTrack's upload queue with isRequired set to false. That means Windows queues the coding-agent usage report for upload to Microsoft unless the user declined optional diagnostic data during setup or turned it off through Settings.

The Diagtrack-Listener session on the test VM subscribed to both ends of the path. It subscribed to KernelProcess with MatchAnyKeyword=0x400000000002, which includes the summary keyword 0x400000000000, and to Microsoft.Windows.MissionControlAggregator with MatchAnyKeyword=0xe00000000000, which includes the report keyword 0x800000000000. Both subscriptions used level 255. Those subscriptions show where the report can go. The upload queue check shows that Windows queued it.

Xusheng Li checked a clean installation of Windows 11 Home ARM64 from the latest official ISO with the region set to the United States. The public ISO's baseline VM had the coding-agent feature disabled by image default. That result does not support a claim that the feature is active on every Windows installation. On the test VM, Windows 11 build 26200.9974 with MissionControlAggregator.dll version 10.0.26100.9818, the feature and DiagTrack were active before testing. DiagTrack ran with startup type Automatic.

Xusheng Li found no prompt text or source code in the report. The report still records which agents and developer tools a person uses, and that has privacy implications.

Users can decline optional diagnostics during setup. Users can turn off Send optional diagnostic data under Settings, Privacy & security, Diagnostics & feedback. Microsoft's diagnostics and privacy guide explains the change.

Xusheng Li published the full investigation, including PowerShell queries and ETW captures, at xusheng.dev [https://xusheng.dev/posts/windows-coding-agent-telemetry/].
