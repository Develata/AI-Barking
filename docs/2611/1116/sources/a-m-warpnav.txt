Windows 11 会记录你用了哪些 AI 编程工具？怎么查、怎么关可选诊断数据

 156 0 [#comments]

 0

 [javascript:;]

研究者 Xusheng Li 在 11 月 16 日公开的逆向分析中发现：在相关实验功能已开启的 Windows [https://warpnav.com/tag/windows] 11 ARM64 环境里，MissionControlAggregator 会把是否用过 Codex、Claude、Copilot、Cursor 等 AI 编程工具，以及 Python、Node.js、GCC、VS Code 等开发工具，编成几组标记位。在允许可选诊断数据的测试中，他还在待上传队列中找到了该事件。这不等于所有 Windows 11 都已开启，也不是网络抓包证明微软已收到。该报告记录的是“用没用过”，研究者未在其中发现提示词、源代码或使用时长。要限制这类可选诊断事件的发送，可先关闭设置里的“发送可选诊断数据”，无需为此安装精简脚本或停用整套诊断服务。

Windows 到底记了哪些工具

研究者在 MissionControlAggregator.dll 里找到了一串写死的程序名，再顺着代码确认了它们的用途：拿来和正在运行的程序名做比对，命中就在对应的槽位上打一个标记。控制 AI 代理检测的功能开关名字很直白，叫 CLICodingAgentUsage。被比对的程序分三组：

分组
比对的程序名
上报粒度

命令行编程代理（4 个槽位）
copilot.exe、claude.exe、codex.exe、agy.exe；在 WSL 里比对不带 .exe 的同名命令
每个代理一位

桌面编程代理（5 个槽位）
github.exe、claude.exe、codex.exe、cursor.exe、antigravity.exe
每个代理一位

开发工具（12 个类别）
node.exe、python.exe、dotnet.exe、gcc.exe、clang.exe、gdb.exe、javac.exe、devenv.exe、code.exe 等
按类别一位，例如 GCC、Clang、GDB 共用“编译器/调试器”这一位

这个组件不自己扫描进程，而是订阅 Windows 已有的事件：普通程序走 KernelProcess.AppStateChangeSummary 和 Win32kTraceLogging.AppInteractivitySummary，WSL 里的命令走 WSL 的执行事件。命中后的状态先保存在本机的 C:\ProgramData\Microsoft\Diagnosis\AggregatorStorage\ 下，大约每天汇总一次，生成名为 Segments.SubCohorts 的诊断事件。研究者在 Windows 的上传队列里找到了这条事件，标记为 "isRequired": false，也就是可选诊断数据。

判断依据主要是文件名。研究者把 cmd.exe 复制一份改名为 codex.exe 运行，Codex 那一位就被置上了；改名为 gcc.exe，编译器类那一位被置上。部分开发工具会额外核对发布者，比如 Node.js 要求是 Node.js Foundation，Python 要求是 Python Software Foundation，.NET 和 Visual Studio 要求是 Microsoft；编译器这一组没有发布者校验。

网上的转述里有几种说法跑偏了，对照如下：

流传说法
研究者实际看到的

Windows 在读我的代码和提示词
上报内容只有几组标记位，研究者没有发现提示词或源代码

它记录了每个工具用了多久
源事件里有运行时长、前台时间等信息，但这个组件丢掉了，只留“用过没有”；报告里的时间戳只表示统计窗口

只有在 WSL 里运行才会被记
普通 Windows 程序也会，通过应用状态事件进入比对

所有 Windows 11 都已经在上传
研究者的 ARM64 虚拟机上实验功能已开启，公开 ISO 基线虚拟机默认关闭；待上传队列也不等于已完成网络发送

还有一点常被忽略：微软自己的文档本来就写明，可选诊断数据包括“应用活动，比如设备上启动了哪些程序、运行了多久、响应输入有多快”。应用活动本来就在微软列出的诊断数据类型中；这次新的发现，是该组件为 AI 编程代理专门设置了匹配名单和标记位。文档列出数据类型，并没有解释这项专门统计的具体用途。从功能名和分组方式看，这更像是在统计 Windows 上各家 AI 编程工具的使用情况；微软没有说明用途，这一点只是推测。

以上证据来自这位研究者的逆向和测试：包括 Parallels 中的 Windows 11 ARM64（版本 26200.9974）以及按美国地区安装的家庭版 ARM64 环境，没有覆盖所有版本和地区。本文核验的微软诊断数据文档也没有专门说明这份 AI 工具名单的统计目的。

我的电脑会把这些上传吗

按这次研究追踪到的数据路径，至少有两个关键条件：

功能开关在你的机器上已开启。CLICodingAgentUsage 由微软的服务端实验控制，研究者的机器上是自动开启的，公开 ISO 新装后默认关闭。普通用户很难直接看到这个开关的状态。

允许发送可选诊断数据。研究者按美国地区全新安装家庭版时，安装界面里的诊断数据开关默认就是“包含可选数据”，装好后 AllowTelemetry 的值为 3。中国地区安装时的默认值，我们没有找到可核实的资料，请以自己设置页显示的为准。

第一个没有普通设置页可单独控制，第二个可以直接检查和调整。所以实用的做法是先检查诊断数据设置。

怎么查自己的设置

设置页

打开“设置 → 隐私和安全性 → 诊断和反馈”，展开“诊断数据”。如果“发送可选诊断数据”的开关是开着的，这类事件就在上传范围内。如果整页显示“某些设置由你的组织管理”且无法修改，说明电脑受公司策略控制，需要找 IT 管理员。

Windows 11 操作路径示意。关闭的是“发送可选诊断数据”，必需诊断数据仍保留；组织策略可能限制修改。

PowerShell 只读检查

以管理员身份打开 PowerShell，下面三条命令只读取、不修改：

# 1. 常见的设备级诊断数据策略值
Get-ItemProperty 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\DataCollection' -Name AllowTelemetry -ErrorAction SilentlyContinue

# 2. 设置页保存的值
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Policies\DataCollection' -Name AllowTelemetry -ErrorAction SilentlyContinue

# 3. 这个组件当前有没有被加载
tasklist /m MissionControlAggregator.dll

前两条的 AllowTelemetry：1 表示只发送必需诊断数据，3 表示包含可选诊断数据，0 表示关闭（只对企业版、教育版和服务器版有效，其他版本按 1 处理）。家用电脑第一条通常没有输出，只能说明这个位置未读到该值，不能据此判定发送开关已关闭。第二处的界面值位置有 Microsoft Q&A 社区回答作参考；它不是完整的策略诊断方法。遇到数值缺失、界面灰显或两者不一致，以设置页的实际状态和组织管理策略为准。

第三条如果列出 AggregatorHost.exe，说明这个组件正在运行。但它被加载不代表 AI 代理检测已开启，研究者是用 ETW 跟踪和改写统计窗口才确认的，普通用户没必要做到那一步。

诊断数据查看器

想查看可见的诊断事件，可以在“诊断和反馈”里启用“查看诊断数据”，按提示从 Microsoft Store 安装诊断数据查看器（Diagnostic Data Viewer），再搜索 MissionControlAggregator 或 Segments.SubCohorts。按微软的查看器专用文档，启用数据查看后 Windows 会保存供查看的数据，应用窗口可以关闭，之后再打开检查；它不是此前所有诊断事件的历史归档。看到事件也不一定表示已经上传，有些仍在队列里。该报告约一天汇总一次，暂时搜不到不能证明未记录。

检查结束后可关闭“查看诊断数据”，清掉这份本地查看记录；它与“发送可选诊断数据”是两个不同的开关。

怎么关

个人电脑：关掉可选诊断数据

在“设置 → 隐私和安全性 → 诊断和反馈 → 诊断数据”里，把“发送可选诊断数据”关掉。研究者在允许可选诊断数据时于待上传队列发现该事件，其 isRequired 标记为 false；按这一分类，关闭开关可限制后续这类可选诊断事件的发送。这不等于禁用组件，也不能据此推断已删除本地聚合状态。

同一页下方还有“删除诊断数据”。按微软的说明，它删除的是微软为这台设备保存的诊断数据，不会删除与 Microsoft 账户关联的数据，也不会阻止之后继续发送。所以顺序是先关开关，再按删除。

专业版、企业版：用组策略限制上调

管理多台电脑、需要通过设备策略限制采集级别时，可以用组策略：打开 gpedit.msc，进入“计算机配置 → 管理模板 → Windows 组件 → 数据收集和预览版本”，双击“允许诊断数据”，设为“已启用”并选择“发送必需的诊断数据”。微软文档说明，策略设为必需后，设置页里的“可选诊断数据”选项会被禁用。家庭版没有组策略编辑器，用设置页的开关即可。

不建议为这件事直接停掉 DiagTrack（Connected User Experiences and Telemetry）服务。它连必需诊断数据一起停了，而微软建议依赖 Windows 更新的设备至少保留必需级别，因为关闭后更新失败的信息也不会上报。为了一个可选事件动整套服务，代价超出了需要。

关掉可选诊断数据会影响什么

微软在支持文档中说，不论是否发送可选诊断数据，设备都同样安全、正常运行。两档的区别如下：

必需诊断数据
可选诊断数据

设备配置、已安装应用与兼容性、更新是否成功、崩溃元数据等

若另行开启基于诊断数据的个性化体验，可参考的数据减少；微软称不影响安全和正常使用

对比之后会发现，可选诊断数据涵盖的范围比这次曝光的标记位大得多，比如崩溃时的内存转储可能意外包含你正在编辑的文件片段，这是微软文档自己写的。如果你介意 AI 工具名单被统计，那么更值得在意的是这一整档数据。

如果你本来就想清理预装应用、广告推荐和各种 AI 入口，站内的 Win11Debloat 介绍 [https://warpnav.com/win11debloat-windows-cleanup]讲了它会改哪些东西、怎样备份和恢复。只为这一条遥测，设置页的一个开关就够了。

另外，Windows 的诊断数据设置只管系统自带的组件。微软文档特别说明，第三方应用会用自己的方式收集诊断数据。Claude Code、Codex、Cursor 这些工具自身的使用统计，要到各自的设置或文档里找开关。常同时开几个编程代理的读者，可以顺带看看 T3 Code [https://warpnav.com/t3-code] 和 Claude Code 的 Code Mode [https://warpnav.com/claude-code-code-mode] 两篇；对隐私工具感兴趣，可以从 Privacy Guides [https://warpnav.com/sites/privacy-guides] 开始看。
