## 一、先说结论性发现（核对者最该看的）

1. **两个开关博文分得很清，二手稿常合成一个。** 功能开关（`CLICodingAgentUsage`）：作者的 Parallels ARM64 VM 上“already enabled as a service experiment”，而“The public ISO’s baseline VM had the coding-agent feature disabled by image default, so the evidence does not support saying that it is active on every Windows installation.”。可选诊断数据开关：作者在美国区域干净安装 Windows 11 Home ARM64（最新官方 ISO）里默认 “Include Optional”，`AllowTelemetry` 为 3，并说 “at least in the US setup I tested”。博文**没有说明“public ISO’s baseline VM”与“clean installation”是不是同一台机器**，也没说 VM 的区域与诊断档位；这一点原文未写。
2. **“上传”的证据是上传队列，不是网络抓包。** 作者原话：“An ETW event by itself would not establish that anything leaves the machine.”，然后“I inspected DiagTrack’s `EventStore.db` and decompressed the JSON batches in its `AsimovEvents` table”，在队列里找到事件。博文开头和结尾写“the data is uploaded to Microsoft”“your coding agent usage data is being uploaded”，措辞比证据（“queues … for upload”）强一档。博文未展示网络层抓包或微软服务端收到的证据。
3. **队列里那条事件是作者用改名的 cmd.exe 造出来的**：他把 `cmd.exe` 复制成 `codex.exe`、`gcc.exe` 运行，所以查看到的 `CliAgentSubCohorts: [4]`、`SubCohorts: [8]` 是测试产物，不是“有真正的 Codex 在跑”。博文也没写队列中的 JSON 是在哪台机器上看到的（有功能的 VM，还是干净安装机，原文未写）。
4. **记的是“见过没有”，不是“用了多久/用了什么”。** “The source events also include runtime, time in focus, interaction counters, and resource usage. This component appears to discard those details and record only a bitmap of which agents were observed.”（作者用的是 “appears to”，是推断）；“I found no prompt text or source code in this report”。
5. **判据是文件名。** “The name alone was enough for the component to recognize it as Codex.”；GCC 等一组“has no additional publisher check in this path”，Node.js/Python/.NET/VS 槽另验发行商。博文用的词是 publisher，不是“签名”。
6. **首发帖比博文更“无条件”。** 作者首发帖（北京 11-16 10:00:25）只写 “Windows starts to collect your coding agent usage information. Windows 11 build 26200.9974 checks codex.exe, … through MissionControlAggregator, then reports agent bitsets in ETW.”，没有出现 optional、默认、上传、条件；博文标题 “Windows 11 Is Collecting Data on Which Coding Agents and Developer Tools You Use” 同样无条件，条件在正文。HN 标题照搬博文标题。
7. **微软自己的文档点了“应用活动”类别、没点编码代理。** 微软 Learn（“Configure Windows diagnostic data in your organization”）：可选诊断数据含 “App activity, such as which programs are launched on a device, how long they run, and how quickly they respond to input.”；三份存档里 `MissionControl|SubCohorts|coding agent|Aggregator|Codex|Claude` **均无命中**（未点名）。同一页又写必需诊断数据是 “the default setting for Windows 10, version 1903 and later”，而作者在美国区域 OOBE 里看到的是 “Include Optional” 默认开，两者并存，原文未调和（企业配置文档 vs 家用安装界面，不替他们裁决）。
8. **截至查询时刻未找到微软回应**（见 A4）。
9. **WorkBuddy 扫描里的二手说法，我没能复现。** 见第六节“扫描说法勘误”。

## 三、可能的吠点（原文里有、线索摘要没提或说反的条件，L6 线索）

1. 功能开关与上传开关要分开：作者自己的 VM 上功能已被服务端实验开启，公开 ISO 基线 VM 上默认关闭，“the evidence does not support saying that it is active on every Windows installation”（博文 “Is it actually running on a normal machine?” 一节）。
2. 可选诊断数据默认开只是作者在美国区域 Home ARM64 干净安装里看到的：“at least in the US setup I tested”（博文末段）；其他区域未测。
3. 上传证据是 DiagTrack 上传队列里的 JSON，不是网络抓包；作者自己写 “An ETW event by itself would not establish that anything leaves the machine.” 并只验证到 “queues … for upload”（博文 “Following the report toward Microsoft”）。
4. 队列/ETW 里的事件是作者拿改名的 `cmd.exe`（`codex.exe`、`gcc.exe`）造出来的，不是真实的 Codex/Claude 运行；且为立刻抓到报告，作者把保存的窗口起点拨前 25 小时（博文 “Testing it in practice”）。
5. 判据只看可执行文件名，改名即可点亮（“The name alone was enough”）；该组件对 GCC/Clang 一组不查发行商（博文 A1-6）。
6. 报告记“见过没有”，不记时长、提示词、源码：作者只写“appears to discard those details”与“I found no prompt text or source code in this report”（A1-8）；开发工具按类别置位，不是每个可执行文件一位。
7. 作者的实验是单台 VM、单一 build（26200.9974 / DLL 10.0.26100.9818）；版本之外的机器是否有同样行为，原文未测。
8. 作者自述该发现始于让 AI 帮忙翻 Windows 二进制，再由作者在 VM 上复核（博文开头）。作者在 Binary Ninja 的开发商 Vector 35 任职（关于页，公开）；博文未提及这一点。
9. 微软文档把“应用活动（哪些程序被启动、运行多久）”列入可选诊断数据，另有抽样条款：“collecting some of the data from only a small percentage of devices (sample)”（支持页）——即便开着可选诊断数据，也不是每台设备都发每类数据；这条抽样说明是否适用于本事件，微软文档未说，原文未写作者是否查过 Diagnostic Data Viewer 的 sample 标记。
10. 微软文档称：“Regardless of whether you choose to send Optional diagnostic data, your device will be just as secure and will operate normally.”（支持页）；关闭可选诊断数据不影响系统功能（微软自述，L1）。
11. HN 评论提出的盲点（L6，原文未讨论）：这批数据只来自开着可选诊断的 Windows 用户，样本有偏（HN 评论 50525342）。
12. 上传队列只证明“在队列”；关掉可选诊断后，已记在本地 `AggregatorStorage` 的状态是否被清除，作者没测（HN 评论 50526682 提出该问题，博文无答案）。

## 六、扫描说法勘误

- **WorkBuddy：“已有转载站写‘未提供具体 build 号／任何未关闭可选诊断的 Win11 都受影响’”**：我抓取并检索的 15 篇二手稿里**没有找到这种写法**（最接近：Reveneau/bytechap 写“功能在测试配置里默认开启”，但都给了 build 号）；博文与首发帖都明确给了 build（26200.9974、DLL 10.0.26100.9818），多数转载保留了该 build。无法确认 WorkBuddy 指的是哪一站；记为**未复现**，不当事实。
- **WorkBuddy：“多篇二手稿写成 usage history”**：未找到含 “usage history”“使用历史” 的稿件；最接近的是 gptclub/Reveneau 等写 “usage”“使用记录”，且均注明只是“有没有用过”的位图。**未复现**。
- **WorkBuddy：“至少 5 家英文小站转载（Tessera、The Terminal、Cloud Updates 等）”**：The Terminal 已找到；**Tessera、Cloud Updates 未找到**（Exa 一次检索无命中，没有再追）。找到的英文转载还有 LavX、Glonce、bytechap、Reveneau。
- **“页脚日期 2026-11-16 00:00，未注时区”**：RSS 的 pubDate 注了 -0500，但那是日期占位，**不能换算成真实发布时刻**（见 A1-2）。
- **“截至 11-17 未找到微软回应”**：与我的查询一致（A4-5）。
- **HN “624 分 / 478 评”**：我 19:25:46 取到 624 分 / 481 评，约 19:3x 页面显示 483 评，评论数随时间增长，分数未变。
- **“默认是否启用（两个开关要分开）”**：与原文一致；补充一点——博文没说基线 ISO VM 与干净安装是不是同一台。
