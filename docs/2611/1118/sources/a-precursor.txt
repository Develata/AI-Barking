NGINX2Root: Critical nginx RCE Vulnerabilities (CVSS 9.2)

Flaws in nginx's HTTP/2 code give unauthenticated attackers code execution on one of the most widely used web servers, and a Linux kernel bug takes them to root. We are tracking developments as they happen.

NGINX2Root is a set of five nginx vulnerabilities disclosed on 18 November 2026. The most serious, CVE-2026-123007 (CVSS 9.2), is HTTP/2 memory corruption in nginx 1.9.5 to 1.31.8 that allows unauthenticated remote code execution; chained with a Linux SCTP kernel flaw it gives host root. Upgrade to nginx 1.30.7 or 1.31.9 now, or disable HTTP/2 until you can.

What you should do now

1Find every nginx, including ones inside appliances, load balancers, Kubernetes ingress (community ingress-nginx is retired and will not be fixed) and container images. Updating the host operating system does not patch a bundled copy.

2Upgrade to 1.30.7 or 1.31.9 (NGINX Plus 37.3.0.1 or 37.0.8.1), or your vendor's fixed package. Internet-facing servers with HTTP/2 enabled go first.

3Restart, do not just reload. nginx -s reload keeps the old binary running. Rebuild and redeploy container images; fixed official Docker images are out. Distribution packages (Debian stable, Red Hat, SUSE) are not fixed yet; Ubuntu (USN-9159-1), Alpine 3.24 and edge, AlmaLinux 8, 9 and 10 (supported streams) and all Amazon Linux versions are.

4Cannot upgrade today? Turn off HTTP/2 with http2 off; (nginx 1.25.1 and later) or remove http2 from the listen directive, then confirm from outside that h2 is no longer offered.

5Reduce the path to root: where SCTP is not needed, block the module with install sctp /bin/false in /etc/modprobe.d/ until a kernel fix ships.

6Hunt for signs of attempts: nginx worker crashes in the error log, nginx workers starting shells or new outbound connections, and long-lived HTTP/2 connections pushing very large volumes of data.

What we know so far

NGINX2Root is the name Xint gave to five nginx vulnerabilities, each with a working exploit, plus a separate Linux kernel flaw that turns code execution in nginx into root on the host. The most serious, CVE-2026-123007, is memory corruption in nginx's HTTP/2 flow control that lets an unauthenticated attacker run commands as the nginx worker. It has been in every official release since HTTP/2 arrived in nginx 1.9.5 in 2015.

A second HTTP/2 flaw, CVE-2026-123633, is a use-after-free reachable when nginx proxies HTTP/2 traffic to a backend. Wiz and Rapid7 both score these flaws CVSS 4.0 9.2 (Critical). At least five teams found them independently: Xint, Wiz, Rapid7, Metnir and Ikotas Labs.

Fixes: nginx 1.30.7 (stable) and 1.31.9 (mainline), released on 18 November, fix ten CVEs in total. NGINX Plus is fixed in 37.3.0.1 and 37.0.8.1. Exploit code: Rapid7 has published a proof of concept for CVE-2026-123007 on GitHub. Exploitation in the wild: none reported at the time of writing.

If you cannot upgrade today, turn HTTP/2 off on internet-facing listeners. That blocks the two HTTP/2 flaws, but not the other three CVEs, which affect the resolver, HTTP/3 and the mail proxy.

12:07 GMT [#update-2026-11-19-1207]·19 Nov 2026

SecurityWeek covers it; Censys clarifies its lab test is not a cheap path to RCE

SecurityWeek [https://www.securityweek.com/f5-patches-critical-nginx2root-flaws-as-poc-exploits-go-public/] reports that F5 patched 22 vulnerabilities on 18 November, including the five NGINX2Root bugs. It adds two useful limits from Rapid7 on its public exploit: on slow connections, nginx's default one-hour connection lifetime prevents exploitation, and "should an HTTP/2 connection be proxied, the precise attacker-controlled HTTP/2 frames being transmitted will likely not be retransmitted in a way that satisfies exploiting the vulnerability."

SecurityWeek also notes that Censys reproduced the CVE-2026-123007 behaviour without the huge traffic volume. Censys's own write-up [https://censys.com/blog/nginx2root-simple-test/] is more precise: its compact cleartext HTTP/2 test reaches the corrupted flow-control state so defenders can study the bug and test patches "without generating the 60 to 119 GiB of traffic reported for Rapid7's later crash and remote code execution (RCE) stages". In other words, it is a patch test, not a cheaper route to code execution. Censys also reproduced three of the use-after-free bugs and reminds readers that "disabling HTTP/2 addresses only two of the five nginx CVEs".

10:13 GMT [#update-2026-11-19-1013]·19 Nov 2026

Imperva: Cloud WAF protects out of the box; keep HTTP/2 off to your origin

Imperva has told customers that, "according to our initial analysis, Cloud WAF and WAF gateway protect out of the box against both vulnerabilities", meaning CVE-2026-123007 and CVE-2026-123633 (Imperva blog [https://www.imperva.com/blog/critical-nginx-http-2-vulnerabilities-cve-2026-123633-and-cve-2026-123007-what-imperva-customers-need-to-know/]).

As an extra layer it recommends the Cloud WAF option that uses HTTP/2 only between the client and Imperva. Traffic from Imperva to your origin then does not use HTTP/2, so attackers cannot reach the vulnerable HTTP/2 code on your nginx servers through Imperva. This is the same principle as Cloudflare's advice: the bugs are only reachable if HTTP/2 from an untrusted client lands on nginx.

The catch for any CDN or WAF: it only protects traffic that goes through it. If your origin's nginx is also reachable directly on the internet, patch it or lock it down to the provider's IP ranges.

AlmaLinux has released patched nginx packages [https://almalinux.org/blog/2026-11-18-nginx2root/] for all five NGINX2Root CVEs, backported to every nginx stream still in the RHEL life cycle. 23:45 GMT [#update-2026-11-18-2345]·18 Nov 2026

CSO Online: watchTowr says exploitation is "by no means a walk in the park"

CSO Online [https://www.csoonline.com/article/4250460/ai-unearths-internet-breaker-flaws-in-nginx-web-server.html] has covered NGINX2Root, quoting Xint CEO Brian Pak calling the headline bug "essentially an internet breaker". It also has a useful reality check from watchTowr.

"Exploitation is by no means a walk in the park, as the vulnerable systems must be directly exposed to the internet with no WAF or CDN terminating HTTP/2," Yordan Ganchev, principal threat intelligence specialist at watchTowr, told CSO. He added that an exploit has to handle different nginx versions, builds and configurations, and that against a busy internet-facing server "exploitation can cause more crashes than successful code execution." CSO also reports that Rapid7's technique relies on a glibc memory-copy routine used only on CPUs with AVX-512, which it notes are common on servers.

Miggo Security CEO Daniel Shechter made the point we keep stressing: "The version number can be wrong because distros backport fixes without changing it, a reload doesn't swap out the running code, and the attack happens in HTTP/2 traffic that WAFs and access logs never see. If you can't prove the fix is actually running, assume you're still exposed."

Censys tracker: 9.5 million nginx services exposed, under 1% fixed so far

Censys has launched a live NGINX2Root exposure tracker [https://nginx2root.censys.com/] that counts what matters for CVE-2026-123007: services on an affected version with HTTP/2 actually turned on. At its 21:21 GMT update it showed 9,482,482 nginx services exposed on their most recent scans, and just 74,782 seen fixed (on 1.30.7 or 1.31.9, or with HTTP/2 off) since disclosure, under 1%. The United States had the most, 2,128,910.

The breakdown: about 7.8 million are on an affected version with HTTP/2 on, and about 1.7 million are distribution builds with HTTP/2 on, which may carry backported fixes Censys cannot see. A further 61.3 million services are in the affected version range with no sign of HTTP/2, and around 100.9 million (91% of nginx it detects) hide their version altogether and are not counted.

This is a better measure than the version-only figures quoted earlier today (Xint's 98.9% and Censys's own 74.2 million), and it confirms the scale: millions of internet-facing servers need patching or HTTP/2 turned off, and almost none have been dealt with yet.

21:17 GMT [#update-2026-11-18-2117]·18 Nov 2026

Managed hosting: check whether your platform patches nginx for you (Laravel Forge does not)

Laravel's two hosting products show why it matters who runs your nginx. Laravel says [https://x.com/laravel/status/2123162049073250534] Laravel Cloud customers need do nothing: it has applied the fixes across the platform. But for Laravel Forge, which provisions and manages servers that customers own, it says [https://x.com/laravel/status/2123161888825733431] "Forge doesn't patch servers automatically, and we recommend users apply the fix to their servers now."

The same split applies across the industry. Fully managed platforms and CDNs patch nginx for you, while server-management tools, control panels and one-click images usually leave patching to you. If a provider set up your server, check its advisory to see which side you are on, rather than assuming it has been handled.

SANS ISC: “the new normal”, so no InfoCon Yellow, and patch faster

The SANS Internet Storm Center has explained [https://isc.sans.edu/diary/33532] why it is not raising its InfoCon threat level to Yellow for Java4Shell or NGINX2Shell, as it did for PHP2Shell last month. Johannes Ullrich writes that its Java honeypots see "many attacks, but none that exploit Java4Shell (yet)", and that these flaws should not be treated as emergencies because "They are the 'new normal'."

If nginx was compromised: what the attacker gets and what to do

Each NGINX2Root nginx flaw gives code execution as the nginx worker, usually an unprivileged account such as www-data or nginx, not root. That is still serious: the worker handles all the traffic passing through it and can reach whatever that account can, including application data, credentials and internal services. Root comes from chaining the separate, unpatched SCTP kernel bug.

If you find signs of compromise, the nginx2root.com [https://nginx2root.com/] guidance is to isolate the system, preserve evidence, work out which files, credentials and services the worker could reach, and rotate any exposed secrets. Assume the host itself may be compromised too, and rebuild from a trusted image: patching does not undo anything an attacker has already changed. Our incident response team [/services/defensive-security/incident-response] can help.

Why a WAF will not catch the main NGINX2Root bug

Xint's analysis [https://xint.io/blog/nginx2root-remote-code-execution] notes that every individual HTTP/2 message in the attack is valid: "Each increment still complies with the HTTP/2 specification." The problem is nginx's running total, which has already gone past the allowed maximum without nginx noticing.

So a WAF or IDS that checks requests or frames one at a time has nothing to match, which is why Cloudflare says it has no WAF rule for these flaws. What does help in front of nginx is something that terminates HTTP/2 itself and talks to nginx over HTTP/1.1, such as a CDN or load balancer, provided nginx cannot be reached directly. Patching remains the fix.

It is tempting to think the HTTP/2 proxy flaw only matters if your config could send traffic to an attacker. Xint's write-up [https://xint.io/blog/nginx2root-remote-code-execution] shows otherwise: its test used a single ordinary proxy_pass to a fixed backend, and the exploit rewrote the backend address in memory so nginx connected out to the attacker's server instead.

The trigger is connection pressure. Client and backend connections share each worker's worker_connections slots, and when 1/16 or fewer are free nginx starts closing idle connections, which is where the bug lies; Xint held slots open with plain HTTP/1 connections, no login needed. Checking HTTP/2 exposure: four checks, and three ways to get a false all-clear

Xint's exposure checks [https://xint.io/blog/nginx2root-remote-code-execution] for CVE-2026-123007: check the version with nginx -v; check the binary includes HTTP/2 with nginx -V 2>&1 | grep -- --with-http_v2_module (if it does not, you are not affected by this flaw); look for http2 in nginx -T; and from outside your network run openssl s_client -connect HOST:443 -servername HOST -alpn h2, where "ALPN protocol: h2" means HTTP/2 is reachable.

For the HTTP/3 flaw (CVE-2026-121810), remove the quic listeners, set http3 off;, send Alt-Svc 'clear', and check nothing still listens on UDP 443 with ss -lunp.

For the resolver flaw (CVE-2026-123634), point proxy_pass at a fixed upstream group instead of a variable. 17:37 GMT [#update-2026-11-18-1737]·18 Nov 2026

The kernel bug: one compromised container can mean every container on the host

The sixth NGINX2Root bug is a use-after-free in the Linux kernel's SCTP code, present since 2018 and still unpatched. Xint says it gives both a memory leak that defeats kernel ASLR and an arbitrary function call in the kernel, and that an attacker running as the nginx worker could reliably get root, including from inside a Docker container.

The worrying detail: on many Linux distributions the SCTP module is installed by default and loads automatically the first time any program opens an SCTP socket. All containers share the host kernel, so where SCTP is reachable a single compromised nginx container can lead to control of the host and every container on it.

Until a kernel fix ships, block the module on hosts that do not use SCTP with install sctp /bin/false in a file under /etc/modprobe.d/, and check whether it is already loaded with lsmod | grep sctp, as the block does not unload it.

17:35 GMT [#update-2026-11-18-1735]·18 Nov 2026

How the main bug works, in plain English

HTTP/2 lets a client tell the server how much data it is ready to receive, a "send window". Xint's analysis [https://xint.io/blog/nginx2root-remote-code-execution] shows nginx can hand the same credit back twice. The attacker gets nginx to queue response data it cannot send, tops the window back up with a WINDOW_UPDATE frame, then cancels the streams with RST_STREAM, and nginx returns the queued credit a second time without checking the maximum.

Once the window is over its limit, a later check wraps round to a huge number and nginx accepts any further increase. The window is then treated as a small negative number, which turns into an enormous copy length. That lets the attacker leak memory addresses in a response, corrupt memory, and replace a cleanup function nginx runs when the connection closes, so their command runs as the nginx worker.

17:34 GMT [#update-2026-11-18-1734]·18 Nov 2026

How to hunt for NGINX2Root attacks: your access logs will not show them

The attack uses HTTP/2 WINDOW_UPDATE and RST_STREAM control frames, which nginx does not log as requests and TLS encrypts, so normal access logs show almost nothing. Xint's investigation guide [https://xint.io/blog/nginx2root-remote-code-execution] suggests four places to look instead.

First, connections: run ss -tinp state established '( sport = :443 )' twice and look for a single client connection open for minutes with bytes_received climbing fast while little is sent back, plus many short TLS connections from the same IP. Second, add a log format that records $connection, $connection_requests and $request_length, and compare logged request sizes with the bytes actually received.

Third, and the clearest sign of success: any program started by an nginx worker. Add an auditd rule on the worker's UID for execve and watch for /bin/sh or /bin/bash. Fourth, failed attempts can crash workers, so check grep -Ei 'worker process.*exited|signal 11|segfault' /var/log/nginx/error.log and coredumpctl list nginx.

NGINX2Root key facts

Main CVE

CVE-2026-123007, HTTP/2 flow control memory corruption. CVSS 4.0 9.2 (Critical); F5 rates all five NGINX2Root CVEs 9.2.

Affected

nginx 1.9.5 to 1.31.8 with HTTP/2 enabled. NGINX Plus 37.x before 37.3.0.1 and 37.0.8.1, and R34 to R36, which get no fix.

Fixed in

nginx 1.30.7 (stable) and 1.31.9 (mainline), released 18 November 2026.

Impact

Unauthenticated remote code execution as the nginx worker; root on the host when chained with an unpatched Linux SCTP kernel flaw.

Exposure

Censys counts about 8.8 million nginx services on an affected version with HTTP/2 on (19 November, 09:06 GMT), with about 425,000 fixed since disclosure. Public proof of concept from Rapid7; no exploitation in the wild reported yet.

Workaround

Disable HTTP/2 on every internet-facing listener until you can upgrade.

Why this one is different: pre-auth RCE in nginx is rare

nginx serves roughly a third of websites whose web server can be identified, and it has been fuzzed and audited for two decades. Xint says the best known previous pre-authentication RCE in nginx dates from 2013. This time five teams, several using AI-assisted tooling, found the same HTTP/2 bugs within weeks of each other.

When that many people find a bug independently, assume others have too. With exploit code now public, the gap between disclosure and attack attempts will be short.

NGINX2Root frequently asked questions

What is NGINX2Root?

NGINX2Root is the name Xint (Theori) gave to five nginx vulnerabilities disclosed on 18 November 2026, CVE-2026-123007, CVE-2026-123633, CVE-2026-123634, CVE-2026-121810 and CVE-2026-113425, plus a separate Linux kernel SCTP flaw. Each nginx flaw has a working exploit for code execution as the nginx worker, and chaining one with the kernel flaw gave root on the host, including from inside a Docker container.

Which nginx versions are affected by CVE-2026-123007?

Official nginx releases from 1.9.5 to 1.31.8 are affected, which covers every release since HTTP/2 support was added in 2015. A server is only exposed if nginx is built with HTTP/2 and a listener accepts HTTP/2 connections. NGINX Plus 37.x releases before 37.3.0.1 and 37.0.8.1 are also affected, as are NGINX Plus R34 to R36, which F5 will not fix. BIG-IP, BIG-IQ and F5OS are not affected. Distribution packages may have backported the fix without changing the version number, so check your vendor advisory.

Which versions fix NGINX2Root?

nginx 1.30.7 (stable) and 1.31.9 (mainline), released on 18 November 2026, fix all five NGINX2Root CVEs and five other nginx CVEs. For NGINX Plus, upgrade to 37.3.0.1 or 37.0.8.1; there is no fix for R34 to R36, so move those to 37.x. Restart nginx after upgrading: a configuration reload does not load the new binary.

Does disabling HTTP/2 protect against NGINX2Root?

Partly. Disabling HTTP/2 blocks the two most serious flaws, CVE-2026-123007 and CVE-2026-123633. It does not address CVE-2026-123634 (resolver with mirror), CVE-2026-121810 (HTTP/3 proxying) or CVE-2026-113425 (mail proxy auth_http). On nginx 1.25.1 and later set http2 off; in each server block; on older versions remove http2 from the listen directive. Then reload and confirm from outside that the server no longer negotiates h2.

Is NGINX2Root being exploited?

At the time of writing no exploitation in the wild has been reported. However, Rapid7 has published a proof-of-concept exploit for CVE-2026-123007 on GitHub, and Xint and Wiz both have working exploits they are not releasing. Public exploit code usually brings scanning and attack attempts within days. Beware fake exploits on GitHub: some carry malware, so only test code you have read, in an isolated virtual machine.

How do I check if my nginx server is vulnerable?

Check the version with nginx -v, then whether HTTP/2 is active: look for http2 in your listen directives or an http2 on; directive, and test from outside with openssl s_client -alpn h2 against the host. Also check for resolver with mirror, HTTP/3 proxying and the mail proxy with auth_http, which are affected by the other three CVEs. For distribution packages, appliances and container images, rely on the vendor advisory rather than the version string.

Does a CDN or load balancer in front of nginx protect me?

Cloudflare says origins reachable only through its HTTP proxy are protected while you update, as it terminates HTTP/2 and HTTP/3 at its edge (not for Spectrum, DNS-only records or mail). More generally, only if it terminates HTTP/2, forwards requests to nginx over HTTP/1.1, and direct access to nginx is blocked. Then the HTTP/2 flaws cannot be reached through it, and Rapid7 says its exploit probably fails over proxied HTTP/2. If the front end uses TLS passthrough or speaks HTTP/2 to nginx, nginx is still exposed. nginx is also often the load balancer itself. Patch regardless.

Is NGINX2Root the same as CVE-2026-123007?

CVE-2026-123007 is the headline NGINX2Root flaw, but NGINX2Root covers five nginx CVEs: CVE-2026-123007 (HTTP/2 flow control), CVE-2026-123633 (HTTP/2 use-after-free), CVE-2026-123634 (resolver use-after-free), CVE-2026-121810 (HTTP/3 use-after-free) and CVE-2026-113425 (mail proxy use-after-free), plus a Linux kernel SCTP flaw without a CVE at disclosure. Wiz and Rapid7 refer to the HTTP/2 flaws by CVE number rather than the NGINX2Root name.

What can an attacker do with NGINX2Root?

Each nginx flaw lets an unauthenticated attacker run commands as the nginx worker process. From there they can read application data, credentials and secrets the worker can reach, and talk to internal services. Chained with the Linux SCTP kernel flaw, Xint reached root on the host, including escaping a Docker container.

Am I safe if nginx is only on my internal network?

No. Restricting access limits who can reach nginx but does not remove the flaw. An attacker who already has a foothold inside your network could use it to move laterally. Include internal nginx servers, ingress controllers and reverse proxies in your patching.

Will disabling HTTP/2 break my application?

Most browsers and web clients fall back to HTTP/1.1, possibly with some loss of performance. gRPC needs HTTP/2, so gRPC services behind nginx will stop working if you turn HTTP/2 off. Test before changing production, and patch instead where HTTP/2 is required.

Can a WAF or rate limiting replace patching?

No. Web application firewall rules inspect URLs and request bodies, but the HTTP/2 flaws are triggered by low-level control frames such as WINDOW_UPDATE and RST_STREAM. Use a WAF or connection limits only alongside patching or disabling the affected features.

How do I tell if my nginx server was attacked?

Ordinary access logs do not record the HTTP/2 control frames used in these attacks, so a clean access log proves nothing. Look at the nginx error log for repeated worker crashes, process execution records for nginx workers starting shells or other programs, and network data for long-lived HTTP/2 connections moving unusually large amounts of data. If you confirm compromise, isolate the host, rotate any secrets the worker could read, and rebuild from a trusted image.

Who found NGINX2Root?

Xint, the AI security platform from Theori, found and named NGINX2Root: researchers Soomin Shin, Joohyun Park, Tim Becker and Yves Bieri. The two HTTP/2 flaws were also found independently by Wiz Research, Rapid7 (Stephen Fewer), Metnir and Ikotas Labs.

Does patching nginx close the whole NGINX2Root chain?

It closes the remote entry point. The Linux kernel SCTP flaw that escalates from the nginx worker to root is separate and had no kernel patch at disclosure. Until one ships, Xint suggests blocking the SCTP module from loading with install sctp /bin/false in /etc/modprobe.d/, where SCTP is not built into the kernel and not already loaded.
