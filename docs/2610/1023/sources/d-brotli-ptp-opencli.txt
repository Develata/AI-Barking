The bug can cause crashes, disclose memory, or allow code execution.Check web services, background workers, tools that bundle Node.js or Bun, and deployments of Envoy Proxy or Istio configured to decompress Brotli.Other software to checkEmbedded runtimes: apps such as Electron-based desktop tools can include multiple Brotli copies. Check both Chromium and Node.js; a fixed browser component does not establish that the embedded Node.js runtime is fixed.Native clients and bindings: check the decoder loaded by curl/libcurl, Python and Java bindings, and other native libraries. Bundled wheels and static binaries may need their own update or rebuild.File processing: include font decoders and data-file readers that use Brotli. Exposure is not limited to HTTP traffic.Using Brotli only to compress outgoing data does not by itself establish exposure to this decoder flaw.Disable Brotli decoding until you can patchYou can keep other compression enabled. Disable Brotli decoding of untrusted data while allowing gzip, deflate, or other supported codecs. Apply this to every decoding path; if your stack cannot block Brotli separately, disable automatic decompression or pause that path until patched.Incoming requests: reject requests with Content-Encoding: br before any proxy, middleware, or body parser decompresses them. Cover direct-to-origin and alternate routes.Fetched responses: disable automatic Brotli decompression in HTTP clients. Reject Brotli responses before decoding; if your client cannot do this, pause the affected fetch or use a patched client. Removing br from Accept-Encoding alone does not stop a server from sending it.In Envoy Proxy and Istio, disable Brotli decompressor filters for both requests and responses. Disabling a filter can pass compressed data onward, so protect downstream decoders too.Files and other inputs: pause untrusted Brotli processing until the decoder is patched.Turning off Brotli response compression on a CDN or web server does not disable request or client-side decompression. Request-size limits and WAF rules alone do not cover every decoding path.Express: reject Brotli, keep gzip and deflateAllow only uncompressed, gzip, or deflate request bodies before any parser runs. Keep automatic decompression enabled for those permitted encodings.Express request encoding guardCopy// Register before every body parser or decompression middleware. app.use((req, res, next) => { const encoding = (req.get('Content-Encoding') || 'identity') .trim().toLowerCase(); if (!['identity', 'gzip', 'deflate'].includes(encoding)) { return res.status(415).send( 'Use gzip, deflate, or an uncompressed request body.' ); } next(); }); // Keep your existing parser options and register routes afterward. app.use(express.json()); app.use(express.urlencoded({ extended: true }));Place this guard before all JSON, form, raw, text, and route-specific parsers. It rejects Brotli, unknown encodings, and stacked encodings such as gzip, br with HTTP 415. A proxy that decodes requests first needs its own mitigation.If you cannot enforce the guard before decoding, set inflate: false on every existing body parser as a fallback.
