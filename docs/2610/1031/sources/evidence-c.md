## 二、可能的吠点（线索，原文有、线索摘要没提或说反的条件与限制）

1. 默认不会“没人 @ 也自己干”：官方默认接受模式是 `observe`，只记录“本来会接”，不执行（docs/002、SETUP.md、`src/policy.ts` 默认值）；要主动干活得切到 `auto` 再自己写规则；飞书默认只收 @（SETUP.md）；默认只有 `copy`、`visual` 两条规则，不含“复现并修 bug”（`src/policy.ts`）。截图 27、29。
2. “没人 @ 它就修 bug、提 PR”是文章里 DeepSeek 内部实例的描述（§1、§3.4），而 README 明说发布版 “not identical to our internal version”。截图 25。
3. “7×24/24/7/always-on”不是 DeepSeek 原文措辞：仓库零命中；文章写的是设计特征 “always online/persistent”，且 §5“云端无状态计算+端点守护进程”与 §6 Watchdog 在仓库里关键词零命中；原型靠运营者本机上的一个 DSH profile，另一个 profile 每小时检查它是否还活着（SETUP.md、docs/006）。
4. “大部分由 agent 写”只有 README 一句自述；仓库只有 1 个 squash 提交、无 Co-authored-by，提交记录无法验证比例。截图 33。
5. 安全面：官方文档自己写 “Both presets run with `danger-full-access` as the operator's OS user”，worker 能读运营者主目录；建议另建专用系统账号。截图 28。
6. 实验限制：文章自己写 “indicative only”，合成负载、5 次运行、编码工作由“只消耗时间的工具”模拟；对比的是调度而不是写代码能力；代价是 token（去掉直通后缓存读取 23.2M→31.8M）。实验代码不在仓库。
7. 设置门槛：需要专用 GitHub 账号、DeepSeek Harness profile、模型提供方，且“设置步骤多，由另一个 coding agent 带你做”（README、SETUP.md）。费用没有任何公开数字。
8. 仓库关闭了 Issues（API `has_issues:false`），没有公开的 bug 反馈入口，而 README 自称 “It may still contain bugs”。
9. 自媒体稿 “99 个疑似 Super-agent 的分支” 是作者自己的推断（原文 “公开仓库看不到 PR 的描述，所以这 99 个只能算疑似，是我的推断”），不是 DeepSeek 数据；不进正文（L5）。
10. 社区质疑（L6）：HN 三帖共 0 条评论，没有可摘的高赞评论；Reddit 未取到（需登录）。AGTP 帖里的批评句只有 “Critics say the framing is about replacing slow humans with agents running many sessions at once.”（原句，无评论链接，只作线索，不采信）。
