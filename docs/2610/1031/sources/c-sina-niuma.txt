别人家的 AI，已经不用艾特 @ 就能主动干活了。

DeepSeek Harness 的内部用户群里，就潜伏着这么一位 AI 牛马。没人 @ 它，它 7x24 小时在线。这时如果有用户抱怨了一个 Bug，它会默默跑去后台复现、排查、修复，等它开口，PR 都已经提交了。

10 月 31 日，DeepSeek Harness 团队发表了一篇长文，把这种 AI 称作 Super-agent（超级智能体），连原型代码都开源了。

长文晒出了三个案例。

我顺着 DeepSeek Harness 公开的提交记录仔细查看了一番，疑似它留下的脚印，将近 100 个。

上面图里的这个双击 Bug 把用户坑得不轻，「我每天会误触发几十次。」

Super-agent 自己查明了原因，还附上了修复前后的对比截图。

波浪号渲染的 Bug，它反应更快。

模型输出里的波浪号被渲染成了删除线。群里还在争论该在训练里解决，还是该修改渲染规则，Super-agent 的 PR 已经提交了。

这种 AI，谁看了不迷糊？

我顺手查了查 DeepSeek 这位 AI 牛马平时到底干了多少活。

DeepSeek Harness 的公开仓库关闭了 PR 功能，但提交记录里还留着分支名。

开源的原型代码又规定，Super-agent 接的每个任务都是一个工单，工作区名字后面都要带上工单 ID 的前 12 位。

于是我按照这个格式去查代码分支名，DeepSeek 长文里晒的那三个案例全都对应上了。

这种带 12 位后缀的分支，从 9 月 14 日起，截至 10 月 29 日，一共合并了 99 个 PR， 仅 10 月就有 75 个，这 AI 是真的卷。

公开仓库看不到 PR 的描述，所以这 99 个只能算疑似，是我的推断。

其中多少是被人 @ 了才接的活，也看不出来。

这 99 个分支大多是小修小补，比如统计信息显示不全时，鼠标悬停上去要能看到完整内容；深色模式下，鼠标移到设置导航上没有反应；Mac 端的菜单离按钮太远。

其中一个分支还被同事回滚了，这种待遇，AI 牛马也逃不过。

这批分支几乎全挂在同一个 GitHub 账号下，账号简介写着 they're made out of meat，他们是肉做的。

这是 1991 年一篇科幻短篇小说的标题，讲两个外星人死活不信宇宙里有会思考的肉。账号背后是员工本人还是智能体，公开记录看不出来。

DeepSeek 为什么要打造 Super-agent？你多开几个 Agent 窗口就明白了。

我平时开着大概 10 个 Agent 终端窗口，一旦真正同时跑起来，最多 4 个左右就管理不过来了。这个等你确认，那个已经跑完了，还有一个跑偏了你都不知道。

DeepSeek 的观察也差不多，「一个人通常只能同时跟进 3 到 5 个活跃 Session。」Session 就是你开的一个个 Agent 窗口。

网友，「我要给我们领导看看，dsh 的大神也只能同时跟进三五个，你指望我们眼观六路耳听八方 10 个 session 并行推进是在想屁吃。」

DeepSeek 给出的解释听起来有点扎心，「单任务的上限取决于模型能力，多任务的上限取决于人的注意力。」

模型越能干，拖后腿的反而是你自己。

所以 DeepSeek 想让 Session 从你眼前消失。「让用户手动管理 Session，在很大程度上是从底层 LLM API 延续下来的设计惯性。」今天的编程智能体基本都是这样设计，连 DeepSeek 自家的 Harness 未能幸免。

解决办法是把 Super-agent 拆成两层。

上面一个常驻的 Router，相当于包工头，所有消息它都能看到，但它只负责派活，不碰具体任务。下面一群 Worker，就是牛马，一个牛马只专注干一件事，干完向工头汇报。

你面对的始终只有这一个工头。

Router 用较轻量的模型往往就够了，Worker 才配置能力最强的模型。

那工头会不会忙到死？

DeepSeek 做了压力测试，需要它拿主意的消息从每分钟约 1 条涨到 40 条，积压的消息会合并成一批处理，单个决定分摊的推理时间，反而从 6.4 秒降到了 1.6 秒。这个包工头，越忙越快。

并且，用户群里的消息会先被筛选一遍，再交给模型判断。模型判断值得动手，Super-agent 也不吭声，先在后台试试。这招叫「投机执行」，有结果就交付，没结果就当没发生过。

你可能会想，我让 Claude Code 开子智能体（Subagent），不也一样？

DeepSeek 团队还真做了实验，只是没写用的哪家工具和模型。300 条消息里混着 20 个工作请求，测试模型的调度能力。

单个 Session 搭配 Subagent 工具，提示词写得很中性，「合适的时候，把活交给 Subagent。」5 次运行，模型一次都没调用过 Subagent。活全自己干，干到一半被新消息打断，回头接着干。

DeepSeek 换了一版提示词，明确要求尽量把每个任务都委派出去，自己只做点轻量活。这回 5 次里有 4 次委派了，剩下那 1 次，模型判断这活「很小」，又自己干了。

拆成两层的 Super-agent，95% 的任务在 15.7 分钟内完成，单个 Session 要 29 分钟以上，差不多慢了一倍。

代价是 token。

Super-agent 单次实验读取 2323 万缓存 token，单个 Session 只要 605 万，前者是后者的 4 倍。

这个差距绝对值听着吓人，可按 DeepSeek-V4.1-Flash 的缓存命中价算，每百万 token 空闲时段 0.02 元、高峰时段 0.04 元，多出来的 1718 万 token，也只多花 3-7 毛钱。

不过这种打法，缓存够便宜才玩得起。

架构未必抄得来，Super-agent 原型仓库里的提示词，倒是拿来就能用。

DeepSeek 给这个原型制设定的核心原则是，「尽可能少占用人的注意力，尽可能多带来价值。」一个能替全团队干活的 AI，也能浪费全团队的注意力，所以提示词花了大段篇幅治它的话痨。

群里单次回复不超过 100 词，超过了发送通道直接拒收。为了防止它钻空子，长句、一串分号、列表、连发几条，一律不许用。

原仓库采用 MIT 协议，下面这几段提示词你可以放进你的 CLAUDE.md 或者 AGENTS.md 试试。

干活时默认不出声。主动发消息只有三种情况，结果可以验收了、需要人来处理、确定干不成了。中途进度不往外发。发送前每个分句都问一遍，删了它，对方还能看懂结果、知道下一步吗？能，就删。绝不说「我来处理」这种废话。技术选型、文件路径、测试数量，一律不写进消息，留在 PR 里。已经授权的活不要再请示，常规实现细节不要问，同一个决定不要反复问，没变化的状态不要重复发。自动评审机器人也会出错，它的意见只作参考。别追着它求通过，每个 PR 最多回应它三轮。发到 GitHub 的每条消息，第一行都必须写上「这是自动化智能体写的，不是人写的。」

Super-agent，什么时候能用上？

Super-agent 目前已经开源，不过只是研究原型，得搭配 DeepSeek Harness 使用。

先把 GitHub 仓库克隆到本地，再对你的 Agent 说，「读这个仓库里的 SETUP.md，安装 dsh-superagent。」

账号这类事得你自己动手，比如给 Super-agent 单独注册一个 GitHub 账号。

Super-agent 原型只监听一个 GitHub 仓库，群聊可以选配飞书，没人 @ 它的消息默认都收不到，打开全量接收，也只记一笔「本来会接」，不动手。想要它静默修复 Bug，得切换到 auto 模式，再自己写规则。

Super-agent 传送门：https://github.com/deepseek-ai/dsh-superagent-prototype

7x24 小时常驻的智能体，又多了一个 Super-agent。
