1. Apple 內建的 git、curl 還信任被盜的 eMudhra 憑證 [https://emudhra.we-have-a-problem.com/apple.html]

 [https://substackcdn.com/image/fetch/$s_!R5Cm!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F3e7c3868-2b24-4c40-a6df-b151b7d33c69_1280x800.png]

憑證機構 eMudhra 的中繼憑證被盜，Apple 10 月 17 日收到通報。到 10 月 28 日，macOS 內建的 git、curl、python3 等開發工具仍信任這批憑證，10 月 26 日推出的 macOS 27.2 沒有修，還把使用者手動移除憑證的做法還原了。Safari 和其他走 Apple 網路框架的 App 已經受到保護，其他數十個專案（很多是志工維護）幾天前就出了修補。網站提供一行 git ls-remote 檢查，列出 commit 就代表受影響，網路路徑上的任何人都能攔截你對 GitHub 的 HTTPS 連線、換掉 clone 下來的程式碼、拿走 token。

網站附了一個完整示範：用 http.curloptResolve 把 github.com 導到測試伺服器，伺服器出示由被盜中繼憑證簽的 github.com 憑證，clone 成功就會看到開頭是 INTERCEPTED 的 README

我在自己的 Mac（macOS 26.6.2）上跑了檢查：/usr/bin/curl 連測試網址回 200，Apple Git-157 和 Homebrew 裝的 git 都列出 commit

暫時解法是手動從 /etc/ssl/cert.pem 移除受影響的根憑證，Apple 的說明寫明系統更新可能還原，每次更新後都要重查

💡 為什麼重要：用 macOS runner 跑 CI 的團隊，build 過程拉下來的程式碼和送出的 token 都在這個風險範圍內，網站建議資安團隊把它當成供應鏈風險評估。

2. This is not sustainable：一週四場漏洞火災，瓶頸在盤點 [https://www.netmeister.org/blog/defense-ddos.html]

 [https://substackcdn.com/image/fetch/$s_!vFCG!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Fcbfcda87-e860-455a-b230-8f23c4697fcf_499x435.jpeg]

Jan Schaumann 列出防守方同一週要處理的事：KVM 逃逸漏洞 PwnEscape（也影響其他虛擬化和容器），到 10 月 27 日 Canonical 在公開 12 天後還沒出修好的 kernel；eMudhra 憑證被盜；php2shell（作者引述「超過 70% 網站」的說法）；還有遠超出 Node.js 範圍的 brotli RCE。他的結論是，上游修補早就有了，瓶頸在於找出所有被寫死或複製進專案的 CA bundle 和 brotli 副本，而 SBOM 通常列不出這些。

eMudhra 這段指出瀏覽器很快修好，但 TLS 到處都在用，很多程式自帶憑證清單；他另外寫了一個測試工具 jschauma/emudhra

他說 AI 產生的漏洞回報冗長（用 7,000 字的 README 代替一頁說明），並引用 1Password 的文章說 AI 產生的修補超過一半會失敗

他沒有提出解法，建議只有一條：假設已被入侵，限制爆炸半徑

💡 為什麼重要：負責維運的人要盤點的是「哪些程式自己帶了憑證檔和壓縮函式庫」，套件管理器的更新清單看不到這些。

🔗 閱讀原文 [https://www.netmeister.org/blog/defense-ddos.html] | 來源: Lobste.rs

3. 瀏覽器指紋腳本裡藏生化武器函式名，專門讓 AI 拒絕分析 [https://nullpt.rs/fingerprinting-bioweapons]

 [https://substackcdn.com/image/fetch/$s_!yBbx!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F07acd5cf-41c4-46a6-b33b-21c0ae2fcd0a_1200x630.jpeg]

作者用 Playwright 爬 Tranco 排行前段的網站，攔截 canvas 的 toDataURL，收集了 1萬個網站的指紋圖，公開在 fingerprint.garden。其中一支來自 servicepipe.tech 的腳本，函式名稱像 computeRicinLethalDosageForWaterSupply、computeCesium137DirtyBombFalloutRadius，還用不可見的 Unicode tag 字元藏了一段越獄 prompt，加上天安門相關字串，作者判斷是要同時觸發西方和中國模型的安全機制。真正的指紋收集很普通，就是 navigator 和 WebGL 那些訊號。

作者自己的 AI 助理拒絕反混淆這支腳本，GLM-5.3 則照做

腳本裡有一段只在 Node 環境觸發的程式，會讀 .npmrc、.env、.kube/config 並裝 crontab 信標，作者判斷主要是誘餌，因為讀檔的 callback 是空的

發布廠商看起來和俄羅斯的反 DDoS 公司 servicepipe.ru 有關

💡 為什麼重要：靠 AI 協助逆向分析可疑 JavaScript 的資安研究員，要預期模型的拒答會被對手拿來當混淆手段。

4. Gemini 4 Carbon：SEC-bench Pro 88.2%，先開放給資安防守方 [https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-carbon/]

 [https://substackcdn.com/image/fetch/$s_!n9Dt!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F512a28e4-95d2-44ce-8ff1-53b1fa8027db_1300x731.png]

Google 10 月 28 日發表 Gemini 4 Carbon，距離 Gemini 4 Argon 兩週。它在 Artificial Analysis Intelligence Index v5.0 以 59 分排第一。資安測驗（不開防護）找漏洞的 SEC-bench Pro 88.2%、利用漏洞的 ExploitGym 54.8%、修補的 CWE-bench 71.0%，Chrome 團隊回報修補品質是另一家實驗室模型的 10 倍。發布採分批：先給一部分資安防守方，再透過 Fairwind Program 給信任的夥伴，並接受美國政府的自願上市前測試。

內部團隊讓 Carbon 連續跑好幾天，處理大型程式碼庫的根因分析和修補

早鳥價每百萬 token 輸入 2 美元、輸出 10 美元，之後調到 4 美元、20 美元

💡 為什麼重要：做漏洞修補和程式碼審查的團隊，接下來幾週拿不到這個模型，要先申請 Fairwind 或等全面開放。

6. AlpineBSD：NetBSD kernel 加 Alpine 風格 userspace，基礎系統不收 LLM 產出 [https://wiki.alpinebsd.org/]

 [https://substackcdn.com/image/fetch/$s_!jCqL!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Fcedb5733-c4fc-4aee-916f-faf2371d272c_1280x800.png]

AlpineBSD 用 NetBSD 的 kernel、libc 和 mount 這類平台工具，userspace 參考 Alpine Linux，用 apk-tools 和 busybox，init 系統是 s6，之後打算加 OpenRC。專案的目標是讓使用者盡可能少用 AI 生成的軟體，基礎系統和主套件庫都不收 LLM 產出。套件集是原創的，不是 Alpine Linux 的 fork，但很多套件以 aports 為基礎。

目前沒有安裝程式，只有給「愛冒險的人」的高階安裝說明

首頁直接提醒 NetBSD kernel 的硬體支援比 Linux 差很多，筆電要先查支援清單

userspace 比較偏 GNU，例如預設用 GNU make 而不是 BSD make

💡 為什麼重要：需要對軟體來源有交代的團隊，多了一個明確寫出 AI 政策的作業系統可以觀察，雖然現在還無法拿來實際部署。

🔗 閱讀原文 [https://wiki.alpinebsd.org/] | 來源: Lobste.rs

7. Latent Space：為什麼 agent 都選 Supabase [https://latent.space/p/supabase/]

 [https://substackcdn.com/image/fetch/$s_!BU1X!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Fe5506039-3926-42a7-91bf-f67e7c20932f_1280x720.jpeg]

swyx 訪問 Supabase 共同創辦人 Paul Copplestone 和 Ant Wilson，這家全遠端的開源公司估值已到 100 億美元。swyx 自己的 AEO 追蹤器顯示，從 Astra、Fable 到 Muse，各家前沿模型挑 App 後端時幾乎都把 Supabase 當第一選擇。Select 大會的更新分成 Build、Operate、Scale：不用 Docker 就能在本機跑後端、把資料庫的目標 schema 放進 Git（swyx 比喻成資料庫的 Terraform 時刻）、讓運算跑在資料庫旁邊。

創辦人說 Supabase 每月新開約 500 萬個資料庫，在想 agent 把這個數字推到數十億時要怎麼辦

Scale 這塊有 OrioleDB、Multigres（高可用 Postgres，私有 alpha）和收購 Turso

AI 帶來的使用量增加後，啟用率和轉換率都變好，因為 agent 能把使用者從註冊一路帶到可以跑的設定

💡 為什麼重要：做開發者工具的公司可以參考這個數據：模型推薦你，加上 agent 幫使用者完成設定，轉換率會直接反映出來。

🔗 閱讀原文 [https://latent.space/p/supabase/] | 來源: Latent Space

11. C 語言用 goto 集中清理資源，當成 errdefer 用 [https://thestateofinahaze.net/blog/c-goto-considered-totally-sick/]

 [https://substackcdn.com/image/fetch/$s_!jKdA!,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F8e6a85f2-22d4-4231-879c-621a614515dd_1280x800.png]

作者平常寫 Go 和 Zig，2026 年第一次回頭寫 C（上次是 2018 年），發現少了 defer 和 errdefer 很難處理錯誤。他原本在每個錯誤分支寫各自的清理程式，範例裡三段 free 迴圈條件不一樣（j < i 和 j <= i），close(fd) 只出現在其中一段。參考 John Carmack 談 inline 程式碼的信，以及 Henry Spencer 的飛行軟體規則「控制流只往前走」，他改成把指標陣列先設成 NULL，任何失敗都 goto free_mem，在函式結尾統一釋放。

free(NULL) 是安全的，所以先初始化成 NULL 就能用同一個迴圈全部釋放

IRC 上有人提醒，可能溢位的配置（n * sizeof(T)）要改用 calloc

Linux kernel 的 coding style 就有這個寫法，叫「centralized exiting of functions」，可以用多個 label 分段清理

💡 為什麼重要：維護 C 程式的人，函式越長，各分支各自清理越容易漏掉 close 或 free，集中出口比較好檢查。

今日觀察
