Codex CLI Ships a Persistent Daemon Without Warning in 0.157.0

Published by Andrés Morales [https://elsolitario.org/en/author/andres_morales/] on 12 October, 202612 October, 2026

⏱️ Reading time: 10 min

Since version 0.157.0, the Codex CLI daemon [https://elsolitario.org/2026/10/12/codex-cli-daemon-auto-start-opt-in/] starts on its own: every interactive session leaves a background process running that survives closing the terminal and auto-updates every hour. The change shipped without explicit notice in the changelog and sparked a direct complaint to OpenAI: issue #48195 [https://github.com/openai/codex/issues/48195], opened on September 25, 2026 in the Codex repository, asks for that behavior to be opt-in instead of enabled by default.

What Codex CLI Is

Codex CLI is OpenAI’s tool for coding with AI agents from the terminal: it reads files, runs commands, and holds multi-turn conversations with a model. It installs as the npm package @openai/codex, and since version 0.157.0, every interactive session activates a Codex CLI daemon in the background.

The project is open source and ships as an npm package under @openai/codex, with native builds for different platforms. The CLI competes with tools like GitHub Copilot CLI or Claude Code, and OpenAI has been adding a Remote Control mode to manage sessions from a phone or the web, which requires a backend shared across devices.

What Happened With the Codex CLI Daemon

The reporter, a GitHub user identified as Yihua-Liu-1997, documented the behavior after updating to version 0.157.0, installed with npm install -g @openai/codex on Linux via WSL2. According to the report, opening an interactive codex session triggers three actions that didn’t happen before.

First, it starts codex app-server --managed-daemon in its own session, with no associated terminal, and the process gets reparented to PID 1: it stays alive after closing each Codex window, until someone runs codex app-server daemon stop or the machine reboots. Second, it copies the complete platform package (about 374 MB, including the codex binary, codex-code-mode-host, and bundled versions of bwrap, zsh, and rg) to ~/.codex/packages/app-server-daemon/releases/<version>/, an identical copy of what npm had just installed, and runs the daemon from that copy. From that point on, the backend version is decoupled from whatever the user installed via their package manager. Third, it launches an independent updater (codex app-server daemon pid-update-loop) that checks for updates 5 minutes after starting and then every hour, downloads new versions, and restarts the backend.

That automatic restart can kill an agent’s active turns mid-execution, a problem documented separately in issue #40969 [https://github.com/openai/codex/issues/40969], which details that the update forces a shutdown after a 60-second wait budget and that, on top of that, it can’t be disabled. The reporter also describes a subtle side effect: the daemon locks in the environment of the session that first started it. If that first session had set a variable like HTTPS_PROXY to route through a corporate proxy, the daemon keeps using that proxy for all outbound connections, regardless of what variables later sessions launch with. Issues #42457 [https://github.com/openai/codex/issues/42457] and #37537 [https://github.com/openai/codex/issues/], which document hooks that receive the daemon’s working directory or terminal instead of the actual session’s, might share the same root cause.

Context and History

The issue was opened on September 25, 2026, and within the first few hours other developers confirmed the same behavior in different environments. One user wrote that nothing should be spinning up mysterious servers and processes out of nowhere on a minor version bump without telling people, a comment that gathered 9 reactions. Another user was blunter, calling the CLI unusable until it’s fixed, a comment that drew 10 reactions. A third user confirmed the problem on Windows 10 LTSC with the same 0.157.0 version and found that setting daemon_auto_start = false in config.toml resolves the symptom, though they also asked that the CLI fall back to local mode when the daemon’s startup is blocked by permissions, instead of requiring the --no-daemon flag manually.

The complaint isn’t isolated. Previous issues had already touched on pieces of the same problem: #41188 [https://github.com/openai/codex/issues/41188] asks for Codex to support externally managed daemon executables instead of always copying its own; #46468 [https://github.com/openai/codex/issues/46468] describes an npm update leaving app-server on an old version without the daemon recovering on its own; and #48050 [https://github.com/openai/codex/issues/48050] reports that on Arch Linux, the Codex 0.157.0 package won’t start unless --no-daemon is used. These are separate reports about the same design decision: turning a CLI that used to live and die with each invocation into a client that talks to a persistent backend.

Technical Details: How the Daemon Works

What distinguishes this process from a simple background job is the combination of three operating system mechanisms. The first is reparenting to PID 1, the standard Unix technique for daemonizing a process: by detaching from the session that created it, it stops receiving signals like SIGHUP when that session ends, so the Codex CLI daemon runs from its own directory and survives closing the terminal by design, not by accident.

The second mechanism is the versioned local copy. Instead of running the binary the package manager left in the PATH, the daemon runs from ~/.codex/packages/app-server-daemon/releases/. This solves a real problem (being able to update the backend without reinstalling the entire CLI) but creates another: there are two copies of the same software on disk, and nothing guarantees they’re on the same version after the updater does its job.

The third mechanism is the updater itself, a separate loop that polls for new versions and restarts the backend if it finds one. The reporter tried shutting everything down manually and found an additional bug along the way: codex app-server daemon stop stops the app-server process, but not the pid-update-loop, which was still alive 70 seconds later and had to be killed manually. The full sequence documented to leave the machine clean is this:

codex features disable daemon_auto_start
codex app-server daemon stop
pkill -f 'app-server daemon pid-update-loop'
rm -rf ~/.codex/packages/app-server-daemon

With daemon_auto_start set to false, a new TUI session no longer triggers any daemon. There’s no documented way to confirm from the outside whether the process was fully shut down: the reporter had to check processes by hand with pkill instead of relying on an official verification command.

⚠️ Heads up: stopping the process with codex app-server daemon stop isn’t enough: the pid-update-loop updater keeps running separately and has to be killed on its own.

Impact and Analysis

The implicit contract of a command-line tool is simple: it runs when you invoke it and ends when you close the terminal. The Codex CLI daemon breaks that contract without asking for confirmation, and it does so in exactly the kind of environment (developer terminals, often with access to corporate proxies and credentials) where a persistent process with its own network connection generates the most friction.

The pattern of having a shared backend isn’t new: Docker Desktop runs a virtual machine in the background, and VS Code keeps an extension host alive while the editor is open. The difference the reports point to is twofold. First, most of those tools explicitly warn during installation that they’ll run a persistent service; Codex CLI turned it on in a minor version bump with no visible change in the installation flow. Second, those tools don’t typically auto-update in the background without user control, and the combination of a persistent process plus automatic updates plus the possibility of killing work in progress is what drew the most complaints.

Packaging fragmentation makes the problem worse. The same symptoms show up with different nuances depending on how Codex was installed: via npm on Linux and WSL2, via the Arch Linux package (#48050 [https://github.com/openai/codex/issues/48050]), and on Windows 10 LTSC. Every package manager expects to control which binary runs and at what version, and a daemon that copies and updates itself behind that manager’s back breaks that expectation for any packager other than OpenAI itself.

What’s Next

As of this writing, issue #48195 [https://github.com/openai/codex/issues/48195] is open and tagged enhancement, CLI, and app-server, with no public response from an OpenAI maintainer on whether daemon_auto_start will become opt-in. The reporter leaves three concrete requests if the default behavior doesn’t change: that the daemon shut itself down once its last client disconnects, that it not auto-update or copy itself when the installation came from a package manager (running the already-installed binary instead), and that it at least ask once before being activated.

In the meantime, the only confirmed mitigation is manual: set daemon_auto_start = false in config.toml before opening a new session, or repeat the full cleanup sequence if the daemon is already running.

Try it yourself: run grep daemon_auto_start ~/.codex/config.toml to see if your install already has the flag set, and if not, join the discussion on issue #48195 [https://github.com/openai/codex/issues/48195] to track whether OpenAI changes it.

Frequently Asked Questions

What exactly does the Codex CLI daemon do?

It starts with the first interactive session from version 0.157.0 onward, runs in the background with no associated terminal, copies the platform package to its own directory, and updates itself every hour until it’s stopped manually or the machine reboots.

How do I disable daemon_auto_start in Codex CLI?

Set daemon_auto_start = false in ~/.codex/config.toml, or run codex features disable daemon_auto_start before opening a new session; if the daemon is already running, you need to stop it and kill the pid-update-loop process separately.

Why did Codex CLI start using a persistent backend in 0.157.0?

There’s no official announcement explaining it, but the design matches the needs of Remote Control and OpenAI’s desktop app, which require a process shared across multiple sessions or devices; the complaint is that the same design got turned on for the terminal CLI too, where it isn’t needed.

Does Codex’s background daemon only affect npm installations?

No. Reports confirm the same problem on Windows 10 LTSC, on WSL2 over Linux, and on the Arch Linux package, each with a different variant of the symptom.

What is daemon_auto_start?

It’s the Codex CLI configuration flag that controls whether each interactive session starts the background backend; since 0.157.0 it comes enabled by default.
