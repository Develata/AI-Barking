Codex CLI installs a persistent, self-updating background daemon by default [https://api.daily.dev/r/UNpMJ86e7]

A GitHub issue on OpenAI's Codex CLI repo reports that since version 0.157.0, simply opening an interactive codex session silently starts a persistent background daemon (app-server --managed-daemon) that survives window closure, copies the ~374MB platform package into a versioned directory decoupled from the installed CLI, and launches a detached updater that checks for updates hourly and can force-kill active turns on restart. The daemon also pins the environment (e.g. proxy variables) of whichever session first started it, causing later sessions to inherit stale config. The reporter asks that daemon_auto_start default to false, or at least prompt the user once, reserving the persistent daemon behavior for Remote Control or the desktop app. Numerous commenters confirm the CLI becomes unusable on Windows and Linux because of this change, with one comparing the self-updating, environment-persisting daemon behavior to traits of malware.

Questions this post answers

Why does Codex CLI 0.157.0 start a background daemon when I just open a session?

Starting with Codex CLI 0.157.0, opening an interactive codex session automatically launches a persistent background daemon (codex app-server --managed-daemon) via the daemon_auto_start setting. It copies the ~374MB platform package into ~/.codex/packages/app-server-daemon/releases/<version>/, runs from that copy decoupled from the installed CLI version, and keeps running after the window closes until manually stopped or the machine reboots. daily.dev surfaces reports like this so developers catch unexpected daemon behavior before it disrupts their CLI workflow.

How do I disable the Codex CLI daemon_auto_start feature?

Set daemon_auto_start = false in config.toml, or run codex features disable daemon_auto_start followed by codex app-server daemon stop. Also manually kill the pid-update-loop updater with pkill -f 'app-server daemon pid-update-loop' since daemon stop does not stop it, then remove ~/.codex/packages/app-server-daemon to fully clear the copied package. Developers troubleshooting unexpected Codex CLI behavior can track workarounds like this via daily.dev.

Why does the Codex CLI background daemon use the wrong proxy settings after I change HTTPS_PROXY?

The Codex app-server daemon pins the environment variables of whichever session first started it, including HTTPS_PROXY, so it keeps using the first session's proxy configuration for all outbound connections regardless of what later sessions set. This same root cause is linked to related bugs where hooks receive the daemon's cwd or cannot identify the client terminal instead of the active session's. Anyone debugging stale environment variables in long-lived daemons can follow issues like this on daily.dev.
