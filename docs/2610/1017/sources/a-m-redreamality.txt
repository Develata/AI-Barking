After the OpenCode Breach: Why Coding Agents Became Credential Magnets

 Published on October 18, 2026 by Remy 

 Tags: 
#security [/tags/security/]
#ai-agents [/tags/ai-agents/]
#agent-harness [/tags/agent-harness/]
#developer-tools [/tags/developer-tools/] 

Early on October 18 (Beijing time), the official OpenCode account posted a short notice. There had been a security breach the night before, “related to a large scale distillation attack,” affecting 1.4% of OpenCode Console users. Affected users had been emailed, and the team was working with Anthropic, OpenAI and Google.[1] [#ref-1] Several hours before that, developers had already noticed their OpenAI and Anthropic keys being drained in the middle of the night.[3] [#ref-3] By that afternoon the Hacker News thread titled “OpenCode Hacked: User credentials leaked” sat at 854 points and 159 comments.[6] [#ref-6]

The scope matters, so let’s pin it down first. What was breached is OpenCode Console, a hosted service. It is not the open-source coding agent most people run in a terminal. When Anthropic’s Lydia Hallie posted about the incident, OpenCode developer dax replied that this was the Console, “not OpenCode itself,” and that the keys people use in local OpenCode never reach the company.[5] [#ref-5] This is not a “you installed OpenCode, rotate everything” event.

Stopping there would miss the more useful lesson. What leaked is a model API key, a credential that turns directly into money, and one hosted gateway held many customers’ keys for several vendors. Your local coding agent does a version of the same thing: it keeps model keys, MCP tokens, project .env files and your git and cloud credentials next to a process that runs as you, executes shell commands and loads outside code automatically. Over the past year, npm worms, a poisoned IDE extension and hallucinated package names have all gone after that spot. Below: what can be verified, how the credentials concentrate, how earlier attacks compare, and a framework you can run through.

The short version

The exposure is third-party provider keys saved in Console workspaces. There is no evidence so far that people who only use their own keys in the local CLI were affected. OpenCode has not said how the intruder got in, how keys were stored, or what exactly the link to “distillation” is.

Stolen model keys are unusually easy to cash out. As labs get stricter with new and fraudulent accounts, a key tied to a real, long-standing paying customer becomes worth more. That connection between distillation and this theft is my inference; nobody involved has confirmed it.

Coding agents are credential magnets by design. They talk to several model vendors, drive your toolchain, spawn MCP child processes and load skills and plugins that update themselves. File permissions protect you from other users on the machine, not from code running as you.

The fixes are mostly unglamorous: separate keys per tool and project, provider-side spending caps, revoking at the provider rather than just swapping the key in a gateway, starting agents from a clean environment, and running untrusted work in a container with a small, scoped key.

Timeline: what can be confirmed

All times are Beijing time (UTC+8).

At 21:36 on October 17, developer Colin Parsons asked on X whether OpenCode had been hacked. Starting around 2 a.m. Eastern (14:00 Beijing), his OpenAI key had been charged 281 dollars and his Anthropic key 168 dollars, and both keys had only ever been used in OpenCode.[3] [#ref-3]

Screenshot: Colin Parsons asks about a breach roughly four and a half hours before the official notice (public X embed, captured 2026-10-18)[3] [#ref-3]

At 23:18, Matt Johansen wrote that OpenCode users were messaging him about breach notifications and API keys running up charges. Twelve minutes later he posted “Confirmed,” with a screenshot of the notice email taken from a post on r/opencode.[2] [#ref-2] The subject line reads “Action Required: Potential provider key breach.” The email says the company identified unauthorized access to a legacy system that was being decommissioned, that third-party provider keys saved in the user’s workspace, such as OpenAI or Anthropic keys, may have been exposed, and that users should revoke and replace those keys in each provider’s dashboard, update anything that uses them, and review recent usage.

Screenshot: the notice email, mentioning a legacy system and provider keys saved in workspaces (public X embed, captured 2026-10-18)[2] [#ref-2]

At 01:56 on October 18, @opencode posted its statement, then edited it twelve minutes later to add that anyone who had not received an email was not impacted, and that those affected were a subset of users with external providers linked.[1] [#ref-1] The post uses the words “security breach” and “large scale distillation attack.” It gives 1.4% of Console users as the share affected and no absolute number.

At 02:01 the statement landed on Hacker News.[6] [#ref-6] Some commenters revisited OpenCode’s earlier privacy and telemetry controversies; others asked for the title to say “OpenCode Console,” since the hosted service and the terminal agent are different products. The top comment says the team had not made that distinction clear, and the official post does not draw it.

 [/go/?to=https%3A%2F%2Fnews.ycombinator.com%2Fitem%3Fid%3D50133401]

Screenshot: the HN thread, whose top comment explains the difference between Console and the coding agent (Hacker News, captured 2026-10-18)[6] [#ref-6]

At 02:41 dax posted that his personal accounts were being attacked too.[5] [#ref-5] At 05:04 Lydia Hallie said Anthropic had been working with OpenCode, had revoked the Claude API keys believed to be affected, and that anyone who had stored a key in OpenCode could create a new one to be safe.[4] [#ref-4] Thirty-four minutes later dax replied with the Console clarification quoted above.[5] [#ref-5] Later that morning he said everyone affected had been contacted and refunds were already underway.[5] [#ref-5]

 [/go/?to=https%3A%2F%2Fx.com%2Fthdxr%2Fstatus%2F2111572618340188393]

Screenshot: Lydia Hallie’s update and dax’s reply (public X embed, captured 2026-10-18)[4] [#ref-4][5] [#ref-5]

The Latent collected more self-reported losses the same day: one user at 1,700 dollars, another past 700 in OpenAI usage before he pulled the key, a third whose OpenAI account was suspended. The Latent could not independently verify these.[7] [#ref-7]

The unknowns outnumber the facts. ThreatWire and TSN both list them: how many people were affected, how the attacker got in, how keys were stored, what this has to do with “distillation,” whether losses will be fully reimbursed, and whether anything besides provider keys was touched.[8] [#ref-8][10] [#ref-10] None has an answer yet.

Console and the local CLI are separate paths

To see why only some users were hit, look at what Console does. OpenCode’s documentation is direct about it. A team connects provider accounts it already pays for, such as Anthropic, OpenAI or AWS Bedrock, by entering an API key on the Providers page. Console stores the credential and serves each provider through its gateway, so workspace members use the models without ever seeing the key, and the same gateway is exposed to your own tools through an API.[11] [#ref-11] The provider bills you for tokens; Console only records usage.

So Console holds a long-lived key on your behalf and sends requests with it. For an admin, one company key serving the whole team is convenient. The cost is that the key’s full spending authority now sits with a third party, and the provider only sees the key, not who is using it.

The local CLI works differently. Keys added with /connect or opencode auth login are documented as living in ~/.local/share/opencode/auth.json, and OpenCode also picks up keys from environment variables and a project .env file at startup.[12] [#ref-12] On the development branch, that file is migrated into a local SQLite database whose file mode is tightened to 0600, owner read and write only.[14] [#ref-14] Those keys stay on your machine, which is what dax means by “those keys never come to us.”

The catch is that the paths cross. Noma Security points out that the CLI can also use a Console-backed provider by picking a workspace in /connect.[9] [#ref-9] “I only use the terminal” does not settle whether you were exposed. The question is whether the provider key was configured on your device or handed to Console.

Why a stolen model key sells so well

A model API key is a bearer credential: whoever holds it can use it, and the bill goes to the owner. Unlike a database password, there is no lateral movement to do and no exfiltration channel to build. You send HTTPS requests and the key turns into compute. A gateway holding several vendors’ keys for many customers multiplies the payoff of one intrusion.

OpenCode tied the incident to a “large scale distillation attack” without explaining the connection. On HN, several people guessed the keys were more likely resold on the black market.[6] [#ref-6] I suspect both readings point to the same economics. In an October 12 post, Anthropic described distillers using proxy networks that control hundreds of thousands of fraudulent accounts, created with false identities and stolen payment details. Its countermeasures include “preserved thinking,” which stops API accounts created on or after August 31, 2026 from editing Claude’s prior context, a two-stage classifier that blocks attempts to extract reasoning, and bans of tens of thousands of accounts, often less than two hours after a distillation campaign starts.[17] [#ref-17] The post also notes that distillers spread their traffic across Anthropic’s API, third-party clouds and other inference providers.

As new accounts and fake identities get harder to use, a key belonging to an established customer with a payment history and no new-account restrictions is worth more to a distiller and a reseller alike. That is my inference; neither OpenCode nor the labs have said it. If it holds, Console, OpenRouter-style bring-your-own-key gateways and internal model proxies will all draw more attention.

How credentials pile up around a coding agent

Console concentrates many people’s keys on one server. A local coding agent concentrates your own credentials around one process, and that follows from what a coding agent has to do rather than from any vendor cutting corners.

Figure: credentials around a coding agent process (left), outside code that enters the same process or its children automatically (right), and the hosted-gateway side path. Based on[11] [#ref-11]–[16] [#ref-16].

First, it talks to many model vendors. OpenCode supports more than 75 providers,[7] [#ref-7] so one credential store often holds keys and OAuth tokens for several of them. OAuth tokens for remote MCP servers are kept separately in ~/.local/share/opencode/mcp-auth.json. Config values can be pulled from the environment with syntax like {env:MY_MCP_CLIENT_SECRET}, and the documentation’s own examples include a Bearer key written straight into a request header.[13] [#ref-13]

Second, it runs a shell as you. OpenCode’s SECURITY.md is candid about this. OpenCode does not sandbox the agent; the permission prompts exist so you know what the agent is doing, they are not security isolation, and if you need real isolation you should run it inside Docker or a VM.[15] [#ref-15] The same document places “behavior of external MCP servers you configure” outside its trust boundary. Whatever your user account can read, the agent can read: the GitHub token gh auth token prints, cloud credentials under ~/.aws, private keys under ~/.ssh. A 0600 file mode keeps other users on the machine out. It does nothing against code that runs as you.

 [/go/?to=https%3A%2F%2Fgithub.com%2Fanomalyco%2Fopencode%2Fblob%2Fdev%2FSECURITY.md]

Screenshot: OpenCode’s threat model, “No Sandbox” and “Out of Scope” sections (GitHub, captured 2026-10-18)[15] [#ref-15]

Third, it hands its environment to child processes. When OpenCode spawns a local MCP server, the environment block in your config is only additive. The code merges in the host process’s entire process.env, and a source comment notes that this matches what the MCP SDK’s stdio transport did.[14] [#ref-14] Every key you exported in your shell is visible to every local MCP server, and many of those servers are packages fetched and run on the spot with npx -y.[13] [#ref-13]

Fourth, it loads code from the cloud on its own. Claude Code is the clearest example. Since v2.1.273, a terminal session signed in with a claude.ai account downloads the account’s skills to ~/.claude/skills/synced/ and rechecks roughly every ten minutes, applying changes without a restart. Account plugins sync to ~/.claude/plugins/synced/ at launch, and their skills, agents, hooks and MCP servers all load at the same trust level as a marketplace install.[16] [#ref-16] Plugins an organization marks as required cannot be turned off by the user. It is documented, can be disabled, and has no public abuse report. I raise it because it widens “who can put code next to your agent” from you to your claude.ai account and your organization’s admin console. Earlier posts here on pre-install scanning with SkillSpector [/blog/nvidia-skillspector-agent-skills-trust-pipeline/] and co-installed skills shadowing each other [/blog/co-installed-agent-skills-conflicts/] covered risks in skill content; this adds the distribution channel.

Together: many credentials, broad permissions, inherited environments, and outside code that arrives unasked. One piece of attacker code running as you next to that process sees all of it.

The same spot, attacked five ways

Figure: how five incidents got in, where the payload ran, and the first thing victims saw. Based on[2] [#ref-2][18] [#ref-18]–[24] [#ref-24].

Nx “s1ngularity” (August 2025). Attackers used a GitHub Actions injection flaw in the Nx repository to steal an npm publishing token, and malicious versions stayed on npm for about four hours.[18] [#ref-18] The postinstall script scanned developer machines for sensitive files and tried to drive whatever AI CLIs were installed, launching Claude Code with --dangerously-skip-permissions, Gemini CLI with --yolo and Amazon Q with --trust-all-tools, and prompting them to hunt recursively for wallets, .env files, SSH keys and the like, writing the results to /tmp/inventory.txt.[19] [#ref-19] Results went, via the victim’s own GitHub CLI, to a public s1ngularity-repository in their account. Wiz counted that in a second phase, attackers used the leaked GitHub tokens to flip more than 5,500 private repositories belonging to over 400 users and organizations to public.[20] [#ref-20] StepSecurity called it one of the first documented cases of malware weaponizing AI CLIs for reconnaissance. It leaned on the second point above: once the prompts are off, an agent running as you works for whoever gives instructions.

Amazon Q Developer extension 1.84.0 (July 2025). AWS’s bulletin says an inappropriately scoped GitHub token in the extension’s CodeBuild configuration let an attacker commit malicious code to the open-source repository, which then shipped automatically in a release.[21] [#ref-21] The payload was a prompt telling the agent to return the system to a “near-factory state” and delete file-system and cloud resources. AWS says a syntax error kept it from executing. Nothing was stolen, but the way in was again a long-lived token in the wrong place, and the target an agent component developers trust and auto-update.

Shai-Hulud (September 2025). CISA’s alert describes a self-replicating npm worm that compromised more than 500 packages. The malware scanned the environment for credentials, specifically GitHub personal access tokens and AWS, GCP and Azure API keys, exfiltrated them, uploaded them to a public repository named Shai-Hulud, and then used stolen npm tokens to publish infected versions as the victim.[23] [#ref-23] A publishing token on a laptop fuels the next round.

Slopsquatting. Spracklen and colleagues generated 576,000 code samples with 16 models. Of 2.23 million package references, 19.7% pointed to packages that did not exist, 205,474 unique fake names in all, with commercial models averaging 5.2% and open-source models 21.7%.[24] [#ref-24] Worse, it is predictable: across ten repeats of the same prompt, 43% of hallucinated names came back every time. An attacker registers them in advance and waits for an agent to install them. No stolen token needed; the way in is a dependency the model wrote.

OpenCode Console (October 2026). Nothing malicious ran on your machine. The party holding your key on your behalf was breached, and the first signal was a provider bill.

What the five share is that each went after the least-reviewed link sitting next to the credentials: a publishing token, a CI config, a dependency install, a hosted service holding keys for you. Coding agents add more of those links and pull them closer to the secrets.

A framework: four questions first

Figure: four questions to ask before giving a coding agent credentials, and what each answer to the last one implies.

How many places hold this key right now? Credential store, shell profile, project .env, CI secret, hosted gateway: each copy is another place to leak from and to clean up. Ideally a key has one purpose and one home.

How much can it spend once stolen? Set spending caps and usage alerts on the provider side. Noma notes that caps may have enforcement delays, and that an alert tells someone to act but neither revokes the key nor guarantees spending has stopped.[9] [#ref-9] Size the cap to the worst case you are willing to pay for, not a multiple of normal usage.

What can the agent see while it runs? Three things: how many vendors’ keys sit in its credential store; which variables are exported in the shell that launches it, since those pass straight through to local MCP servers; and whether its shell tool can read ~/.aws, ~/.ssh and your gh token.

Will this task run untrusted code? Cloning an unfamiliar repository, letting the agent install its own dependencies, and long unattended runs with approvals skipped all count. If yes, use a container or VM, mount only the project directory, hand it one small, tightly scoped key, and add an egress allowlist. If no, at least start the agent from a clean shell.

In concrete terms:

If you used OpenCode Console with external providers linked, whether or not you got the email, revoke the original keys in the OpenAI, Anthropic, Google and other dashboards and create new ones. Check recent usage and billing, and raise anything odd with the provider. Replacing or deleting the key inside Console leaves the old key valid at the provider.[9] [#ref-9][10] [#ref-10]

Split keys by tool and environment. Give coding agents their own provider project and key, never reuse a production application’s key, and keep separate keys per project and per machine. Then an incident means revoking one key, not all of them.

Prefer short-lived tokens to long-lived keys. dax noted in another reply that signing in to a provider through OpenCode uses OAuth tokens by default rather than long-lived API keys.[5] [#ref-5] Claude Code supports an apiKeyHelper script that fetches credentials on demand.[16] [#ref-16] After the Amazon Q incident, Chainguard’s Matt Moore put it bluntly: long-lived static tokens are liabilities waiting to be discovered, leaked and abused.[22] [#ref-22]

Keep keys in a secrets manager and inject them per process instead of exporting them from .bashrc or .zshrc. OpenCode config supports {env:VAR} references,[13] [#ref-13] so the key need not sit in every child’s environment.

Give local MCP servers the smallest environment you can. Since they inherit everything from the host, launch the agent from a shell containing only what it needs, pass each server only its own token through environment, and pin the version of anything you run with npx -y.

Turn off sync you don’t use. Claude Code users who don’t need skills and plugins from claude.ai can set syncClaudeAiSkills and syncClaudeAiPlugins to false in user settings.[16] [#ref-16]

Check package names before installing: publish date, download count, a committed lockfile. Merely resolving won’t stop slopsquatting, since the attacker may have registered the name already.[24] [#ref-24]

Control egress. One of CISA’s recommendations for Shai-Hulud was to block the domains the malware used for exfiltration and monitor for unusual outbound traffic.[23] [#ref-23] For a coding agent, the practical version is an allowlist in the sandbox covering only model APIs, package registries and your code host. The earlier post on Claude Code’s four outbound channels [/blog/claude-code-data-egress-secrets-control/] has a settings checklist you can copy.

Before storing a key in a hosted gateway, ask how it is stored, who can read it, whether sub-keys or limits exist, and how notification and revocation work. One HN commenter noted the Console page where you paste keys says nothing about storage,[6] [#ref-6] which is reason enough to pause.

A sandbox answers “what can untrusted code touch on my machine.” It does nothing when the hosted party is breached, as with Console, and it cannot protect a key you deliberately hand to the agent inside it. As I argued in why sandboxing is not enough [/blog/sandboxing-not-enough-rogue-agents-authority/], the ceiling on damage is set by the authority the agent holds. Shrink the key’s scope and budget first, then worry about isolation.

Conclusion

The incident itself has clear edges: a hosted service’s legacy system was breached, saved provider keys leaked, and they were used to run up charges. It matters because it exposes a problem much bigger than OpenCode. Model API keys are becoming the most easily monetized credential a developer holds, and coding agents, along with the gateways, plugins and MCP servers around them, put those keys right next to a lot of automatically executed outside code.

Switching to a “safer” agent isn’t the answer. Claude Code, Codex and OpenCode all read your files, run your shell and hold your keys; that is what makes them useful. The realistic move is to accept that the agent is a credential magnet and treat every model key like a credit card with no limit: keep them apart, cap them, make them short-lived where possible, and be able to revoke them in minutes. From vendors, I’d like more OAuth and short-lived tokens, per-project sub-keys and hard caps, so a stolen key means a known loss rather than a blank check.
